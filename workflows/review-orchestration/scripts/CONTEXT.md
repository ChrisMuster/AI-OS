# Review Orchestration - Scripts

**Last modified:** 2026-10-19

## Purpose
Holds the review-orchestration entry point, the brief checker, and the engine: the build-and-review loop and every part it calls, for either pairing of the two AIs. `brief.py` reads a run brief, classifies every line the way a CommonMark renderer would (so a heading inside a comment or a fenced block does not count), splits the brief into its seven sections and applies each section's rules, reporting every problem rather than the first. It never runs a command the brief contains. `limits.py` reads each provider's usage and decides whether a run may start its next step; `runrecord.py` creates a run's record folder and keeps its state file; `settings.py` reads the settings file, the model and effort for each provider in each role, and gives a run its roles from the builder the user names. `approver.py` decides every tool call the builder makes; `stopreasons.py` holds the pause and stop-reason vocabulary, reads the builder's and reviewer's structured replies, and applies the loop-exit rules; `providers.py` runs the builder and reviewer sessions. `loop.py` is the build-and-review loop that drives them: it runs a builder pass, then review rounds and fix passes until a stop reason, with `worktree.py` measuring and recording what the run changed, `checks.py` running the mechanical checks before each review and `packet.py` writing the review packet. Roles are named by what they do, not by provider: the user names the builder for each run (`--builder`), the other provider reviews, and both pairings are built. A Claude builder is held by the approver in the orchestrator's own process. A Codex builder is held by `codex_hook.py`, a program Codex runs before every tool call from a frozen copy outside the project, deciding with `codex_rules.py` and the same approver, with Codex's sandbox beneath it for file writes, an approval handler that accepts only what the hook allowed, and a check of the whole project after every turn. `run.py` is the workflow's entry point. `container.py` runs builder-written code in an offline container over a clean copy, which the checks after every builder turn have used since stage S6b, and `check_server.py` is the check helper that gives a builder that as its one way to run a check, plus a clock; since S7 it is every builder's one MCP server and the shell is no longer theirs. Since S6a a run's own code comes from its starting commit: `start.py` is the one way in, `frozen.py` makes the run's frozen folder with a trusted copy of that commit, a started run is handed to the trusted copy of `run.py`, and `tripwire.py` fails a process if it executes a file from the live tree, the orchestrator's own since S6a and every Python process the run starts since S7. Since S7 every session the run opens starts only trusted programs: no project hook or plugin runs in any of them, a builder's calls go through the frozen folder's trusted copy of the rule hooks, and the Codex reviewer runs no project code. Since A3 chunk 1 (plan 10.3 steps 6 and 8) `run.py --approve` continues a run paused for plan approval into the build, after four read-only checks that the project has not moved, and `run.py --amend` replaces such a run's brief; the frozen folder's write-once `approval.json` is the one source of the edit paths and the image tag for the Codex hook, the Claude builder's approver and the check helper, and until the planning half is joined a start writes it itself, straight after its host start check.

## Contents
- start.py - `workflows/review-orchestration/scripts/start.py` - The starter (plan 7.0 items 2 and 3, S6a), the way every start, brief check, resume, stop, approval and amendment is entered. Standard library only, importing nothing from the project; the mode is the first argument. `--run` (dry or real) refuses unless `git status --porcelain --untracked-files=all` over the whole project prints nothing, and `--check-brief` unless it prints nothing for the two folders the brief checker loads, and both refuse a `BOOK_DRAGON_ROOT` naming any project but the starter's own (code review R22-1); then it runs the project's `run.py` under `.venv`. `--resume <run-id>`, `--stop <run-id>`, and A3's `--approve <run-id>` and `--amend <run-id> <revised-brief>` (`TRUSTED_MODES`, plan 10.3 step 8, added by hand on 2026-10-15 since no builder may change the starter) make no git check: they refuse unless the run id has the run-record form and its frozen folder holds `hook.json` and the trusted `run.py`, with `hook.json` naming this project, then run that trusted `run.py` with every argument after the run id passed on unchanged. It sets a marker so `run.py` knows it was entered through it. A refusal exits 3 having run nothing. No builder may change it.

- run.py - `workflows/review-orchestration/scripts/run.py` - The entry point. `--check-brief <brief>` calls the checker and returns its result unchanged (the same stdout, exit code and LOG.md entries as `brief.py --check`). `--run <brief> --builder claude|codex --item <item> --git-dir <dir>` starts a run with the named provider building and the other reviewing (no default: a missing `--builder` is a usage error, and `--builder` with any other mode is refused, since a resumed or stopped run keeps the roles it started with; `--allow-paid` permits only the next step with `--run`, `--resume` or `--approve` and cannot join `--wait`; `--wait` sleeps through a usage limit with a reset time; `--inject-limit <step>` is test-only); `--resume <run-id> [--rounds N]` continues an ended run; `--stop <run-id>` ends a paused one; since A3 chunk 1, `--approve <run-id>` approves a run paused for plan approval and builds it (`loop.approve`), and `--amend <run-id> <revised-brief>` replaces its brief and supersedes its open plan-review findings (`loop.amend`), printing that the run stays paused and exiting 0; both are in `STARTER_MODES` and go straight to the trusted copy, which refuses a run id other than its own. `--dry-run` logs to stderr for a check, makes only the read-only preflight for a run, and makes every check of a resume, stop, approval or amendment, changing nothing. Exit 0 on a passed check or a run ending `reviewed-clean` or `clean`, 1 on a failed check or any other end, 2 on a usage error, 3 when a run is refused before it starts or resumes. Run from the command line under any interpreter other than the project `.venv` one, it first re-runs itself under `.venv` (`reexec_under_venv`, as the close-out verifier does), because the SDKs live there and plain `python` finds the system interpreter in some shells, Codex's PowerShell among them; everything the run starts uses `sys.executable` and so follows. With no `.venv`, it carries on and the SDK check names what is missing. Since S6a (plan 7.0): run from the project for a brief check, start, resume, stop, approval or amendment without the starter's marker, it prints the starter command and exits 2, and it does so before importing anything of the project (code review R18-2), so a builder's edit to a module it imports never runs on the way; the starter's path is restated there (`STARTER_PATH`) for that reason. A start makes its preflight, start check, frozen folder and run record in the live tree, then `hand_over` arms the tripwire and runs the frozen folder's trusted copy of this script with `--advance <run-id>` (a hidden mode only that copy accepts), which takes every step, and returns its exit code. If the hand-over fails (the tripwire cannot be armed, the trusted copy cannot be started, or it exits without ending the run), `hand_over` ends the run `error` naming why, so no run is left marked `running` and the starter can resume it (code review R19-3); an interrupt is left to the trusted copy, which receives it too. The trusted copy (`trusted_frozen_folder`, by its path) runs `set_up_trusted` before importing anything else: it arms the tripwire, puts the tripwire folder first on `PYTHONPATH` (`with_tripwire`, keeping what was there) and sets `BOOK_DRAGON_FIRE_LOG` to the run's fire log (S7), so every process the run starts inherits both, then takes the project root from `hook.json`, refusing one without `AGENTS.md` [[AGENTS]] or a set `BOOK_DRAGON_ROOT` that disagrees, and exits 3 naming the problem; it refuses `--run` and a run id other than its own folder's. The hand-over gives its child the same `PYTHONPATH`.

## Inputs
- A project-relative path to a brief, from the command line.
- The project tree, for resolving the Source section's paths.
- For `limits.py`: an initialised Codex client, and the Claude SDK's rate-limit events and assistant messages, both passed in by the caller.
- For `settings.py`: `workflows/review-orchestration/config/settings.json` [[workflows/review-orchestration/config/CONTEXT]].
- For `approver.py`: the edit paths, passed in by the caller (for a run's Claude builder, `loop.approver_for` reads them from the frozen folder's `approval.json`), and `workflows/review-orchestration/config/verify-commands.txt` [[workflows/review-orchestration/config/CONTEXT]].
- For `stopreasons.py`: the reviewer's parsed reply and the builder's reply text, passed in by the caller.
- For `providers.py`: the loaded settings, an `Approver`, and each provider's subscription login; the SDK entry points can be replaced by factories, which is how the tests run without a model call. A Codex builder also takes the run's folder, whose name is the run id, and a Claude session the run's usage object.
- For `codex_rules.py` and `codex_hook.py`: `workflows/review-orchestration/config/codex-read-commands.txt` and `codex-verify-commands.txt` [[workflows/review-orchestration/config/CONTEXT]], read by the hook from the run's frozen folder, never from the project, the folder's `hook.json` (the run id and the project root) and its `approval.json` (the approved edit paths).

## Outputs

## Steps
Checking a brief:
1. Read the brief: refuse an absolute path, one resolving outside the project, a folder, a missing or unreadable file, or invalid UTF-8.
2. Classify each line (blank, text, fence, heading) with HTML comments removed.
3. Check the H2 headings: the seven required ones, each once, spelled as shown, in order.
4. Check each recognised section against its own rules.
5. Print the result and append LOG.md with a completion or failure entry.

Running a brief (`start.py --run`, which refuses an uncommitted tree and then runs `run.py --run`):
1. Preflight, creating nothing: a builder is named and the pairing has a model for every role, the brief passes, the item name is valid and its packet absent, the edit paths hold no uncommitted work, no `.env`-named file is both untracked and unignored, both SDKs are installed, and the personal repository is captured; then Docker (started if it is not running, a dry run only asking); then Codex usage is under the ceiling and its credit snapshot can be tracked.
2. Run the close-out verifier read-only and refuse unless it is clean (a dry run makes it too); then the image step, its constraints file in a temporary folder (a dry run stops here, saying whether a real start would reuse or build the image, or that this is unknown while Docker is not running); then make the run's frozen folder (`frozen.setup`; a failure refuses the start, leaving nothing) and, until A3's planning half is joined, write its `approval.json` from the brief's edit paths and the image tag (`frozen.write_approval`, with no pause and no checks; a failure refuses the start and removes the folder), create `runs/<run-id>/`, copy the constraints file, the brief and the resolved settings in, record both start commits and the starting diff, and append `started` to LOG.md. A start refused after this run started Docker stops it again. From the command line the run is then handed to the frozen folder's trusted `run.py` (`--advance`), which takes the steps below.
3. Builder pass. An empty diff under the edit paths ends the run `no-change-made`. With a Codex builder, every builder turn (this one and every fix pass) sits between two inventories of the project, and any change outside the edit paths ends the run `error`, except the one run-record file the session copies in during a turn, its hook's decisions file (`worktree.TURN_RECORD_WRITES`); any other change to the run record, such as its saved settings, ends the run too, even under an edit path that covers this workflow, since run records are judged before edit paths.
4. Each review round: run the mechanical checks (the close-out verifier and the acceptance commands in the container over a clean copy, then the four trusted host checks; a Docker or copy failure ends the run `error`), record the round, have a fresh reviewer session review, label the findings and write the packet. No findings ends the run `reviewed-clean`.
5. Each fix pass: resume the builder's session with the open findings and read its action for each.
6. Before every step, read Codex usage and the saved Claude event; before each Claude step in a running run, send a one-turn probe unless a known overage stops it. Stop `usage-limit` on the ceiling, a hard limit, or unpermitted paid usage. During a Claude step interrupt on a new unpermitted overage event. `--allow-paid` permits only the next step. After every step, apply the stop-reason rules and write `state.json`.
7. At the end, write the report and packet; copy the rule-hook fire log into the run record; stop Docker if the run (or its resume or approval) started it; at a stop reason a resume cannot continue, remove the frozen folder, the clean copies and the fire-log folder; write the report again with what happened; and append LOG.md with a completion or failure entry.

Approving a run paused for plan approval (`start.py --approve <run-id>`, which runs the trusted `run.py --approve`; plan 10.3 step 6):
1. Refuse, changing nothing, a run whose earlier approval failed after its first project write, one not paused `awaiting-plan-approval`, one with no frozen folder, or one whose `approval.json` exists; read the run's `brief.md` with the brief checker, logging off.
2. The four read-only checks over the approved edit paths (both `HEAD`s as recorded; no uncommitted public change under the paths; no change to a personal file tracked under them; no uncaptured Category A file under them outside this run's own record); every failure is named and nothing changes. Then a fresh Codex reading and credit snapshot. A dry run stops here, saying what approval would do, with no Docker command.
3. Docker (started if it is not running) and the check image. A failure refuses, stops a Docker this approval started, writes nothing, and leaves the run approvable.
4. The run's writes in the project: the `started` entry in the workflow's LOG.md, then the item's packet from the run's ledger, both diffed either side of the writes and recorded in `check_writes` whether or not the edit paths cover them.
5. The scope rebuild: `start/` and `state.json`'s `edit_paths`, `acceptance` and `start.snapshot` from the approved brief, keeping the recorded `HEAD`s.
6. `approval.json`, then the constraints file, Docker and image records, credits, the run's step set to `approved` (the build's entry step, the planning step it paused on kept in the `approval` record), and the run set from paused to running and saved. A failure in steps 4 to 6 restores `state.json`, records `approval_failure`, appends a `failed` entry if `started` was written, stops a Docker this approval started, and refuses for good, naming `--stop` and a new run.
7. The build starts and the run goes on as a run does.

Amending a run paused for plan approval (`start.py --amend <run-id> <revised-brief>`):
1. Refuse as approval's step 1 does, and refuse a revised brief the checker refuses (logging off), changing nothing. A dry run stops here, saying what it would replace and which findings it would move.
2. Copy the revised brief beside `brief.md`, mark every open ledger entry `fixed` with the note `superseded by amendment` (so it is Addressed), record the amendment, save `state.json`, then replace `brief.md`; if any of that fails, put the ledger and `state.json` back and refuse (or, if they cannot be put back, record `approval_failure`); re-render `plan-review/packet.md` if one exists. `edit_paths`, `acceptance` and `start` are untouched, and the run stays paused.

## Choices where the specification is silent
The specification leaves these to the builder. Each is covered by a test in `workflows/review-orchestration/tests/` [[workflows/review-orchestration/tests/CONTEXT]]: the brief checker's in `test_brief.py`, the usage readings' and settings' in `test_limits.py`, the run record's in `test_runrecord.py`, the approver's in `test_approver.py`, the stop reasons' in `test_stopreasons.py`, the sessions' in `test_providers.py`, the Codex rules' and hook's in `test_codex_rules.py`, the loop's in `test_loop.py`, and approval's and amendment's (A3 chunk 1) in `test_approval.py`, with the frozen folder's in `test_frozen.py` and the check helper's in `test_check_server.py`.

**Reading the file**
- The path is resolved against the project root, not the working directory, so the result does not depend on where the command is run. Backslashes in the argument are accepted as separators; a path that resolves outside the project is refused, and so is a folder.
- A UTF-8 byte-order mark is refused and the rest of the brief is still checked. Invalid UTF-8 is refused and checking stops, since nothing after it can be read reliably.
- CRLF and a lone CR are accepted as line endings.

**Headings**
- Headings follow CommonMark: up to three leading spaces, and `##` must be followed by a space, so `##Goal` is text. The title is compared after trimming, but a closing `##` is kept as part of it, so `## Goal ##` is an unexpected heading.
- An underlined (setext) level-2 heading is refused anywhere: headings must be written with `## `. A dash line under a list item or under indented code is not a heading, as in CommonMark.
- A level-1 heading is allowed before the first section and refused after it.
- Content under an unexpected or repeated heading is not checked, and a missing section gets only its `Headings` line, not an "empty" line as well.
- Each heading that appears after a later one is reported as out of order, naming the latest heading seen so far. Its section is still checked.
- A heading that differs from a required one only in case is reported with the correct spelling.

**Content**
- Deeper headings (`###` and below) are not content: a section holding only them is empty, and they are skipped when reading bullets.
- The `...` and angle-bracket placeholders may be bulleted with `-`, `*` or `+`. The two placeholder words the specification names (the upper-case to-do and to-be-decided markers) are matched with case and as a prefix, so a plural of either is a placeholder and the lower-case word is text. A placeholder line is ignored wherever it appears; it is not refused when the section has other content.
- A fenced block is reported once, at its opening line, and its lines are not content.
- Section reasons carry their line number.

**Bullets**
- Only `- ` starts a bullet; `*` and `+` bullets are refused. Leading indentation is allowed. A line that is not a bullet, including a wrapped continuation line, is refused.
- Open questions: `None` must be written with that case and alone. The question and answer split at the first `| Answer:`; an empty question is refused.
- Edit paths: the path and command split at the first `| Measure:` (case-sensitive). `.git`, `.env` and duplicates are compared the way Windows compares names: without case, ignoring trailing dots and trailing spaces. `docs` and `docs/` are duplicates; a folder and a file beneath it are not. An empty or `.` component and a backslash are refused.
- Source: a name ending `.md` is matched without case. Brackets, quotes and trailing punctuation are stripped from a word outside backticks before it is tested, so `plan.md.` and `(docs/plan.md)` are caught. A backtick-quoted path with a backslash, a leading `/` or `~`, a drive letter or a `..` component is refused; `.` and empty components are ignored. Existence is checked with exact spelling and case, so a brief that passes here passes on a case-sensitive file system too. A trailing `/` requires a folder. An unbalanced backtick is refused, and the text after it is treated as unquoted.

**One command**
- Command substitution is refused even inside single quotes.
- An unquoted operator is reported as the whole run of operator characters, so `2>&1` reports `>&`.
- A wrapper is looked for as the program, `argv[0]`, and nowhere else, so a shell or launcher name later in the arguments, as in `rg bash -c README.md`, is data. A launcher that runs another program (`env`, `sudo`, `doas`, `xargs`, `nohup`, `nice`, `timeout`, `time`, `command`, `exec`, `stdbuf`, `runas`, `start`) is refused outright as the program, with `` `<launcher>` launches another program; name that program directly ``. Reading past it would mean modelling each launcher's options (`timeout 10`, `sudo -u x`), and `env -S` / `--split-string` hide a whole command in one argument; a brief can always name the program itself. Chosen in code review round R2 over Codex's suggested per-launcher parsing, which the round's R1-3 repair had already shown to be a source of both false refusals and bypasses.
- Only a shell's own options count, read up to its script operand (or `--`), so `bash scripts/check.sh -c` passes: that `-c` belongs to the script. Options that take a value (`-o`, `+o`, `-O`, `+O`, `--rcfile`, `--init-file`) skip it, so `bash -o pipefail -c ...` is still caught. `-c` combined with other single-letter flags (`-lc`, `-ec`) and `--command` count; for fish, `-C` and `--init-command` too, which run a string there and mean noclobber elsewhere.
- For `cmd`, any argument beginning `/c` or `/k`. For PowerShell, parameters are matched as PowerShell matches them, by prefix, with `-`, `--` or `/`: any prefix of `-Command`, `-EncodedCommand` or `-CommandWithArgs`, plus the `-ec` and `-cwa` aliases, read up to `-File`, after which the arguments are the script's. Windows PowerShell (`powershell`, not `pwsh`) treats a bare argument as a command string, so a bare argument with no `-File` before it is refused.
- The wrapper check reads the command twice: once with POSIX quoting, and once with quotes honoured but backslashes kept, because POSIX reading turns an unquoted `C:\Git\bin\bash.exe` into a name that is no longer `bash`. Either reading finding a wrapper refuses the command; quoted text is data in both.

**Command line**
- A usage error exits 2 (the argparse default), distinct from a refused brief.
- A refused brief logs `failed`; an unexpected error logs `failed` and is then raised. A LOG.md that cannot be written fails the check: the audit trail is part of it, so a brief that would pass prints `FAIL: Brief: could not append to the workflow LOG.md (<reason>)` instead of PASS and exits 1, and a refused brief gets that line first.

**Usage readings (`limits.py`)**
- A Codex JSON-RPC error, a response that is not a JSON object, and a response that fails validation are each an `unavailable` reading carrying the error text, as the plan says; a validation error is kept whole, flattened to one line, since its first line names only the model and the failing field is on the lines after it. A closed transport (`TransportClosedError`) is not: it is raised, because it is a provider failure rather than an answer about usage.
- A negative Codex result holds for the rest of its run, as the plan says, through `RunUsage`: one object per run, every Codex reading passed through it. After the first `unavailable` reading, a later `reported` one comes back `unavailable`, naming the first failure and keeping its own figures for the report, so the ceiling is not applied. A later `limit-reported` reading is passed through unchanged and still stops the run. A new run starts from a new object.
- Where two windows report the same percentage, the one with the later reset is taken, since waiting for the earlier reset would not free the other window. An unknown reset counts as earlier than a known one.
- When Codex says usage is not allowed and windows are present, their highest reading is still recorded beside the stop, so the report shows the numbers the plan asks for.
- A null or absent `ordinaryUsageAllowed` stops as `usage-limit` with that field named, even with a window present. A one-step paid permission may pass that unknown value; `false` remains a hard stop. `true` with no window remains an unavailable reading.
- Claude's percentages come from each event's raw `unifiedWindows` map first and its top-level `utilization` only as a fallback: in the event recorded by the B1 probe the top-level field was empty and the real figures were only in the map. Windows accumulate across events, and the latest event's `status` is the current status, so a later `allowed` clears an earlier `rejected`. A `rejected` status stops the run whatever the percentages say; its reset time is the event's own, or the highest window's where the event gives none.
- Paid overage stops the run (the user's rule, now in plan section 10.10 item 3): an event with raw `isUsingOverage` true, or an event for the `overage` window, makes Claude's reading `limit-reported` with the reason `using paid overage`. The `overage` window is never counted as an included window, so it never sets the percentage or the reset time; the reset reported is the fullest included window's, which is when the run can resume. The latest event decides, so overage that has ended no longer stops a run, and overage that is available but unused never did. Overage is checked before a `rejected` status, so an event that is both (overage itself refused) still reports `using paid overage` with the included window's reset, since that is when the run can resume. Where the fullest included window carries no reset of its own, the event's top-level reset is used only if the event names that same window; a different window's reset would not free it, so the reset is reported as unknown instead. A stop with an unknown reset does not resume on its own: the user checks whether the allowance has reset and says when to start again (the user's ruling, 2026-09-26).
- Since the 2026-10-16 rule, an unpermitted Claude session is interrupted on its first paid-overage event and the step ends `usage-limit` with its partial diff, even if saving that event fails. The ceiling is still checked only before a step. A known saved overage stops a preflight or step before a probe is sent unless its reset passed or the step has paid permission. A saved reading whose known reset has passed is treated as unavailable until the next event; this also prevents an old ceiling reading blocking a resume forever. With an unknown reset, only the first step of a user-started plain resume gets one chance to probe; a later step asks again. A probe with no event leaves `claude_last_reading` unchanged but gives its step an unavailable live reading. A newly discovered overage is recorded as `probe_on_overage`.
- Mid-session, Codex's `usageLimitExceeded` turn error and Claude's `rate_limit` assistant-message error are usage limits. Codex's `rateLimitExceeded` is not: it is short-term request throttling, not the plan allowance, and is left to the caller as an ordinary error.
- `check_ceiling` checks every `limit-reported` reading before any percentage, so a provider that reports its limit reached stops the run even when another provider is above the ceiling too. A reading exactly at the ceiling stops.

**Run record (`runrecord.py`)**
- A run ID is `YYYYMMDD-HHMMSS-xxxx`: the local start time, so IDs sort by start, plus four random hex digits, so two runs started in the same second do not collide. Any other form is refused, which also rules out a path separator or `..` in an ID.
- Creating a run whose folder exists is refused. A run record is never reused or overwritten.
- The first `state.json` holds `status: running`, `step: created`, no pause, and empty `stop_reasons` and `rounds` lists: the fields plan section 10.7 names, present from the start.

**Settings (`settings.py`)**
- A missing `usage_ceiling_percent` takes the default, 80. A present one outside `0 < value <= 100`, or not a number (a JSON `true` included, although Python counts `bool` as `int`), is refused rather than replaced by the default.
- `max_turns` has defaults of 80 for the Claude builder and 200 for the Claude reviewer; each override must be a whole number of at least 1, and unknown keys are refused. `usage_probe_model` defaults to `claude-haiku-5-5` and must be a non-empty string. Each run saves its resolved settings, so a resume keeps its turn limits and probe model.
- Models are held per provider and per role (`models.<provider>.<role>`), not per role alone, so that either provider can hold either role with no code change. The user's decision of 2026-09-26: roles are named by what they do, and the reverse pairing must stay possible.
- Roles are not a setting (the chunk (d) short plan, 11.1, the user's option A of 2026-10-04): the first proof run showed that swapping them by editing `settings.json` refuses every run, because the tests assert the shipped file and doc-sync sees the config folder change. `assign_roles` takes the builder named on the command line and gives the reviewer role to the other provider. A settings file that still holds `roles` is refused naming `--builder`, rather than ignored, so a stale file cannot quietly decide the pairing. `loop.preflight` also accepts settings that already carry `roles` with no builder named, which is how the tests and a caller holding resolved settings pass them; a run started from the command line always names one.
- The defaults are exactly the pairs plan section 11's table names, which since chunk (d) include a Codex `builder` and a Claude `reviewer`, so either pairing runs on the defaults. A role with no model for its provider is still refused, naming the missing entry, rather than guessed.
- The synthesiser has no entry: section 11 makes it the builder's provider on the builder's model, so it reads the builder entry.
- Only the pairs the assigned roles will use are required: the builder's provider needs `builder` and `planner`; the other provider needs `planner`, `plan_reviewer`, `reviewer` and `intent_checker`. The reviewer is always the provider the user did not name, since one AI builds while the other reviews.
- An entry given in the file overrides that provider's role only; everything else keeps its default. Unknown keys inside `round_caps`, `models` and a model entry are refused, since a misspelt role would otherwise be silently ignored. Unknown top-level keys are still kept, as before.
- Effort is checked against the values each pinned SDK accepts, per provider: `ultra` is valid for Codex and refused for Claude. Round caps are whole numbers of at least 1 (`true` refused).

**Approver (`approver.py`)**
- Refusal is the default: a tool not named below is refused, so a tool added to Claude Code later is never allowed by accident.
- Read tools: Read, Grep, Glob, TodoWrite and ToolSearch (the last so deferred Biblio Tools schemas can be loaded). Read, Grep and Glob are allowed subject to the read rules, which bind both builders and the reviewer through one function (the user's choice of 2026-10-02 to close the gap for the Claude builder in chunk (d)): a call is refused when any string in its input, however nested, names a `.env` file by the test the shell checks use, a Grep's `pattern` apart, since that is the text searched for; and a Grep carrying a `glob` key is refused whatever its value, since an explicit wildcard overrides the ignore rules that keep a `.env` file out of a folder search. A Glob lists names and reads nothing, so it is allowed under the first rule alone. A refused read records its path, pattern and wildcard as the detail.
- An edit is allowed when the file resolves (links followed) inside the project and its path, compared the way `brief.py` compares edit paths, equals an edit path or lies under it. `workflows/x-old/` is not under `workflows/x/`. A path through `..` is judged by where it lands. `.git`, `.env` and `.env.*` are refused even inside an edit path, and so is an alternate data stream (`file:stream`); so are the project `.venv`, the starter and, since S7, `.codex` (decision 33), only at the project root: a `.codex` or `.venv` folder lower down is not the project's.
- No line of `verify-commands.txt` accepts a flag it does not name: a free argument cannot start with `-`. The audit's `--save` and close-out's `--repair` both write outside any edit path (review finding R2-2). The test-runner line takes test names and an optional `-v` only, since a `--help` there exits 0 without running a test (R3-1). A test checks the rule on every line for bare and valued flags at every position (R4-1); it checks those shapes, not every possible input.
- A check command (since S7 the check helper's `run_check`, never the shell) is allowed only when the whole trimmed command matches one line of the builder's verification list, which is one regular expression per line (the user's choice, 2026-09-26, over literal prefixes: it is the B2 form that has run). On top of any match, a command with a `..` path component, one naming a `.env` file, one spanning lines, or one whose quoting `shlex` cannot read is refused, and so is a `run_check` call carrying any argument but `command`. The `..` refusal exists because a listed test-runner pattern would otherwise run a script anywhere, by stepping back out of a `tests` folder with parent components. The test is `verify_refusal`, the helper's own, so nothing the approver allows is refused by the helper and nothing is allowed that it would not run.
- Since S7 (plan 7.4, 7.6) a builder has no shell and no Biblio Tools tool, all refused outright with a message naming the check helper: the Biblio Tools tools run the working tree's scripts on the host. Its clock is the helper's `get_timestamp`, allowed only with no arguments.
- Every refusal message starts `Refused by the orchestrator:` and says what is allowed, so the builder can act on it; every refusal is recorded with the tool, a detail cut to 300 characters, and the reason.

**Stop reasons and replies (`stopreasons.py`)**
- The builder's action list is the last fenced `json` block in its reply, parsed strictly (the user's choice, 2026-09-26): every open finding exactly once, only `label`, `action` and `note`, and nothing that is not open. A block written earlier in the reply as a draft does not count.
- The reviewer's field is named `reraises`, as the plan says; B2 called it `repeats`. An empty string means new, since a strict structured-output schema requires every field. A `reraises` naming a label the run has not issued is a malformed reply.
- A label in a finding title is refused twice (the user's choice, 2026-09-26): the schema's `title` carries a pattern refusing it, for the provider to enforce if it accepts the pattern, and `parse_review` checks every title whatever the provider did. The script's check also catches `R3 - 1` and a dash-joined label; `R2-D2` and `PR12-3` are not labels.

## Known Issues
- The one-command rule refuses the listed shell wrappers only. An interpreter given code as a string (`python -c`, `node -e`) passes, because it is one command with quoted arguments. The checker never runs anything; whether an acceptance check does what it claims is the intent check's job in a later sub-stage.
- The launcher list is fixed. A shell wrapper behind a launcher not on it (for example `parallel sh -c ...`) is read as that launcher's data and passes; adding a launcher is a one-line change, which the every-launcher test then covers.
- A valid command that happens to go through a launcher, such as `env rg bash -c README.md`, is refused. That is deliberate: the refusal names the launcher, and dropping it gives an equivalent command that passes.
- The line classifier models the CommonMark cases a brief uses (ATX and setext headings, fences, HTML comments, list items, quotes, indented code). It is not a full CommonMark parser: an HTML block other than a comment, or a lazy continuation line inside a quote, is read as plain text.
- The Windows name folding for `.git`, `.env` and duplicates covers case, trailing dots and trailing spaces. It does not cover short 8.3 names or alternate data streams.
- Claude reports no usage until a session emits a rate-limit event, so at a run's preflight Claude's reading is always `unavailable` and the ceiling cannot be applied to Claude before its first Claude step. The reading lives in the run's one usage object, which starts empty in each process, so it is `unavailable` again after a resume until a Claude session reports.
- A Codex builder turn holding an item that is neither a message nor a tool call ends the run `error`, as the short plan specifies. `plan` and `contextCompaction` are such kinds: a long turn in which Codex compacts its own context would be stopped. Neither appeared in the probe turns; the proof run is the first long turn.
- A Codex builder is kept off the network by its hook, not by its sandbox, which does not block the network on the build machine. A hook that fails lets a call run: a shell command or a patch is still refused by the approval handler, and web search is switched off, but another tool needing no approval could run once before the session ends the turn.
- The check helper's tools are named `mcp__checks__run_check` and `mcp__checks__get_timestamp` in both providers' calls, by the standard MCP naming Codex's own text describes; a real Codex turn shows it in live check 3. If Codex's hook saw another name, every helper call would be refused, a lost check rather than a gap. Codex does ask approval for an MCP call: proof run 1 (2026-10-12) ended `error` when, after the hook allowed a `run_check`, Codex sent `mcpServer/elicitation/request`, which carries no call id to match to the hook's decision line. Since decision 36 the Codex builder's `checks` server is launched with `default_tools_approval_mode="approve"`, so Codex asks for none of that server's tools; each call is still judged by the run's hook and by the helper itself. The launch is refused unless `config/read` reports the setting, and a request that still arrives, from any server, ends the turn as before. That no request arrives in a real builder turn is the rerun proof run's live check 3.
- Whether `disableAllHooks` leaves the orchestrator's own `pre_tool_use` callback firing is live check 4; if it does not, the build stops and the user is told (plan 7.6 item 2). Proof run 2 (2026-10-13) showed it firing for the check tool, the shell and an edit through their denials, but could not show it judging every call, since the callback's list was never written out; since decision 39 each Claude builder step's `live.claude_builder_callbacks` entry compares the judged calls with the turn's tool-use blocks, and the rerun of run 2 is what reads it. A mismatch refuses nothing: it is evidence for the user. A call Claude Code refuses itself before any hook runs (an edit of a file not yet read) is never judged; since plan 10.7 it is told apart by its error result's `<tool_use_error>` element and listed in `rejected_before_hook`, so `not_judged` holds only calls that ran unjudged. The element is Claude Code's own wording, not a documented interface: if a version stops using it, such calls fall back into `not_judged`, an over-report rather than a hidden call. Live check 4c, a required pass, passed on 2026-10-11: a command the Codex reviewer's model ran got the tripwire, as the launch self-test's `command/exec` does.
- The Codex reviewer is told to run no project code and its Python processes load the tripwire (decision 34); code that is not Python, which the project barely has, is guarded only by the instruction.
- No run may change `.codex/` (decision 33): a change to Codex's configuration or rules is made by hand, outside a run.
- The frozen folder is in the system temp folder, made for every run and removed only at a stop reason a resume cannot continue (plan 7.3), so it is kept after `max-rounds`, `usage-limit` and `error`. Something that clears it between a stop and a resume means the starter cannot resume or stop the run, which is then started again from its brief. A removal that fails is recorded in the report and `state.json` (`cleanup`), and the folder is then left for the user to delete.
- The check after every turn takes two inventories per builder turn, about 1,100 files and a few seconds each on 2026-10-02. During a Codex builder turn nothing else may write a tracked or Category A file anywhere in the project, or the run ends `error`.
- The Codex builder's facts are evidence for one machine and one version (Windows 11, `openai-codex` and `codex-cli` 0.157.0): the launch readings, the hook's trust override, and the notification shapes. `CodexBuilder` reads the hook's trust and the thread's settings back at every launch, so a version that stops honouring them stops the session; and it uses `CodexClient._request_raw`, a private method an SDK upgrade can move.
- The read rules leave two routes by which a `.env` file could reach a Claude session, accepted by the user on 2026-10-02: a `.gitignore` changed during a run, and a `.env`-named file that git tracks. The start-up check is made once, before the run.
- Codex's paid use is guarded by the credit rule (plan 10.10 item 3), checked in `loop.py` before every Codex step; `limits.py` itself reads no credit field.
- The `awaiting-user` pause is in the vocabulary and `--stop` ends a paused run, but nothing in the loop enters that pause yet: a builder question the brief does not answer arrives as its reply, like any other. The `awaiting-plan-approval` pause belongs to the planning sub-stage: since A3 chunk 1 `--approve` and `--amend` act on a run in it, but nothing enters it until chunk 3 joins the planning half, so they are proved only on runs the tests put in that pause, and an amendment does not yet restart planning.
- Until chunk 3, a start writes `approval.json` itself with no approval checks, as the plan says, since nothing can have moved between the start check and the frozen folder.
- A failure from approval's step 3 on whose own record cannot be written to `state.json` (a disk fault) leaves no `approval_failure`; a retry is then refused only if its checks find the earlier writes or `approval.json` exists. The refusal says the record could not be written.
- The live proof run settles whether Codex accepts the schema's `title` pattern (a lookahead), whether a `PreToolUse` hook's `deny` stops a call a `permissions.allow` rule permits, and which model spelling Claude reports; their results are in the decision log. The tests prove the loop's handling of each answer, not the providers' answers.
- The doc-sync filter reads the directory from the start of each finding's message, the form every doc-sync WARN has today. A WARN written another way would be treated as outside the edit paths and listed but not raised.
- The close-out baseline is taken once, at the start. Uncommitted work outside the edit paths that changes during a run (someone else editing the tree) can still turn into a new close-out failure the builder did not cause. The plan's rule that the user does not edit during a run (derailment check D7) covers it.
- The Category A selection takes about 4 seconds, measured on 2026-09-30, and is taken at the start, after the build and in every review round. Its git commands run in the process's working folder, so a run is started from the project root, as every workflow script is.
- A dry run cannot say whether a real start would reuse or build the image while Docker is not running, since only the engine knows which images exist and a dry run never starts it; it reports the image as unknown instead (R24-1).
- A run cannot start while the project's close-out checks are failing or skip a scope, whatever the cause: the failure has to be fixed first. Measured clean through every round of this chunk's review except while Biblio's own documentation was mid-edit.
- Start times recorded before 2026-09-30 carry only `created`, to the second, so the price alarm cannot order such a run against another from the same second; it leaves it out rather than guess. Two such records exist, the chunk (c) proof runs.
- The project allowlist gains `Bash(python *workflows/review-orchestration/scripts/run.py*)` (the user's A2 decision 2), but Claude Code's auto mode ignores wildcard `python` rules, so in auto mode a run command still goes to the classifier, and its changing arguments rule out an exact rule. A run also needs network access for both providers.
- A test file the builder writes inside its edit paths can be run through the listed test-runner pattern. Since S7 it runs only through the check helper, in the offline container over a clean copy with no personal file, never on the host; the approver confines tool calls, not what a script does once running, and the container bounds it.
- The approver does not expand Windows 8.3 short names for a file that does not exist yet; the brief checker has the same limit.
- The Codex reviewer calls `openai_codex._run._collect_turn_result`, a private function of the pinned SDK, so that a completed turn is built exactly as the SDK builds it. An SDK upgrade can move or change it; the provider tests call it too, so they fail rather than pass silently if it goes.
- The effort lists are copied from the pinned SDKs (`EffortLevel`, `ReasoningEffort`). An SDK upgrade that changes them needs `settings.EFFORTS` changed too.
- A Claude model reported under a different spelling from the one requested (a suffix, say) would be refused as a substitution. The live proof run shows which spelling the SDK reports.
- The price alarm has no Codex builder history until the first run after A3 chunk 1 with a Codex builder: since then it compares `uncached_tokens` alone, and every earlier Codex builder step lacks it, so each is left out rather than corrected (plan 10.10 item 6). Earlier Claude and Codex reviewer steps have it computed from their recorded usage where that holds the counts.
- Only the run record's JSON files are escaped. `report.md`, the round copies of edit-path files and the diffs are text: a round copy or diff carries a project file's own characters, which the encoding guard checks in the project anyway, and a garbled tool output quoted into the report would still be flagged against the run's own record.
- The Codex read list's `Get-Content` line and the prompt's literal example of it must change together; a test checks the example is accepted by the list.
- The loop's use of Docker is tested against a fake: no test starts, stops or builds with the real Docker Desktop. `container.py` itself ran against the real Docker in S4's live check; the loop's start, image step, checks in the container and stop are live checks of the proof run after S7 (plan section 8, live checks 1, 2 and 7).
- A run started before S6a has no frozen folder with a trusted copy, so the starter cannot resume or stop it; one started before S6b has no image recorded, so its first review round after a resume ends `error`; either is started again from its brief.
- A run whose end cannot write its state (the first `save` in `Run.end` failing) stops Docker and removes what it should, but stays saved as it was before the end, usually `running`. A started run is ended again by the hand-over in the live process, which re-reads the state (R19-3); a resumed run has no such second attempt, so the next resume refuses it as already running and its `state.json` needs correcting by hand. Older than S6b; recorded by the R30 audit.
- The tripwire is a net, not a wall: it sees only Python processes that load it, and only the `compile` and `exec` audit events, so code reached another way (a subprocess running a non-Python program, say) is outside it.
- `check_server.py` is given to both builders since S7, but its tests replace the copy and the container with fakes; the real stdio server is started in tests, one of them with a check that starts a program reading its stdin. Its first real checks for a real builder, in proof run 1 (2026-10-12), never answered the Codex builder: the programs `container.py` started inherited the helper's stdin, its MCP pipe, and held each call until the client closed it. Decision 37 gives every such program an empty stdin; a reply reaching a real builder is the rerun proof run's live check 3, and Claude's is live check 4. Each client's MCP call limit is set to 1,800 seconds, the container's own, so a check that takes minutes is not cut short; the proof run is the first to show a client honouring it.
- `runrecord.py` now imports `brief`, so it is no longer loadable on its own: a caller loading it by file path must have `brief` importable first (the tests load `brief` before it).
- A run started, resumed or stopped from a Codex session must run outside Codex's sandbox. Inside it the Codex usage reading cannot use the login (probed on 2026-10-12: the same reading from a Codex session failed sandboxed with "authentication required to read rate limits" and read normally with escalated permissions), so `preflight` and `resume` refuse through `sandbox_refusal`, naming the sandbox and the way out, before anything is created or changed. Codex gives a sandboxed command and an escalated one the same environment (the same `CODEX_*` names and values), so the sandbox is recognised by that answer in a process carrying `CODEX_THREAD_ID`, not detected beforehand. The `.codex/rules/` entry does take `start.py` out of the sandbox: on 2026-10-04 a start from Codex read usage and three resumes from the same session did not, but in the isolation proof run (2026-10-13) a dry resume, a start and a real resume from the VS Code Codex panel all read usage with no approval prompt, and the resumed fix pass's launch record shows `method: resume` on the build's thread.
