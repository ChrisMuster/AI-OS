# Review Orchestration - Scripts

**Last modified:** 2026-10-12

## Purpose
Holds the review-orchestration entry point, the brief checker, and the engine: the build-and-review loop and every part it calls, for either pairing of the two AIs. `brief.py` reads a run brief, classifies every line the way a CommonMark renderer would (so a heading inside a comment or a fenced block does not count), splits the brief into its seven sections and applies each section's rules, reporting every problem rather than the first. It never runs a command the brief contains. `limits.py` reads each provider's usage and decides whether a run may start its next step; `runrecord.py` creates a run's record folder and keeps its state file; `settings.py` reads the settings file, the model and effort for each provider in each role, and gives a run its roles from the builder the user names. `approver.py` decides every tool call the builder makes; `stopreasons.py` holds the pause and stop-reason vocabulary, reads the builder's and reviewer's structured replies, and applies the loop-exit rules; `providers.py` runs the builder and reviewer sessions. `loop.py` is the build-and-review loop that drives them: it runs a builder pass, then review rounds and fix passes until a stop reason, with `worktree.py` measuring and recording what the run changed, `checks.py` running the mechanical checks before each review and `packet.py` writing the review packet. Roles are named by what they do, not by provider: the user names the builder for each run (`--builder`), the other provider reviews, and both pairings are built. A Claude builder is held by the approver in the orchestrator's own process. A Codex builder is held by `codex_hook.py`, a program Codex runs before every tool call from a frozen copy outside the project, deciding with `codex_rules.py` and the same approver, with Codex's sandbox beneath it for file writes, an approval handler that accepts only what the hook allowed, and a check of the whole project after every turn. `run.py` is the workflow's entry point. `container.py` runs builder-written code in an offline container over a clean copy, which the checks after every builder turn have used since stage S6b, and `check_server.py` is the check helper that gives a builder that as its one way to run a check, plus a clock; since S7 it is every builder's one MCP server and the shell is no longer theirs. Since S6a a run's own code comes from its starting commit: `start.py` is the one way in, `frozen.py` makes the run's frozen folder with a trusted copy of that commit, a started run is handed to the trusted copy of `run.py`, and `tripwire.py` fails a process if it executes a file from the live tree, the orchestrator's own since S6a and every Python process the run starts since S7. Since S7 every session the run opens starts only trusted programs: no project hook or plugin runs in any of them, a builder's calls go through the frozen folder's trusted copy of the rule hooks, and the Codex reviewer runs no project code.

## Contents

- run.py - `workflows/review-orchestration/scripts/run.py` - The entry point. `--check-brief <brief>` calls the checker and returns its result unchanged (the same stdout, exit code and LOG.md entries as `brief.py --check`). `--run <brief> --builder claude|codex --item <item> --git-dir <dir>` starts a run with the named provider building and the other reviewing (no default: a missing `--builder` is a usage error, and `--builder` with any other mode is refused, since a resumed or stopped run keeps the roles it started with; `--wait` sleeps through a usage limit with a reset time; `--inject-limit <step>` is test-only); `--resume <run-id> [--rounds N]` continues an ended run; `--stop <run-id>` ends a paused one. `--dry-run` logs to stderr for a check and makes only the read-only preflight for a run. Run from the command line under any interpreter other than the project `.venv` one, it first re-runs itself under `.venv` (`reexec_under_venv`, as the close-out verifier does), because the SDKs live there and plain `python` finds the system interpreter in some shells, Codex's PowerShell among them; everything the run starts uses `sys.executable` and so follows. The trusted copy (`trusted_frozen_folder`, by its path) runs `set_up_trusted` before importing anything else: it arms the tripwire, puts the tripwire folder first on `PYTHONPATH` (`with_tripwire`, keeping what was there) and sets `BOOK_DRAGON_FIRE_LOG` to the run's fire log (S7), so every process the run starts inherits both, then takes the project root from `hook.json`, refusing one without `AGENTS.md` [[AGENTS]] or a set `BOOK_DRAGON_ROOT` that disagrees, and exits 3 naming the problem; it refuses `--run` and a run id other than its own folder's. ## Inputs
- A project-relative path to a brief, from the command line.
- The project tree, for resolving the Source section's paths.
- For `limits.py`: an initialised Codex client, and the Claude SDK's rate-limit events and assistant messages, both passed in by the caller.
- For `settings.py`: `workflows/review-orchestration/config/settings.json` [[workflows/review-orchestration/config/CONTEXT]].
- For `approver.py`: the brief's edit paths, passed in by the caller, and `workflows/review-orchestration/config/verify-commands.txt` [[workflows/review-orchestration/config/CONTEXT]].
- For `stopreasons.py`: the reviewer's parsed reply and the builder's reply text, passed in by the caller.
- For `providers.py`: the loaded settings, an `Approver`, and each provider's subscription login; the SDK entry points can be replaced by factories, which is how the tests run without a model call. - For `codex_rules.py` and `codex_hook.py`: `workflows/review-orchestration/config/codex-read-commands.txt` and `codex-verify-commands.txt` [[workflows/review-orchestration/config/CONTEXT]], read by the hook from the run's frozen folder, never from the project, and the folder's `hook.json` (the run id, the brief's edit paths and the project root).
- For `loop.py` (a run): a brief that passes the check, an `--item` name whose review packet does not exist yet, and `--git-dir`, the personal repository, captured before the run (plan 10.4 step 2). The prompts in `workflows/review-orchestration/prompts/` [[workflows/review-orchestration/prompts/CONTEXT]]. Both SDKs and both subscription logins.

## Outputs
- `PASS: <path>` or one `FAIL: <heading>: <reason>` line per problem on stdout. `Brief` lines (the file itself) come first, then `Headings` lines, then section lines in document order. Exit code 0 on PASS, 1 on any FAIL, 2 on a usage error.
- `started`, then `completed` (PASS) or `failed` (refused, or an unexpected error), appended to `workflows/review-orchestration/LOG.md`, with a generic note that never includes the brief's path. `--dry-run` prints each entry to stderr as a `[DRY RUN]` line instead, so stdout still carries only the PASS or FAIL lines.
- `runrecord.py` writes `workflows/review-orchestration/runs/<run-id>/state.json` (and a `state.json.tmp` beside it for the moment of each write). `limits.py`, `settings.py`, `approver.py`, `stopreasons.py` and `providers.py` write nothing: the approver's refusals, the sessions' transcripts and the stop decisions are returned to the caller, which writes them into the run record.
- A run (`loop.py`) writes, inside `runs/<run-id>/`: `brief.md`, `settings.json` (the resolved settings and SDK versions), `state.json` (since S6b with `image`, the tag and whether it was built, `docker`, whether the run started Docker and each start and stop, and `cleanup`, what its end removed), `image/constraints.txt` (the constraints the image was built from), `start/` (both start commits and the starting diff), `rounds/R<n>/` (`files.zip`, every file under the edit paths as the reviewer received it, and `diff.patch`, the diff it was shown), `transcripts/`, `partial/` (the diff left by a step that did not complete), `report.md` and `report.json`, with a Codex builder `hook-decisions.jsonl`, the hook's decision for every tool call, copied in after every turn, and since S7 `fire-log.jsonl`, the trusted rule hooks' fire log, copied in at every end with each line escaped to ASCII; `state.json` records the run's `frozen_dir`, and since S7 a Codex reviewer's launch readings under `live.codex_reviewer_launches`. Outside the project, for every run (since S6a): the frozen folder `<temp>/book-dragon-orchestration/<run-id>/` (`frozen.py`), holding `trusted/`, copies of `codex_hook.py`, `codex_rules.py`, `approver.py`, `brief.py`, `check_server.py` and `container.py`, the two Codex command lists and the Claude builder's verification list, `hook.json`, `start-ignored.txt`, `tripwire/sitecustomize.py`, and with a Codex builder the decisions file. The check helper adds `check-calls.jsonl` there. Clean copies go to `<temp>/book-dragon-copies/<run-id>/copy-<n>/`, made by the checks after every builder turn since S6b and by the helper since S7, each removed after its use. The trusted rule hooks write the run's fire log to `<temp>/book-dragon-runlogs/<run-id>/fire-log.jsonl` (S7), outside the project and the frozen folder. A usage reading made before the frozen folder exists uses an empty `book-dragon-usage-*` folder in the system temp folder, removed after it. At a stop reason a resume cannot continue, the run removes its frozen folder, its copies folder and its fire-log folder (plan 7.3). A real start or resume starts Docker Desktop if it is not running, and the run's end stops it again; the image step may build the `bookdragon-checks:<tag>` image. Outside the run record: the review packet `memory/<item>_review_packet.md`, the builder's own edits inside the brief's edit paths, and a `started` entry and a `completed` (or, for `error`, `failed`) entry in the workflow's `LOG.md` for each start or resume and each end. It never stages, commits, pushes or changes branch.

## Steps
Checking a brief:
1. Read the brief: refuse an absolute path, one resolving outside the project, a folder, a missing or unreadable file, or invalid UTF-8.
2. Classify each line (blank, text, fence, heading) with HTML comments removed.
3. Check the H2 headings: the seven required ones, each once, spelled as shown, in order.
4. Check each recognised section against its own rules.
5. Print the result and append LOG.md with a completion or failure entry.

Running a brief (`start.py --run`, which refuses an uncommitted tree and then runs `run.py --run`):
1. Preflight, creating nothing: a builder is named and the pairing has a model for every role, the brief passes, the item name is valid and its packet absent, the edit paths hold no uncommitted work, no `.env`-named file is both untracked and unignored, both SDKs are installed, and the personal repository is captured; then Docker (started if it is not running, a dry run only asking); then Codex usage is under the ceiling and its credit snapshot can be tracked.
2. Run the close-out verifier read-only and refuse unless it is clean (a dry run makes it too); then the image step, its constraints file in a temporary folder (a dry run stops here, saying whether a real start would reuse or build the image, or that this is unknown while Docker is not running); then make the run's frozen folder with the image tag (`frozen.setup`; a failure refuses the start, leaving nothing), create `runs/<run-id>/`, copy the constraints file, the brief and the resolved settings in, record both start commits and the starting diff, and append `started` to LOG.md. A start refused after this run started Docker stops it again. From the command line the run is then handed to the frozen folder's trusted `run.py` (`--advance`), which takes the steps below.
3. Builder pass. An empty diff under the edit paths ends the run `no-change-made`. With a Codex builder, every builder turn (this one and every fix pass) sits between two inventories of the project, and any change outside the edit paths ends the run `error`, except the one run-record file the session copies in during a turn, its hook's decisions file (`worktree.TURN_RECORD_WRITES`); any other change to the run record, such as its saved settings, ends the run too, even under an edit path that covers this workflow, since run records are judged before edit paths.
4. Each review round: run the mechanical checks (the close-out verifier and the acceptance commands in the container over a clean copy, then the four trusted host checks; a Docker or copy failure ends the run `error`), record the round, have a fresh reviewer session review, label the findings and write the packet. No findings ends the run `reviewed-clean`.
5. Each fix pass: resume the builder's session with the open findings and read its action for each.
6. Before every step, read usage and stop `usage-limit` rather than start it; after every step, apply the stop-reason rules and write `state.json`.
7. At the end, write the report and packet; copy the rule-hook fire log into the run record; stop Docker if the run (or its resume) started it; at a stop reason a resume cannot continue, remove the frozen folder, the clean copies and the fire-log folder; write the report again with what happened; and append LOG.md with a completion or failure entry.

## Choices where the specification is silent
The specification leaves these to the builder. Each is covered by a test in `workflows/review-orchestration/tests/` [[workflows/review-orchestration/tests/CONTEXT]]: the brief checker's in `test_brief.py`, the usage readings' and settings' in `test_limits.py`, the run record's in `test_runrecord.py`, the approver's in `test_approver.py`, the stop reasons' in `test_stopreasons.py`, the sessions' in `test_providers.py`, the Codex rules' and hook's in `test_codex_rules.py` and the loop's in `test_loop.py`.

**Reading the file**
- The path is resolved against the project root, not the working directory, so the result does not depend on where the command is run. Backslashes in the argument are accepted as separators; a path that resolves outside the project is refused, and so is a folder.
- A UTF-8 byte-order mark is refused and the rest of the brief is still checked. Invalid UTF-8 is refused and checking stops, since nothing after it can be read reliably.
- CRLF and a lone CR are accepted as line endings.

**Headings**
- Headings follow CommonMark: up to three leading spaces, and `##` must be followed by a space, so `##Goal` is text. The title is compared after trimming, but a closing `##` is kept as part of it, so `## Goal ##` is an unexpected heading.
- An underlined (setext) level-2 heading is refused anywhere: headings must be written with `## `. A dash line under a list item or under indented code is not a heading, as in CommonMark.
- A level-1 heading is allowed before the first section and refused after it.
- Content under an unexpected or repeated heading is not checked, and a missing section gets only its `Headings` line, not an "empty" line as well.
- Each heading that appears after a later one is reported as out of order, naming the latest heading seen so far. Its section is still checked.
- A heading that differs from a required one only in case is reported with the correct spelling.

**Content**
- Deeper headings (`###` and below) are not content: a section holding only them is empty, and they are skipped when reading bullets.
- The `...` and angle-bracket placeholders may be bulleted with `-`, `*` or `+`. The two placeholder words the specification names (the upper-case to-do and to-be-decided markers) are matched with case and as a prefix, so a plural of either is a placeholder and the lower-case word is text. A placeholder line is ignored wherever it appears; it is not refused when the section has other content.
- A fenced block is reported once, at its opening line, and its lines are not content.
- Section reasons carry their line number.

**Bullets**
- Only `- ` starts a bullet; `*` and `+` bullets are refused. Leading indentation is allowed. A line that is not a bullet, including a wrapped continuation line, is refused.
- Open questions: `None` must be written with that case and alone. The question and answer split at the first `| Answer:`; an empty question is refused.
- Edit paths: the path and command split at the first `| Measure:` (case-sensitive). `.git`, `.env` and duplicates are compared the way Windows compares names: without case, ignoring trailing dots and trailing spaces. `docs` and `docs/` are duplicates; a folder and a file beneath it are not. An empty or `.` component and a backslash are refused.
- Source: a name ending `.md` is matched without case. Brackets, quotes and trailing punctuation are stripped from a word outside backticks before it is tested, so `plan.md.` and `(docs/plan.md)` are caught. A backtick-quoted path with a backslash, a leading `/` or `~`, a drive letter or a `..` component is refused; `.` and empty components are ignored. Existence is checked with exact spelling and case, so a brief that passes here passes on a case-sensitive file system too. A trailing `/` requires a folder. An unbalanced backtick is refused, and the text after it is treated as unquoted.

**One command**
- Command substitution is refused even inside single quotes.
- An unquoted operator is reported as the whole run of operator characters, so `2>&1` reports `>&`.
- A wrapper is looked for as the program, `argv[0]`, and nowhere else, so a shell or launcher name later in the arguments, as in `rg bash -c README.md`, is data. A launcher that runs another program (`env`, `sudo`, `doas`, `xargs`, `nohup`, `nice`, `timeout`, `time`, `command`, `exec`, `stdbuf`, `runas`, `start`) is refused outright as the program, with `` `<launcher>` launches another program; name that program directly ``. Reading past it would mean modelling each launcher's options (`timeout 10`, `sudo -u x`), and `env -S` / `--split-string` hide a whole command in one argument; a brief can always name the program itself. Chosen in code review round R2 over Codex's suggested per-launcher parsing, which the round's R1-3 repair had already shown to be a source of both false refusals and bypasses.
- Only a shell's own options count, read up to its script operand (or `--`), so `bash scripts/check.sh -c` passes: that `-c` belongs to the script. Options that take a value (`-o`, `+o`, `-O`, `+O`, `--rcfile`, `--init-file`) skip it, so `bash -o pipefail -c ...` is still caught. `-c` combined with other single-letter flags (`-lc`, `-ec`) and `--command` count; for fish, `-C` and `--init-command` too, which run a string there and mean noclobber elsewhere.
- For `cmd`, any argument beginning `/c` or `/k`. For PowerShell, parameters are matched as PowerShell matches them, by prefix, with `-`, `--` or `/`: any prefix of `-Command`, `-EncodedCommand` or `-CommandWithArgs`, plus the `-ec` and `-cwa` aliases, read up to `-File`, after which the arguments are the script's. Windows PowerShell (`powershell`, not `pwsh`) treats a bare argument as a command string, so a bare argument with no `-File` before it is refused.
- The wrapper check reads the command twice: once with POSIX quoting, and once with quotes honoured but backslashes kept, because POSIX reading turns an unquoted `C:\Git\bin\bash.exe` into a name that is no longer `bash`. Either reading finding a wrapper refuses the command; quoted text is data in both.

**Command line**
- A usage error exits 2 (the argparse default), distinct from a refused brief.
- A refused brief logs `failed`; an unexpected error logs `failed` and is then raised. A LOG.md that cannot be written fails the check: the audit trail is part of it, so a brief that would pass prints `FAIL: Brief: could not append to the workflow LOG.md (<reason>)` instead of PASS and exits 1, and a refused brief gets that line first.

**Usage readings (`limits.py`)**
- A Codex JSON-RPC error, a response that is not a JSON object, and a response that fails validation are each an `unavailable` reading carrying the error text, as the plan says; a validation error is kept whole, flattened to one line, since its first line names only the model and the failing field is on the lines after it. A closed transport (`TransportClosedError`) is not: it is raised, because it is a provider failure rather than an answer about usage.
- A negative Codex result holds for the rest of its run, as the plan says, through `RunUsage`: one object per run, every Codex reading passed through it. After the first `unavailable` reading, a later `reported` one comes back `unavailable`, naming the first failure and keeping its own figures for the report, so the ceiling is not applied. A later `limit-reported` reading is passed through unchanged and still stops the run. A new run starts from a new object.
- Where two windows report the same percentage, the one with the later reset is taken, since waiting for the earlier reset would not free the other window. An unknown reset counts as earlier than a known one.
- When Codex says usage is not allowed and windows are present, their highest reading is still recorded beside the stop, so the report shows the numbers the plan asks for.
- Claude's percentages come from each event's raw `unifiedWindows` map first and its top-level `utilization` only as a fallback: in the event recorded by the B1 probe the top-level field was empty and the real figures were only in the map. Windows accumulate across events, and the latest event's `status` is the current status, so a later `allowed` clears an earlier `rejected`. A `rejected` status stops the run whatever the percentages say; its reset time is the event's own, or the highest window's where the event gives none.
- Paid overage stops the run (the user's rule, now in plan section 10.10 item 3): an event with raw `isUsingOverage` true, or an event for the `overage` window, makes Claude's reading `limit-reported` with the reason `using paid overage`. The `overage` window is never counted as an included window, so it never sets the percentage or the reset time; the reset reported is the fullest included window's, which is when the run can resume. The latest event decides, so overage that has ended no longer stops a run, and overage that is available but unused never did. Overage is checked before a `rejected` status, so an event that is both (overage itself refused) still reports `using paid overage` with the included window's reset, since that is when the run can resume. Where the fullest included window carries no reset of its own, the event's top-level reset is used only if the event names that same window; a different window's reset would not free it, so the reset is reported as unknown instead. A stop with an unknown reset does not resume on its own: the user checks whether the allowance has reset and says when to start again (the user's ruling, 2026-09-26).
- Mid-session, Codex's `usageLimitExceeded` turn error and Claude's `rate_limit` assistant-message error are usage limits. Codex's `rateLimitExceeded` is not: it is short-term request throttling, not the plan allowance, and is left to the caller as an ordinary error.
- `check_ceiling` checks every `limit-reported` reading before any percentage, so a provider that reports its limit reached stops the run even when another provider is above the ceiling too. A reading exactly at the ceiling stops.

**Run record (`runrecord.py`)**
- A run ID is `YYYYMMDD-HHMMSS-xxxx`: the local start time, so IDs sort by start, plus four random hex digits, so two runs started in the same second do not collide. Any other form is refused, which also rules out a path separator or `..` in an ID.
- Creating a run whose folder exists is refused. A run record is never reused or overwritten.
- The first `state.json` holds `status: running`, `step: created`, no pause, and empty `stop_reasons` and `rounds` lists: the fields plan section 10.7 names, present from the start.

**Settings (`settings.py`)**
- A missing `usage_ceiling_percent` takes the default, 80. A present one outside `0 < value <= 100`, or not a number (a JSON `true` included, although Python counts `bool` as `int`), is refused rather than replaced by the default.
- Models are held per provider and per role (`models.<provider>.<role>`), not per role alone, so that either provider can hold either role with no code change. The user's decision of 2026-09-26: roles are named by what they do, and the reverse pairing must stay possible.
- Roles are not a setting (the chunk (d) short plan, 11.1, the user's option A of 2026-10-04): the first proof run showed that swapping them by editing `settings.json` refuses every run, because the tests assert the shipped file and doc-sync sees the config folder change. `assign_roles` takes the builder named on the command line and gives the reviewer role to the other provider. A settings file that still holds `roles` is refused naming `--builder`, rather than ignored, so a stale file cannot quietly decide the pairing. `loop.preflight` also accepts settings that already carry `roles` with no builder named, which is how the tests and a caller holding resolved settings pass them; a run started from the command line always names one.
- The defaults are exactly the pairs plan section 11's table names, which since chunk (d) include a Codex `builder` and a Claude `reviewer`, so either pairing runs on the defaults. A role with no model for its provider is still refused, naming the missing entry, rather than guessed.
- The synthesiser has no entry: section 11 makes it the builder's provider on the builder's model, so it reads the builder entry.
- Only the pairs the assigned roles will use are required: the builder's provider needs `builder` and `planner`; the other provider needs `planner`, `plan_reviewer`, `reviewer` and `intent_checker`. The reviewer is always the provider the user did not name, since one AI builds while the other reviews.
- An entry given in the file overrides that provider's role only; everything else keeps its default. Unknown keys inside `round_caps`, `models` and a model entry are refused, since a misspelt role would otherwise be silently ignored. Unknown top-level keys are still kept, as before.
- Effort is checked against the values each pinned SDK accepts, per provider: `ultra` is valid for Codex and refused for Claude. Round caps are whole numbers of at least 1 (`true` refused).

**Approver (`approver.py`)**
- Refusal is the default: a tool not named below is refused, so a tool added to Claude Code later is never allowed by accident.
- Read tools: Read, Grep, Glob, TodoWrite and ToolSearch (the last so deferred Biblio Tools schemas can be loaded). Read, Grep and Glob are allowed subject to the read rules, which bind both builders and the reviewer through one function (the user's choice of 2026-10-02 to close the gap for the Claude builder in chunk (d)): a call is refused when any string in its input, however nested, names a `.env` file by the test the shell checks use, a Grep's `pattern` apart, since that is the text searched for; and a Grep carrying a `glob` key is refused whatever its value, since an explicit wildcard overrides the ignore rules that keep a `.env` file out of a folder search. A Glob lists names and reads nothing, so it is allowed under the first rule alone. A refused read records its path, pattern and wildcard as the detail.
- An edit is allowed when the file resolves (links followed) inside the project and its path, compared the way `brief.py` compares edit paths, equals an edit path or lies under it. `workflows/x-old/` is not under `workflows/x/`. A path through `..` is judged by where it lands. `.git`, `.env` and `.env.*` are refused even inside an edit path, and so is an alternate data stream (`file:stream`); so are the project `.venv`, the starter and, since S7, `.codex` (decision 33), only at the project root: a `.codex` or `.venv` folder lower down is not the project's.
- No line of `verify-commands.txt` accepts a flag it does not name: a free argument cannot start with `-`. The audit's `--save` and close-out's `--repair` both write outside any edit path (review finding R2-2). The test-runner line takes test names and an optional `-v` only, since a `--help` there exits 0 without running a test (R3-1). A test checks the rule on every line for bare and valued flags at every position (R4-1); it checks those shapes, not every possible input.
- A check command (since S7 the check helper's `run_check`, never the shell) is allowed only when the whole trimmed command matches one line of the builder's verification list, which is one regular expression per line (the user's choice, 2026-09-26, over literal prefixes: it is the B2 form that has run). On top of any match, a command with a `..` path component, one naming a `.env` file, one spanning lines, or one whose quoting `shlex` cannot read is refused, and so is a `run_check` call carrying any argument but `command`. The `..` refusal exists because a listed test-runner pattern would otherwise run a script anywhere, by stepping back out of a `tests` folder with parent components. The test is `verify_refusal`, the helper's own, so nothing the approver allows is refused by the helper and nothing is allowed that it would not run.
- Since S7 (plan 7.4, 7.6) a builder has no shell and no Biblio Tools tool, all refused outright with a message naming the check helper: the Biblio Tools tools run the working tree's scripts on the host. Its clock is the helper's `get_timestamp`, allowed only with no arguments.
- Every refusal message starts `Refused by the orchestrator:` and says what is allowed, so the builder can act on it; every refusal is recorded with the tool, a detail cut to 300 characters, and the reason.

**Stop reasons and replies (`stopreasons.py`)**
- The builder's action list is the last fenced `json` block in its reply, parsed strictly (the user's choice, 2026-09-26): every open finding exactly once, only `label`, `action` and `note`, and nothing that is not open. A block written earlier in the reply as a draft does not count.
- The reviewer's field is named `reraises`, as the plan says; B2 called it `repeats`. An empty string means new, since a strict structured-output schema requires every field. A `reraises` naming a label the run has not issued is a malformed reply.
- A label in a finding title is refused twice (the user's choice, 2026-09-26): the schema's `title` carries a pattern refusing it, for the provider to enforce if it accepts the pattern, and `parse_review` checks every title whatever the provider did. The script's check also catches `R3 - 1` and a dash-joined label; `R2-D2` and `PR12-3` are not labels.
- Labels are issued by the script, `R<round>-<n>`, the script's own mechanical findings first, then the reviewer's, as B2 did. A mechanical finding never carries `reraises`.
- Rule 3 is built to the plan, not to B2: B2 counted a finding repeated in two rounds whatever the builder had done with it; here each reraise counts only when the finding it raises again was marked `fixed`, and only when the chain's first finding is raised again in two consecutive rounds.
- The rules run in the plan's order over everything recorded so far, so `out-of-scope` wins over `disagreement` when one pass produces both.
- No findings at the round cap is not `max-rounds`, and the rules never return `clean`: a clean end also needs the final intent check (plan section 10.6), which arrives with that sub-stage.
- `record_stop` refuses to stop a run that has already ended; `continue_run` resumes an ended run only for `max-rounds`, `usage-limit` and `error`, and the earlier stop reason stays in `stop_reasons`.

**Providers (`providers.py`)**
- Sessions are registered by provider in `BUILDERS` and `REVIEWERS`, and both providers have a session for each role. A provider with none raises `ProviderError` naming it, never runs another instead. Each session class names what it takes of what the loop offers (`wants`): a Claude builder the session to resume and the run's usage object, a Codex builder the session to resume and the run folder, a Claude reviewer the usage object.
- The orchestrated-session marker is added by the provider, as the first line of the builder's first prompt and of every review prompt, so no caller can forget it; a prompt already carrying it is not given a second. A resumed builder session sends no marker, since a resumed turn does not rerun startup (B1).
- The approver sees every builder call through a `PreToolUse` hook, not only through `can_use_tool`. The installed SDK calls `can_use_tool` only for a call its permission rules would ask about, never for one a `permissions.allow` rule in the project's `.claude/settings.json` already permits, and that allowlist includes writing scripts and every Biblio Tools tool (review finding R1-1). The hook denies a refused call with the approver's reason and gives an allowed call no decision, rather than `allow`, so the project's own hooks and rules still run after it. `can_use_tool` stays as a second layer.
- A Claude turn whose result is marked `is_error` (a provider failure, or the turn cap) raises `ProviderError`, never returns as a completed pass (review finding R1-2).
- A Claude session that reports starting on a different model from the one requested raises `ProviderError`. A Codex model missing from `models()` raises before any thread starts.
- The Codex reviewer starts its turn with `thread.turn(...)` and reads the turn's events itself rather than calling `thread.run()`: on a failed turn the SDK's collector raises a plain `RuntimeError` carrying only the message, which loses the code saying a usage limit was hit (review finding R2-1). A turn-completed event marked failed is judged from its own error; a completed turn goes through the SDK's collector unchanged.
- A Claude assistant message with the `rate_limit` error and a Codex turn error `usageLimitExceeded` are raised as `limits.UsageLimitError`; every other failure is a `ProviderError`. The builder keeps its transcript so far in `last_messages`, so a turn cut off still leaves its partial record.
- Transcripts are returned as JSON-safe copies of the SDK objects; writing them into `runs/<run-id>/transcripts/` is the loop's job.

**The Codex builder (`providers.py`, `codex_rules.py`, `codex_hook.py`)**
- What the short plan specifies is built as written: the frozen folder, the hook command and its refusal of a path that would need quoting, the self-test, the two launches, the checks before any work, the thread's settings read back, the table of hook-run statuses, the approval handler by call id, and the item check. The choices below are where it is silent.
- The frozen folder's `hook.json` holds the run id as well as the edit paths and the project root (and since S6a the builder provider and public head), and the hook refuses when its argument is not that folder's name, so a hook started for one run cannot judge another's calls.
- Each decision line carries the call's `session_id`, which is what lets the hook refuse a call from a session other than the one an earlier line recorded. A line written for input that was not a JSON object carries none, so it cannot become the session every later call must match.
- A call with both an `allow` and a `deny` line is denied.
- The self-test sends a shell command that is on no list. On a first launch it uses a placeholder session id; on a resume it uses the thread's id, so the command reaches the rules and is not refused for its session alone. Its line is removed afterwards either way, and no other line is touched.
- The thread id is published as the session's `session_id` only once a turn has started, because a thread with no turn cannot be resumed. Since S6a the frozen folder is the run's, made by the orchestrator before any session (`frozen.py`): a launch, first or resumed, only checks it holds every frozen module, list and `hook.json`, naming what is missing, and neither a failed launch nor a close ever removes it, so the next launch checks the same folder.
- A `preToolUse` hook run from any source other than the run's own (the project's, or a user-level or plug-in hook) ends the turn whatever its status, since S7 (plan 7.6 item 3): the project's hooks are switched off for a builder, so a run of one means code the run does not hold ran. Before S7 a `completed` or `blocked` project run was accepted as the project's guardrails working; the run's trusted copy of those guardrails now runs inside the run's own hook instead. Runs of other events (session start, stop) are not judged.
- A notification the SDK could not parse (a hook status it does not list) is read from what the server sent, so an unparsed hook run is still judged.
- An item "ran" unless its status is `declined`. The item kinds taken as tool calls are `commandExecution`, `fileChange`, `webSearch`, `mcpToolCall`, `dynamicToolCall`, `collabAgentToolCall`, `imageGeneration` and `imageView`; any kind that is neither one of those nor a message ends the turn, as the plan says.
- The item check is made on a turn that completed. A turn that failed or was ended raises its own error, and the decisions file is still copied into the run record and its refusals kept.
- A turn's tokens are the thread's total from its last token-usage notification; the loop turns that into the step's share (below). A Codex turn has no cost figure.
- Every successful launch keeps a `launch_record` (the chunk (d) short plan, 11.2): the run hook's `trustStatus`, `enabled`, `timeoutSec` and `matcher` (which must read `.*`, every tool, or the launch is refused: R4-1), each project hook's event, matcher, trust and enabled state (since S7 each must read `enabled: false`), since S7 every MCP server Codex lists with its plugin, tool names and discovery error (live check 4a), `self_test: passed`, the effective `web_search`, and the thread's `start` or `resume` with its id, sandbox and approval policy as Codex replied. A launch whose checks fail raises and keeps none, so a record is evidence that every check of that launch passed.
- `codex_rules.decide` adds the accepted `Get-Content` form to a refusal of any `Get-Content`, or of a command setting `[Console]::OutputEncoding`, that does not match the read list, so the builder is told the one form rather than retrying blind; a command in that form refused for another reason (a `.env` file) is not given it.
- The session uses one private method of the pinned SDK, `CodexClient._request_raw`, for `hooks/list`, `config/read`, `thread/start` and `thread/resume`: the typed methods do not take the raw parameters or return the raw reply the read-back compares.

Within one process the session stays open from the build through every fix pass, so a resume, and with it a `thread/resume` reply, happens only after a stop; the second proof run forces one with `--inject-limit fix-R1` (finding R8-1).
- Every JSON and JSON Lines file of a run record is written with non-ASCII characters escaped (`state.json`, `settings.json`, the transcripts, `report.json`, `start/heads.json`, and the hook's decisions file, which is copied in), so a garbled tool output kept verbatim cannot fail the encoding guard, and reads back as the same values (the chunk (d) short plan, 11.4). The first proof run's record was re-saved the same way, each file checked to read back unchanged.
- The builder prompt's tool rules are a file per provider in `prompts/`. The "no git commands" rule moved into them, since a Codex builder's read list has three read-only git forms. A Claude builder's fix prompt is as it was; a Codex builder's repeats its tool rules. The lists a Codex builder's prompt prints are read from the run's frozen folder where it exists, since those copies are the ones that judge it.
- The check after every turn records its time and what it found in `state.json` as `turn_checks`, and the report lists it. The frozen folder is compared as a SHA-256 per file with the hook's decisions file and the check helper's calls file left out, since those two are written during a turn. Bytecode caches count like any other file (code review R20-1): every program run from the folder (the trusted `run.py`, `codex_hook.py`, `check_server.py`) turns bytecode writing off as its first statement, and the hand-over and the starter's resume and stop also set `PYTHONDONTWRITEBYTECODE=1`, so a cache appearing there is a change.

## Known Issues
- The one-command rule refuses the listed shell wrappers only. An interpreter given code as a string (`python -c`, `node -e`) passes, because it is one command with quoted arguments. The checker never runs anything; whether an acceptance check does what it claims is the intent check's job in a later sub-stage.
- The launcher list is fixed. A shell wrapper behind a launcher not on it (for example `parallel sh -c ...`) is read as that launcher's data and passes; adding a launcher is a one-line change, which the every-launcher test then covers.
- A valid command that happens to go through a launcher, such as `env rg bash -c README.md`, is refused. That is deliberate: the refusal names the launcher, and dropping it gives an equivalent command that passes.
- The line classifier models the CommonMark cases a brief uses (ATX and setext headings, fences, HTML comments, list items, quotes, indented code). It is not a full CommonMark parser: an HTML block other than a comment, or a lazy continuation line inside a quote, is read as plain text.
- The Windows name folding for `.git`, `.env` and duplicates covers case, trailing dots and trailing spaces. It does not cover short 8.3 names or alternate data streams.
- Claude reports no usage until a session emits a rate-limit event, so at a run's preflight Claude's reading is always `unavailable` and the ceiling cannot be applied to Claude before its first Claude step. The reading lives in the run's one usage object, which starts empty in each process, so it is `unavailable` again after a resume until a Claude session reports.
- A Codex builder turn holding an item that is neither a message nor a tool call ends the run `error`, as the short plan specifies. `plan` and `contextCompaction` are such kinds: a long turn in which Codex compacts its own context would be stopped. Neither appeared in the probe turns; the proof run is the first long turn.
- A Codex builder is kept off the network by its hook, not by its sandbox, which does not block the network on the build machine. A hook that fails lets a call run: a shell command or a patch is still refused by the approval handler, and web search is switched off, but another tool needing no approval could run once before the session ends the turn.
