# Review Orchestration

**Last modified:** 2026-11-10

## Purpose
Replaces the manual relay between two AIs with a run the user starts from Book Dragon: both AIs plan a task independently from one brief, the plans are merged, then one AI builds while the other reviews, in rounds that repeat automatically until a stop reason is reached. The orchestrator is a script that hands out every task and moves results between the AIs; the user assigns every role and keeps every git decision.

The workflow is built in six sub-stages that each ship with tests and a close-out pass. **The first is built: the run brief and its checker.** A run starts from a brief, a markdown file with seven required sections (Goal, Constraints, Out of scope, Acceptance checks, Edit paths, Open questions, Source) written with the user before the run, and nothing starts without one that passes the check.

**The second, the engine, is built in four chunks.** The first built the run record folder and its state file, the usage-limit readings for both providers with the ceiling that stops a run before it spends allowance needed for interactive work, the settings file that holds that ceiling, and the optional requirements file for the two AI SDKs. The second built the approver that confines the builder to the brief's edit paths and a list of verification commands, the stop-reason rules and the structured replies they read, and the builder and reviewer sessions. The third built the live build-and-review loop: `run.py --run` takes a checked brief, has one AI build, then repeats review rounds and fix passes until a stop reason, checking usage and the Codex credit balance before every step, stopping cleanly and resuming, and writing the review packet and a report. A run with nothing left to fix ended `reviewed-clean` rather than `clean` until the intent check was built (see below). The fourth built the reverse pairing. Roles are named by what they do, and the user names the builder for each run (`--builder claude` or `--builder codex`); the other AI reviews, and there is no default. A Codex session in the project can start, resume and stop a run through a rules entry in `.codex/rules/`. A Codex builder is held by a program Codex runs before every tool call, with its sandbox beneath that for file writes and a check of the whole project after every turn; a Claude reviewer can only read and search. **The third, the front half, is built in three chunks.** The first built approval and amendment. The second built the planning sessions: two planners, one per provider, planning in parallel from the same brief, a pause for any question the brief does not answer, a check that refuses a plan naming the AI that wrote it, and a synthesiser merging the two plans, unlabelled, into one, with a plan report in the run record. The third built the plan review, where the AI that will not build reviews the merged plan and the synthesiser revises it in rounds, and joined the front half to the start: a run now plans, reviews its plan and pauses for the user's approval before it builds, with Docker and the check image waiting for that approval, finding labels running on from the plan review into the build, and the approved plan given to every builder turn and reviewer. The same chunk made each step stop only on its own provider's usage readings, let a resume with `--wait` wait at its preflight, and made every resume and approval claim the run with a lock file. **The fourth, the intent check, is built.** It runs twice, each time a script check and then one fresh read-only session on the AI that did not build: on the merged plan before the approval pause, where its result goes into the plan report and never stops the run, and on the final change once a review round finds nothing, where it decides the end: `clean` when both layers pass, `intent-failed` when the script finds a changed file outside the edit paths or inside a backticked Out of scope path, or an acceptance check that did not exit 0, or the session finds a Goal or Constraint line not met, an item not delivered or a change not asked for. `reviewed-clean` is retired for runs started from then on. Its proof runs of 2026-11-02 ended as expected: `clean` with Claude building, and `intent-failed` on a planted change with Codex building. **The fifth, the measurement harness (A5), is built** and has not yet run a measurement: `scripts/measure.py`, started by the starter's `--measure` forms (added by hand on 2026-11-10), measures the one review step real runs use, for each of the two default reviewers, on two replayed past review rounds and seven planted changes (six with one defect each and a clean control), with judge sessions on the other AI proposing what was caught and the user ruling on each proposal before a final report is written. Its fixtures are in `measurement/`; their patches were validated against the fixed public ref by hand on 2026-11-10 (see Known Issues). The plain-language triggers come in the last sub-stage and do not exist yet.

## Inputs
- A run brief: a markdown file at a project-relative path, normally `workflows/review-orchestration/runs/<run-id>/brief.md` once runs start, copied from `prompts/brief.md` and filled in with the user.
- For the Source section: the files and folders the brief names, which must exist in the project.
- Which AI builds, named by the user for each run (`--builder`).
- `config/settings.json`, for the usage ceiling, Claude turn limits, probe model, round caps and models, and `config/verify-commands.txt`, for the commands a Claude builder may run, or the two Codex lists for a Codex builder.
- The two AI SDKs, installed into the project `.venv` from `requirements.txt`, and each provider's existing subscription login. The engine's live parts need them; the brief checker does not.
- For a run: an item name for its review packet (`memory/<item>_review_packet.md`, which must not exist yet), and the personal repository's folder, captured before the run starts.

## Outputs
- The brief check result on stdout: `PASS: <path>`, or one `FAIL: <heading>: <reason>` line per problem, with exit code 0 or 1.
- `started` and `completed` or `failed` entries in this directory's `LOG.md` for every command-line check, with a note that never includes the brief's path. `--dry-run` prints them to stderr instead.
- From a run: a run record, which is all a run writes before its plan is approved (its plan report, its plan-review findings and their rendered packet included); then, from approval on, the builder's edits inside the brief's edit paths, the review packet `memory/<item>_review_packet.md` (first written at approval, holding both halves' findings), and `started` and `completed` or `failed` entries in this directory's `LOG.md`. Nothing is staged or committed.
- The run records: one folder per run, `runs/<run-id>/`, created by `runrecord.py` with its `state.json`, which is rewritten atomically after every completed step, and filled by the loop with the brief, the resolved settings, the intent check's start snapshot (since A4), the start and round records, transcripts and the report. `runs/` is gitignored and classified for the personal repository, so it is local only and a capture after a run picks it up, except each run's `start-snapshot.json`, which no capture takes and which is removed once the run can no longer continue (`--stop` abandons a run that ended resumably). It is described here rather than under Contents because it does not exist until the first run, and the audit checks every Contents path against the disk.
- From a measurement (A5): `runs/measure-<id>/`, beside the run records and covered by the same gitignore and capture, holding `progress.json` (every session's attempts and result, rewritten atomically after each), the sessions' transcripts, the planted copies' round records, `proposals.json`, the rulings file `rulings.md` the user edits, and after scoring `report.md`; outside the project, its frozen folder (as a run's) and throwaway restored copies and judge folders in the system temp folder, each removed after its session; and `started` and `completed` or `failed` entries in this directory's `LOG.md` at each start, resume, pause, stop and finish. Nothing is staged or committed, and nothing is written in the live project's repositories.

## Steps
1. Copy `prompts/brief.md` to the run's brief path and fill in every section with the user.
2. Run `python workflows/review-orchestration/scripts/start.py --check-brief <brief>` (the starter first checks the two folders the checker loads are committed).
3. Fix every FAIL line and rerun until it prints PASS. An acceptance check must be on both builders' verification lists (`config/verify-commands.txt` and `config/codex-verify-commands.txt`), so whichever AI builds can run it.
4. Commit everything (the starter refuses a start while anything tracked or unignored is uncommitted, anywhere in the project), make sure the close-out verifier passes, and make sure no `.env`-named file is both untracked and unignored (a run refuses to start without all three; `start.py --run ... --dry-run` checks all of them, the verifier included, and starts nothing), then capture the personal repository with the gated chain (`workflows/sync-architecture/` [[workflows/sync-architecture/CONTEXT]]), so everything the run starts from is committed somewhere.
5. Start the run through the starter: `python workflows/review-orchestration/scripts/start.py --run <brief> --builder claude|codex --item <item> --git-dir <personal repository>`, with the builder the user named (`run.py` run directly, for any mode, prints the starter command instead and loads nothing of the project); the other AI reviews. An AI asked to start a run with no builder named asks the user which AI builds and never picks one itself. The run plans first (both planners, the synthesis and the plan review), asking only Docker's status, and pauses `awaiting-plan-approval` with `runs/<run-id>/plan-report.md` written, or `awaiting-user` with `questions.md` when a planner asks something the brief does not answer. From a Codex session, a start, resume, stop, approval or amendment must run outside Codex's sandbox. Do not edit the brief's edit paths while it runs; with Codex building, change nothing tracked or hand-written anywhere in the project while a builder turn is running, since the check after the turn would end the run.
6. At the plan-approval pause, read `plan-report.md`, its intent section included (what the first intent check found, and any backticked Out of scope item it could not check because no such path exists), and decide: `start.py --approve <run-id>` continues the same run into its build, after checking the project has not moved during the pause (refusing, changing nothing, if it has), then starting Docker and preparing the check image; `start.py --amend <run-id> <revised-brief>` replaces the brief and plans again from the start; `start.py --stop <run-id>` ends it. At an `awaiting-user` pause, answer the questions in the run's `brief.md` and resume.
7. Read `runs/<run-id>/report.md` and do what it recommends for the stop reason (since A4 a run with nothing left to fix ends `clean` or `intent-failed`, the report's intent section naming every cause and every `cannot tell`); `python workflows/review-orchestration/scripts/start.py --resume <run-id>` continues a run that stopped on `max-rounds` (with `--rounds N` for more rounds, in either half), `usage-limit` (`--wait` sleeps to a known reset first; `--allow-paid` permits one step on paid usage) or `error`. Each mode takes `--dry-run`. All of them run the run's trusted copy, never the live `run.py`, and a resume, approval or real stop that finds `runs/<run-id>/resume.lock` refuses, naming it.
8. Append LOG.md with a completion or failure entry (the script does this itself from approval on).

Measuring the review step (A5, plan 10.8), only at the user's direction:
1. Check every fixture in `measurement/` for whether each change is believable, gives nothing away and is defined tightly enough (a fixture changed since its validation needs its `base_blob` validated again, `measurement/CONTEXT.md`); commit; make sure the check image `bookdragon-checks:211a000e7364` exists.
2. `python workflows/review-orchestration/scripts/start.py --measure` runs the first reviewer's 12 sessions and pauses; read `runs/measure-<id>/rulings.md` and the transcripts.
3. `start.py --measure --resume <id>` runs the second reviewer's set (and continues after any usage stop, only from the commit the measurement started at).
4. Rule on every line of `rulings.md`, then `start.py --measure --score <id>` writes `report.md`; it can be rerun after a ruling changes.

## Dependencies
- Python 3.13+ standard library for the brief checker, the run record and the settings reader.
- `claude-agent-sdk` and `openai-codex`, pinned in `requirements.txt`, for the usage readings and every later part of the engine. `limits.py` imports them only inside the functions that need them.
- Docker Desktop with the Linux engine, for every run since stage S6b: the check image is built from `python:3.13-slim`, its packages installed offline from a wheel store the host fills from PyPI's release records (only a build needs the network: every pinned release's record each time, and the files the store lacks; decision 41), and the checks after every builder turn run in it. A run's approval (since A3 chunk 3; its start only asks Docker's status) starts Docker Desktop when it is not already running, and the run's end stops it again.
- `AGENTS.md` [[AGENTS]] - the Workflow scripts convention (`run.py` entry point), the Script safety rule (`--dry-run`), and the encoding rules the scripts follow.
- `workflows/close-out/` [[workflows/close-out/CONTEXT]] - discovers and runs the test suites as part of the close-out verifier.
- `.codex/rules/` [[.codex/rules/CONTEXT]] - the Codex rules entry that lets an interactive Codex session run `start.py --run`, `--resume`, `--stop`, `--approve` and `--amend` outside its sandbox. The `--approve` and `--amend` entries were added by the user by hand after A3 chunk 1's run, since no run may change `.codex/` (decision 33). Changing the starter's path or modes means changing it too. The project's `.claude/settings.json` allowlist has the matching `start.py` rule. Since A5 it holds one more entry, a prefix rule on `start.py --measure`, added by hand on 2026-11-10 with the starter's three `--measure` forms; the Claude allowlist's `start.py` rule already covers them.
- `workflows/sync-architecture/` [[workflows/sync-architecture/CONTEXT]] - `runs/` is classified in Category A of the executable `allowlist` block of the gitignored `SYNC-ARCHITECTURE-PLAN.md`, and checked with that workflow's `boundary.py` and `run.py --check`. Moving or renaming `runs/` means changing that line, the `.gitignore` rule, and its row in `workflows/doc-sync-guard/config/output-inventory.yaml` [[workflows/doc-sync-guard/config/CONTEXT]] together.

## Known Issues
- Since A3 chunk 3 a run builds from a plan the two AIs made and the user approved, but the planning, plan-review and synthesis sessions have run only against fakes: their first live run, with the live lockdown check for each new Claude session role, is the proof run that follows chunk 3. The intent check (A4) was proved live on 2026-11-02, except a missed goal, which cannot be planted live and rests on the fake tests; a run started before A4 keeps its frozen copy and can still end `reviewed-clean`, when the user reads the diff against the brief.
- The reverse pairing (Codex builds, Claude reviews) made its first live run on 2026-10-03, which found five defects, fixed on 2026-10-04 and tested with no model call; a second proof run that day ended `reviewed-clean`, and the isolation proof run of 2026-10-12 and 2026-10-13 ran both pairings again.
- A Codex builder is kept off the network by its hook, not by its sandbox: on the build machine a third-party firewall leaves Codex's own network block inactive. The detail and the remaining limits are in `scripts/CONTEXT.md`.
- The README entry is marked `[in progress]` and this file describes a partial workflow. Both are brought to their finished shape by the integration sub-stage, which also adds the trigger phrases.
- The checker proves a brief is complete and well-formed, and that either builder can run its acceptance checks. It cannot prove the brief is right: whether the goal, the edit paths and the acceptance checks describe the work the user wants is the user's call. The intent check (A4) judges the plan and the change against the brief as written, not the brief itself.
- A run started before the orchestrator isolation stage S6a has no frozen folder with a trusted copy, so the starter cannot resume or stop it; such a run is started again from its brief.
- The isolation work is built (stages S1 to S7) and proved live: a run's own code comes from the starting commit (S6a), builder-written code runs only in an offline container over a clean copy, with the host checks from trusted copies (S6b), and every session starts only trusted programs, a builder running its checks only through the check helper and the Codex reviewer running no project code (S7). Its proof run (2026-10-12 and 2026-10-13, both pairings) held every live check after four defects it found were fixed: Codex's approval question for check-helper calls (decision 36), the helper's child programs inheriting its MCP pipe (decision 37), two tests' Windows-only sample paths (decision 38), and a Claude builder's callback decisions not reaching the run record (decision 39). A run needs Docker Desktop for its build: since A3 chunk 3 a start, which plans first, and a resume in the planning half only ask Docker's status, while an approval or a resume of the build starts it if it is not running and prepares the check image (approval only), and the run's end stops it again. The details are in `scripts/CONTEXT.md`.
- A run starts only from a fully committed tree (decision 17): work in progress outside the brief must be committed or set aside first. Gitignored files are unaffected.
- Isolation covers code a builder wrote, not its reads: whatever a builder reads with its file tools goes to its AI provider, and personal files a brief names as sources are readable by design.
- Windows-only assertions and the live-data sync-architecture tests do not run inside the Linux container; a builder's change to that logic is caught at the user's close-out on Windows, not in the review loop.
- An untracked, unignored file a builder creates during a run goes into the clean copy. None can exist at the start (the starter refuses them), the preflight refuses an unignored `.env`, and anything personal must be gitignored.
- The guarantee covers the run, from its start to its end. After a run, the user's own close-out and tests on Windows run the builder's uncommitted changes on the host, a deliberate human step taken after reading the report and the diff.
- Docker Desktop waiting on an interactive update cannot be started, and the run is refused with the reason.
- The Codex reviewer is told to run no project code, and the tripwire stops a Python process its shell starts from executing a live-tree file (decision 34); code that is not Python is guarded only by the instruction.
- No run may change `.codex/` (decision 33): a brief naming it is refused, and so is an edit or patch under it. A change to Codex's configuration or rules is made by hand, outside a run.
- Inside Codex's sandbox the Codex usage reading cannot use the login, so a start or resume made there is refused, saying so, before anything changes. Codex gives sandboxed and escalated commands the same environment, so the refusal is recognised from Codex's answer rather than detected beforehand. The `.codex/rules/` entry does take `start.py` out of the sandbox: in the isolation proof run (2026-10-13) a run was started and resumed from an interactive Codex session, with no approval prompt and the usage reading working; the details are in `scripts/CONTEXT.md`.
- The SDKs are pinned exactly and change their interfaces between releases, so upgrading either means rerunning the test suites and the live usage read before the new pin is trusted.
- The measurement harness (A5) is built and tested with fakes only; no measurement has run. Its starter forms and `.codex/rules/` entry were added by hand after its build run, and its planted patches were validated against the fixed refs by hand (`measurement/CONTEXT.md`), since the build run had no git; neither has yet been exercised by a live measurement.
