# Review Orchestration - Prompts

**Last modified:** 2026-11-11

## Purpose
Holds the text the review-orchestration workflow gives to people and to the AIs it runs: the run brief template, the prompts for the planners, the synthesiser and the plan reviewer of the planning half, with the synthesiser's revision, the builder's first pass, its fix passes and the reviewer, the intent checker's two prompts (A4), the measurement's judge prompt (A5), and the parts of those prompts that differ by which AI holds the role.

## Contents
- brief.md - `workflows/review-orchestration/prompts/brief.md` [[workflows/review-orchestration/prompts/brief]] - The run brief template: a usage comment (since 2026-11-11 also asking for the work to be sized so its build fits one five-hour usage window where it allows, split into chunks otherwise, the plan report's size estimate being the check, plan 10.2), then the seven required headings in order, each followed only by an HTML comment saying what goes there. The Acceptance checks comment says each check must be on both builders' verification lists, and since A4 the Out of scope comment says what plan 10.2 says: a path written in backticks there is checked by the script at both intent checks if it names a file or folder that exists when the run starts, one that names nothing being listed in the plan report as not checked, and the rest of the section is read by the intent checker only. The checker refuses it as shipped, six sections empty, which is the proof that an unfilled brief cannot start a run; `tests/test_brief.py` asserts exactly that refusal.
- builder.md - `workflows/review-orchestration/prompts/builder.md` [[workflows/review-orchestration/prompts/builder]] - The builder's first-pass prompt: the run's rules (edit paths, maintenance obligations with every LOG.md entry written `Actor: Biblio` whichever AI builds, the builder's tool rules), the brief and, since A3 chunk 3, the approved merged plan in a section of its own after the brief. Fields `$edit_paths`, `$tool_rules`, `$brief`, `$plan`.
- builder-tools-claude.md - `workflows/review-orchestration/prompts/builder-tools-claude.md` [[workflows/review-orchestration/prompts/builder-tools-claude]] - A Claude builder's tool rules (since S7): run checks only with the check helper's `run_check`, in an offline container over a clean copy, the shell not available; its verification commands; a LOG.md entry written with the edit tools, its time from the helper's `get_timestamp`; a Grep call carrying the `glob` option refused, with `path` or `type` to use instead; no git commands and no Biblio Tools tools. Field `$verify_commands`.
- builder-tools-codex.md - `workflows/review-orchestration/prompts/builder-tools-codex.md` [[workflows/review-orchestration/prompts/builder-tools-codex]] - A Codex builder's tool rules: read with the listed shell commands, and with `Get-Content` only in the one form that sets both encodings, shown literally with the reason, change files only with apply_patch, write a LOG.md entry with apply_patch and take its time from the listed command, run checks only through the check helper's `run_check` (since S7, in the container, never the shell) from its own verification list, and use no MCP tool but the helper's two and no other tool. Fields `$read_commands`, `$verify_commands`.

Fields `$round`, `$findings`, `$tool_rules` (`fix-tools-claude.md` for a Claude builder; a Codex builder's tool rules again), `$brief`, `$plan`.

Fields `$brief`, `$public_head`, `$personal_head`. It names no provider.
- synthesiser.md - `workflows/review-orchestration/prompts/synthesiser.md` [[workflows/review-orchestration/prompts/synthesiser]] - The synthesiser's prompt (plan 10.3 step 3): the brief and the two plans as Plan 1 and Plan 2, who wrote which not given, and the synthesis schema's fields. Fields `$brief`, `$plan_1`, `$plan_2`. It names no provider.
- reviewer-tools-codex.md and reviewer-tools-claude.md - `workflows/review-orchestration/prompts/reviewer-tools-codex.md` [[workflows/review-orchestration/prompts/reviewer-tools-codex]] - The one sentence of the reviewer prompt that differs by provider: a Codex reviewer may read the code but run no project code, the checks having already run in the container (since S7, decision 34; it was invited to run the tests, which ran builder-written code on the host); a Claude reviewer can read and search but run nothing, and a Grep call carrying the `glob` option is refused. Fields `$round`, `$brief`, `$plan`, `$mechanical`, `$prior`, `$changed_files`, `$check_written`, `$diff`, `$reviewer_tools`.

## Inputs
None. The template is copied by hand and filled in with the user; the prompts are filled in by `workflows/review-orchestration/scripts/loop.py` [[workflows/review-orchestration/scripts/CONTEXT]].

## Outputs
None. A filled brief lives with its run, never here, and so does every filled prompt, in the run's transcripts.

## Steps
1. Copy `brief.md` to the run's brief path; do not edit it in place.
2. Fill in every section, then check it with `python workflows/review-orchestration/scripts/start.py --check-brief <path>`, the starter every orchestrator command goes through.
3. Append LOG.md with a completion or failure entry when the template or a prompt is changed.

## Dependencies
- `workflows/review-orchestration/scripts/brief.py` [[workflows/review-orchestration/scripts/CONTEXT]] - the checker whose rules the template's comments describe.
- `workflows/review-orchestration/scripts/loop.py` [[workflows/review-orchestration/scripts/CONTEXT]] - fills the prompts with `string.Template`, so a field is written `$name` and a literal dollar sign `$$`; a field missing from a prompt, or one the loop does not supply, fails loudly.
- `workflows/review-orchestration/scripts/stopreasons.py` [[workflows/review-orchestration/scripts/CONTEXT]] - the action names and the fenced json block `fix.md` asks for, and the reviewer schema `reviewer.md` describes.
- `workflows/review-orchestration/scripts/planning.py` [[workflows/review-orchestration/scripts/CONTEXT]] - fills `planner.md`, `synthesiser.md`, `plan-reviewer.md`, `revision.md` and, since A4, `intent-first.md`, through `loop.render`; `loop.py` fills `intent-final.md`. Both intent prompts describe the reply `stopreasons.parse_intent_reply` checks.
- `workflows/review-orchestration/scripts/measure.py` [[workflows/review-orchestration/scripts/CONTEXT]] - fills `judge.md` (A5), and through the shared steps in `loop.py` fills `reviewer.md` and `plan-reviewer.md` unchanged for a measured session; `tests/test_measure.py` renders both forms of the judge prompt and checks them against the identity rules.
- `workflows/review-orchestration/tests/test_intent_prompts.py` [[workflows/review-orchestration/tests/CONTEXT]] - asserts both intent prompts carry the exemption sentence and the line rule, the payloads hold only the brief and the plan or diff, a large diff becomes a pointer, and the brief template's Out of scope comment says what 10.2 says while the template is still refused.
- `workflows/review-orchestration/tests/test_brief.py`, `test_loop_parts.py`, `test_planning.py` and `test_plan_review.py` [[workflows/review-orchestration/tests/CONTEXT]] - assert the shipped template is refused only for its six empty sections, that every build prompt renders with its fields, that the planner and synthesiser prompts carry what plan 10.3 gives them and no provider name, and that the plan reviewer and revision prompts carry theirs and the approved plan reaches the build, fix and reviewer prompts.

## Known Issues
- The comments restate the checker's rules in brief. A rule changed in `brief.py` and not here leaves the template giving wrong guidance; the test catches a heading change but not a wording drift in a comment.
- The prompts restate rules held elsewhere: the action names and json block (`stopreasons.py`), the Revision History cap (`AGENTS.md` [[AGENTS]] and the audit), and the reviewer's fields (the schema). A change there and not here leaves a prompt asking for the wrong thing, and the loop then ends the run `error` on the reply rather than accepting it.
- The tool-rules files say what each provider's session can do, and the sessions enforce it elsewhere (`approver.py`, `codex_rules.py`, the reviewer's hook). A prompt that names a tool its provider lacks costs refused calls, not safety: a test renders each form and checks it names nothing the other provider's session alone has.
- `builder-tools-codex.md` is filled in with `string.Template`, so a literal dollar sign in it must be written twice. The command lists are passed in as values and are not parsed.
- The intent prompts restate the reply contract (`stopreasons.INTENT_SCHEMA`, and the eight opening words of `stopreasons.OPENING_WORDS`) and number the lines as `loop.numbered_lines` writes them, `N. (Section) text`; a change to either and not here gives replies the parser refuses, ending the step `error`. A test checks the prompts' wording and that `OPENING_WORDS` is still eight. A prompt must not be named `*-plan.md`, which the gitignored `*-PLAN.md` pattern matches on a case-blind file system; a test checks this.
- `judge.md` restates the judge's reply contract (`stopreasons.JUDGE_SCHEMA` and `parse_judge_reply`, the `<finding id>: <quote>` match form, `false alarm` for the control alone) and the line forms `measure.judge_material` writes; a change to either and not here gives replies the parser refuses, ending the judge session in error and, after its one rerun, leaving its items not measured.
- `builder-tools-codex.md` shows the `Get-Content` form literally as well as in the read list; a change to that line of `config/codex-read-commands.txt` must change the example too. A test checks the example is accepted by the read list.
