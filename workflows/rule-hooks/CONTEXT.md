# Rule Hooks

**Last modified:** 2026-09-21

## Purpose
Deterministic rule enforcement: moves Book Dragon's load-bearing always/never rules out of prose and into hooks that fire when an AI acts, so a violation is blocked at the moment it would happen rather than relied on by discipline. Phase 1 wires the two daily-use AIs (Claude Code and Codex) plus an AI-agnostic git pre-commit net that protects every AI and manual commits. The benchmark principle: "hooks guarantee execution; prompts do not."

## Contents
- scripts/ - `workflows/rule-hooks/scripts/` [[workflows/rule-hooks/scripts/CONTEXT]] - The `run.py` entry point, the shared `core.py` contract (which since 2026-09-05 includes a hand-written shell reader in place of `shlex`), and the `rules/` and `adapters/` packages. The blocking rules are A3 (a shell file-read where a dedicated tool applies), A4 (LOG.md shell writes), A6 (dangerous shell), A7 (`.env` writes), A8 (a PowerShell here-string in a Bash command), A9 (inline interpreter code writing a markdown file or `.env`), A10 (a command hidden inside a wrapper option's value, `env -S` and `env --split-string`) and B3 (personal data); A2 is the one remaining log-only trial. A10 runs first, because it fires on a command the reader cannot see at all, and every rule after it would allow that command for want of anything to read.
- tests/ - `workflows/rule-hooks/tests/` [[workflows/rule-hooks/tests/CONTEXT]] - Synthetic-event tests for every rule and both adapters, plus subprocess exit-code, config wiring, and cwd-drift contract tests.
- git-hooks/ - `workflows/rule-hooks/git-hooks/` [[workflows/rule-hooks/git-hooks/CONTEXT]] - The universal git pre-commit shim, activated via `core.hooksPath`.
- fire-log.jsonl (gitignored) - runtime, machine-specific append-only record of trial-rule fires, all blocks, and one `doc_sync_recording` row per pre-commit doc-sync fire; never committed.
- archived/ - `workflows/rule-hooks/archived/` [[workflows/rule-hooks/archived/CONTEXT]] - Holds this workflow's finished design-time documents (`*-PLAN.md`, `*-BRIEF.md`); gitignored and local-only. Individual files are not named here, matching that directory's own CONTEXT.md, since they are personal content.

## Inputs
- A firing tool event on stdin (PreToolUse JSON) from an AI's native hook, selected by `--ai <id>`.
- The project root, resolved at runtime from the AI's channel (`CLAUDE_PROJECT_DIR` for Claude; stdin `cwd` for Codex), falling back to `git rev-parse` then script-relative, adjudicated by a read-only AGENTS.md+.git signature test on disagreement. Codex hook launch commands also resolve the git root before starting `run.py`, because they have no project-root environment variable and may fire from a drifted session cwd.
- For B3 (personal data): the personal-data-guard workflow, reused as the single detection source.

## Outputs
- A block decision rendered in the firing AI's contract (Claude: exit 2 + stderr; Codex: `hookSpecificOutput.permissionDecision="deny"` JSON + exit 0), carrying the three-part block-and-explain message (Blocked / Why / To do it manually).
- The git pre-commit gate blocks a commit that would add personal data to tracked files (exit 1) and prints the same block-and-explain; it then prints a warn-not-block doc-sync CONTEXT/LOG drift advisory (exit 0, commit proceeds) and silently appends one `doc_sync_recording` fire-log record for that fire.
- The SessionStart reminder text (`--reinject`) re-injecting the permission gate and self-correction rules.
- Trial-rule warns and all blocks appended to the gitignored fire-log.

## Steps
1. An AI's PreToolUse hook launches `workflows/rule-hooks/scripts/run.py --ai <id>` with the event on stdin, anchored through the AI's project-root mechanism (Claude: `$CLAUDE_PROJECT_DIR`; Codex: `git rev-parse --show-toplevel` in `.codex/config.toml`).
2. `run.py` resolves the project root and routes the event through that AI's adapter into a normalised `Context`.
3. The dispatcher runs the rules for the event category (shell / write); the first block wins, warns are collected.
4. On a block, the adapter emits the AI's block contract; on a warn or allow, the action proceeds (warns are fire-logged).
5. Any hook or rule failure degrades to allow + fire-log, so a tooling bug never freezes the agent.
6. Separately, `--precommit` runs the commit-time gates (the personal-data hard block, then the doc-sync drift advisory), and `--reinject` prints the SessionStart reminder.
7. Append LOG.md with a completion or failure entry. (Per-fire activity is recorded in the gitignored fire-log, never LOG.md.)

## Known Issues
- The Codex live smoke test initially failed on 2026-07-01 because the adapter used the unsupported `continue:false` PreToolUse output and did not read apply_patch bodies from `tool_input.command`. After correction, Codex live blocking is confirmed for A7 on shell redirect, apply_patch, and cp writes to `.env.hooktest`.
- The Claude PreToolUse live block is confirmed live: both A7 paths (the Edit/Write file path and the Bash `> .env` redirect) and the git pre-commit block. It requires the `.claude/settings.json` hooks applied and a new session started, since Claude loads hooks at startup.
- **A hook that does not answer has allowed the command.** The five-second timeout means cost is a correctness property rather than a comfort, and four separate paths crossed it before being fixed: a quadratic pattern in A2, an unbounded glob expansion in A3, quadratic write patterns in A9 reaching four minutes on a large inline script, and the shared reader being re-run once per rule, which took a whole fire to 6.46 seconds while every per-rule cost test passed. Any future rule is subject to the same test: it is not enough to be right, it has to be right inside the budget on adversarial input.
- **The threat model is still a cooperative AI reaching for the wrong tool, and that is what makes the coverage boundary defensible.** Four review rounds pushed hard on evasion - quoted operators, substitutions, wrappers, `sh -c` strings, fabricated heredocs - and every one of them was fixed, so the rules read a command through a reader that models those shell rules rather than matching text. It is not a shell, and the places where it deliberately diverges are recorded in `scripts/CONTEXT.md` [[workflows/rule-hooks/scripts/CONTEXT]]. That is a real improvement, but it does not make this a sandbox: an AI with a shell cannot be contained at the verb-parsing layer, and the list of write shapes each rule recognises remains a list rather than a rule. The backstops are unchanged and are what the guarantee actually rests on: the fully-covered Edit/Write tool path, `.env` being gitignored, and the git pre-commit gate.
- **Shell-write coverage boundary (deliberate, not a gap).** A4/A7 detect shell writes to a protected file via output redirections (`>`, `>>`, `>|`, `&>`, `&>>`), `cp`/`mv` destinations (including the `-t` / `--target-directory` forms), `tee`, and `sed -i` - all through the shared `core.shell_write_targets`. This is intentionally NOT exhaustive: rarer verbs (`dd of=`, `truncate`, `rsync`, `install`, `ed`/`ex`) are out of scope by design. **Arbitrary-code interpreters were wholly out of scope until 2026-09-02, and are now partly covered by A9.** The original reasoning was that their writes "cannot be statically parsed", and that still holds for a *saved* script: nothing in `python build.py` says what it writes. It does not hold where the code is inline, in a heredoc body or after `-c`, because the code is then sitting in the command text. That gap was not theoretical - an inline heredoc appending to three `CONTEXT.md` files is what put a personal name into a publicly tracked file that day. A9 covers the inline case for markdown targets only; the saved-script case remains out of scope for the reason originally given. The threat model is a cooperative AI reaching for the wrong tool, not an adversary - an AI with a shell cannot be fully contained at the verb-parsing layer, and chasing completeness only breeds false-positive fatigue on legitimate tooling. The fully-covered Edit/Write tool path, `.env` being gitignored, and the git pre-commit gate are the backstop for anything the shell parser does not catch.
- **The pre-commit doc-sync advisory surfaces drift only, and that is separate from what it records.** Since 2026-08-11 the same step also reads the guard's `INFO` and `DEGRADED` counts into a fire-log record, so the doc-sync guard's switched-off CONTEXT-only LOG clause can be measured against real commits. The print filter below was not relaxed to do it: the advisory still announces WARN and nothing else, and recording mode adds a silent record rather than commit-time output about a clause that is switched off. Both statements are true at once, so a reader who meets only one of them will draw the wrong conclusion about the other.
- **The pre-commit doc-sync advisory surfaces drift only.** `_precommit_doc_sync` filters the guard's findings to WARN, so a DEGRADED finding (a component of the guard that could not run, today its output-inventory probe on an interpreter without PyYAML) prints nothing at commit time. That is the intended boundary while nothing consumes the inventory answers: the advisory exists to name directories needing a documentation update, and a missing package is not one. It stops being safe once the guard acts on the inventory, because a machine without PyYAML would then skip every gitignored directory at commit time with no signal, so the guard-coverage scope extension carries a locked decision requiring this advisory to be made degrade-aware at that point, presenting the degrade on its own line rather than folding it into the drift list. The producer half of the boundary is recorded in `workflows/doc-sync-guard/scripts/CONTEXT.md` [[workflows/doc-sync-guard/scripts/CONTEXT]].
- **A10 refuses a shape rather than reading it, and a harmless `env -S` is refused with the rest.** `env -S "python3 --version"` is blocked, and that is the accepted cost rather than a defect. Reading the option's value instead would mean reimplementing GNU env's own string splitting, whose quoting, backslash escapes, `${VAR}` substitution and leading-`#` comment rule each differ from the shell's, and any difference between our version and the real one would be a new bypass of the shape being closed. The cost was measured before it was accepted: across 26,985 indexed transcript messages spanning 2026-05-29 to 2026-09-20, every occurrence of `env -S` or `env --split-string` is dated to the single day the bypass was reported and is the review that reported it or the documents it produced, no script in the tree uses either spelling, and `env` is not used as a command wrapper in real work at all. **The fire-log was deliberately not consulted**, and the reason generalises: A6 had never fired on `env -S`, that being the bug, so a zero there measures the gap rather than the usage. A measured false block on ordinary work is the signal to revisit this, as it is for `find -delete`.
- A2 remains a trial rule: it fires to the fire-log only and never blocks. It scans the raw command rather than the parsed one, because the backslash it looks for is consumed by any reader that resolves quoting, so it is intentionally coarse pending fire-log tuning. A3 left that state on 2026-09-02 and now blocks; it keeps one warn, the byte-level allowance, which is warned rather than silently allowed so the fire-log shows whether it is being leaned on.
- Phase 1 ships Claude + Codex only. Cursor, Gemini/Antigravity, Windsurf/Devin, Copilot, Cline, and OpenCode are Phase 2+, covered meanwhile by the git pre-commit + audit + prose fallback. A1 and A5 are also Phase 2.
