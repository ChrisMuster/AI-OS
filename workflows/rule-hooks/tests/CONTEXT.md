# Rule Hooks - Tests

**Last modified:** 2026-09-22

## Purpose
Synthetic-event tests for the rule-hooks evaluator: prove each rule blocks what it should and allows what it should (the false-positive guards), and prove each adapter parses its AI's payload and emits the right block contract. Verification discipline: the build is not done until the suite passes and a live block is confirmed.

## Known Issues
- **A control that names a file which exists nowhere proves nothing.** The clearest example was `cd && grep pattern no-such-file.md`, written to pin that the rule does not guess a home directory: it passed however the rule behaved, because the file was absent either way, and the claim it was named for had never been tested. Rewritten to name a file that exists at the project root, it immediately failed. When writing a must-allow control, check that it can actually distinguish the two behaviours, not merely that it passes.
- **The chain operator and the operands are part of the specimen.** Three round-eleven controls could not fail because of what joined or named their commands: `pushd +0 && cat` passes whether `pushd +0` succeeds or reports an unknown status, since both let the read run, and only `||` separates them; a `;` in front of an absolute read is seen whatever the directory verb before it did; and a first operand that does not exist makes a move fail with or without the check under test. Choose the operator and the operands so the two behaviours reach different verdicts, and confirm it with the mutant before trusting the test.
- **A test must not read the constant it guards.** The work-count test for arithmetic depth first bounded its count by the production budget constant plus linear work, so a mutation removing the budget, by raising that constant, raised the bound in step and the quadratic walk passed. It was the one miss in the round-eleven mutation pass. A guard on a limit states the limit itself, as a number measured on correct code, and says so beside it.
- **A control can be disarmed by the very fix it is written beside.** `test_a6_still_allows_a_client_that_is_the_source` used `sqlite3 db .dump | grep -c 'DROP TABLE'`, and the same round's fix makes the sweep discard a `-c` matcher's pattern whether or not the upstream-only logic exists - so the test passed under a mutation that read the whole pipeline, and needed two simultaneous defects to move. Dropping the `-c` restores it. This is a sharper variant of the entry below: the command was not chosen carelessly, it was made vacuous by a change landing in the same commit, which is a reason to re-run the mutation for any control whose command touches the behaviour being changed.
- **Three tests in this suite were found passing for the wrong reason, all by mutation testing rather than by reading.** `grep -- -pattern README.md` blocked even with end-of-options handling removed, because `-pattern` was being read as a bundle of short flags containing an `r`, which made grep look recursive - two defects cancelling out. `sed -i 's/a/b/' notes.md memory/LOG.md` blocked even when only the last operand was recorded, because the protected file happened to be last. And `pushd x && popd && grep p CONTEXT.md` passed whether `popd` returned to the right directory or simply gave up, because both outcomes allow. Each was rewritten so that only the intended behaviour passes.
- The subprocess tests spawn `run.py`, so the suite shells out and takes some seconds rather than being instant. **No figure is given, and that is the correction.** One was quoted here as 2 seconds, then 5, then 8, then a measured range of 9.8 to 11.3 - and a reviewer then observed 10.3 to 19.4 across eleven runs, so the fourth attempt was wrong the same way as the first three. The number depends on what else the machine is doing, which no amount of re-measuring fixes, and a figure in prose cannot be re-measured by the reader. Run the suite if the duration matters while the suite grew past both. A number in prose decays unless it is re-measured, which is the same defect this file records for its own test count.
- **A timing assertion has to be sized so a correct implementation is nowhere near it.** The end-to-end budget test first used 234,000 characters of operator-dense input, which measures anywhere between 1.9 and 3.4 seconds on the development machine and so failed intermittently against its own threshold. An intermittent failure teaches people to rerun the suite, which is worse than not having the test. Two attempts to fix that by tuning the threshold both failed, the second still failing five times in ten runs at up to 6.98 seconds on correct code. The conclusion is that no wall-clock line inside a four-fold load-dependent spread is stable, so the end-to-end budget test now carries no wall-clock assertion at all and measures the mechanism instead: `test_the_whole_command_is_scanned_once` counts the characters the scanner walks per fire, which is a regression measured in work rather than in time.

  **Three per-rule cost tests still assert wall-clock time, and that is not the same instrument problem.** `test_the_path_backslash_scan_is_linear` (0.5s), `test_a_recursive_glob_operand_does_not_walk_the_project` (1.0s) and `test_a9_scanning_is_linear_in_the_size_of_the_code` (2.0s) each guard a quadratic path measured at 4.9 seconds, 5.9 seconds and four minutes respectively, against correct code that returns in milliseconds. The threshold sits roughly two orders of magnitude away from correct behaviour rather than inside the spread, which is what made the end-to-end test flaky, so these are order-of-magnitude canaries rather than performance lines. Read a claim about the timing strategy as being about the end-to-end test unless it names these.
- **The suite must never append to the real fire-log, and containment is done once at the top of the file rather than per test.** The store is read as evidence for decisions such as promoting a trial rule to blocking, so a fixture row is indistinguishable from a genuine fire and corrupts the evidence rather than adding noise. Two channels are closed there: `run_mod.FIRE_LOG` is repointed for the in-process writers, and `BOOK_DRAGON_FIRE_LOG` is set in `os.environ` for the subprocess ones, which re-resolve the constant in their own memory and cannot be reached by a monkeypatch. `test_fire_log_containment_is_intact` asserts both are in place and that no test hands `run.py` an env not derived from `os.environ`; `tearDownModule` is the runtime half, failing the run if the real store's size moved, which is what proves the containment worked rather than merely being written.

  **The predecessor of that test is the cautionary half, and it is why containment moved to module level.** `test_no_test_writes_to_the_real_fire_log` scanned for test functions mentioning `_precommit_doc_sync` or `run_precommit` and required each to redirect `FIRE_LOG`. There are four writers in `run.py` (`evaluate` on a rule crash, `run_ai`, `main`, `_precommit_doc_sync`), so it covered one of the four and skipped every other test in the file, while its name and its comment promised the general guarantee. It passed for three months over a store that had reached 15,827 rows, 2,096 of them one A6 fixture. Widening the filter was rejected: `evaluate` is called by nearly every test here, so the per-test rule would have to be remembered by every future test author, and the test that forgets is the test that writes.
