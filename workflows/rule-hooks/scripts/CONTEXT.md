# Rule Hooks - Scripts

**Last modified:** 2026-09-23

## Purpose
The evaluator code for the rule-hooks workflow: one entry point plus the shared contract and the rule and adapter packages.

## Contents
- run.py - `workflows/rule-hooks/scripts/run.py` [[workflows/rule-hooks/scripts/CONTEXT]] - Entry point. Parses `--ai`/`--reinject`/`--precommit`, resolves the project root, dispatches an event through the right adapter and rules, and applies the fail-safe (any failure degrades to allow + fire-log). In `--precommit` mode it runs two gates in order: a hard block on a personal-data leak (rule B3 layer 2, exit 1), then a warn-not-block doc-sync CONTEXT/LOG drift advisory (`format_doc_sync_advisory` + `_precommit_doc_sync`, running the doc-sync guard in `--staged` mode and filtering the findings it *prints* to WARN, so only drift is announced) that prints a loud block but always allows the commit (exit 0), since close-out is the deterministic gate. The same step also appends one `doc_sync_recording` fire-log record per fire, carrying that fire's `INFO` and `DEGRADED` counts, which is the collection path for the doc-sync guard's switched-off CONTEXT-only LOG clause. **The fire-log's path is overridable by the `BOOK_DRAGON_FIRE_LOG` environment variable**, read once at import so it is in place before any of the four writers can fire (`evaluate` on a rule crash, `run_ai` for warns, blocks and its four error events, `main` on a fatal, and `_precommit_doc_sync` for the recording row). It exists for one reason: a test that runs this file as a subprocess cannot redirect the constant, because the child re-resolves it in its own memory, and that is how the suite came to contaminate the real store. It is not configuration and belongs in no `.env`; unset, which is every real hook fire, the path is the workflow directory's own `fire-log.jsonl`. A warn row carries `command` alongside `reason`, so the A3 byte-level allowance can be inspected rather than only counted.
- core.py - `workflows/rule-hooks/scripts/core.py` [[workflows/rule-hooks/scripts/CONTEXT]] - Shared contract: the `Context` and `Decision` types, the three-part `format_block` helper, and **a hand-written shell reader** that every shell rule depends on. The reader replaced Python's `shlex` on 2026-09-05; the reasoning is in the module's own header and summarised under Known Issues below. Its surface: `tokenize` (words, each carrying whether it was quoted), `split_segments` (argv lists), `split_segments_detailed` (a `Segment` per command, carrying the operator that joined it to the one before, its parenthesis depth, its argv, and the files it reads from and writes to by redirection), `redirect_targets`, `shell_write_targets` (redirections plus cp/mv/tee/sed -i, used by A4 and A7), `strip_heredoc_bodies` and `heredoc_bodies` (inverses of each other: A3 and A8 want a body removed because it is data, A9 wants it on its own because inline interpreter code is what it inspects), `expanded_heredoc_bodies` (only the bodies whose delimiter was unquoted, which the shell expands), `effective_argv` (the argv with shell keywords, `!`, `VAR=value` assignments and wrapper commands and their options removed), `negation_parity` (whether that removed prefix negated the command an odd number of times, which `effective_argv` alone cannot answer once it has stripped the `!`: finding the program and judging what the command RETURNS are two questions, and a rule modelling an `&&` / `||` chain needs the second), `nested_commands` (the command a `sh -c` string or an `eval` carries), and `option_letters` (the short option letters and long names an argument list really sets, where a letter that takes a value ends its bundle and, standing last, takes the next word; used by A3 and A6, each of which had read attached and separate values as flags), and `hidden_command_wrappers` (the wrapper options in an argv whose value is the COMMAND rather than configuration, which is what A10 refuses). That last one shares one prefix walk with `effective_argv` rather than repeating it, because the two questions are answered from the same words and a second copy would be free to drift. **`effective_argv` deliberately does not recover such a value**, and says so in its own docstring, per this module's rule that a reader which stops looking somewhere has to state what is true of the place it stopped: `env -S "find . -delete"` returns an empty argv from it, and the shape is refused by A10 instead of being split, because splitting it means reimplementing GNU env's own string rules and any difference would be a bypass of the same kind. A `Segment` also carries `here_text`, the operand of a `<<<` here-string, which is literal input handed to the command rather than a filename and was previously consumed and discarded. A command substitution, a `sh -c` string and an `eval` operand are all parsed as commands in their own right and appended one grouping level deeper, because that is what they are; arithmetic expansion (`$((...))`) is not, and is read as a value rather than recursed into - but the expression is expanded before it is evaluated, so a command substitution written **inside** one really does run and is collected as a command, which reading the whole `$((...))` as an opaque value had hidden from every rule at once. **The two scanners underneath all of this (`_scan` and `_split_heredocs`) are memoised on their input text**, so one hook fire pays for one parse rather than the five the seven rules used to ask for separately. The cache sits on the scanners and deliberately not on `split_segments_detailed`, which returns `Segment` objects that its own recursion mutates.
- rules/ - `workflows/rule-hooks/scripts/rules/` [[workflows/rule-hooks/scripts/rules/CONTEXT]] - One module per rule plus the category registry.
- adapters/ - `workflows/rule-hooks/scripts/adapters/` [[workflows/rule-hooks/scripts/adapters/CONTEXT]] - Per-AI input parsing and output block-contract (Claude, Codex).

## Inputs
- A PreToolUse event as JSON on stdin (in `--ai` mode); none for `--reinject`; the git index (in `--precommit` mode).

## Outputs
- A process exit code (0 allow, 2 block for the per-AI hooks, 1 block for the pre-commit personal-data gate) plus the block-and-explain text on the AI's channel; warns and blocks appended to the gitignored fire-log. In `--precommit` mode, doc-sync drift prints the advisory to stderr but keeps exit 0 (warn-not-block); findings at any other severity, including DEGRADED, print nothing. Every fire that reaches the doc-sync step also appends one `doc_sync_recording` record (`{"event", "info", "degraded"}`) to the gitignored fire-log, including a fire with no findings at all, which carries zeroes as the denominator.

## Known Issues
- **The shell reader is hand-written because a lexer is not a shell.** It used `shlex` until 2026-09-05. `shlex` splits text into words and respects quotes, which is all it was built for, and four review rounds each found a fresh crop of the same defect: a rule reaching the wrong verdict because the reader did not know something the shell does. Live at the moment it was replaced: a newline was never a separator, so `echo cleaning` then `rm -rf build` on the next line arrived as one command and A6 allowed it; `#` was a comment anywhere rather than only at the start of a word, so `echo done#now && rm -rf build` discarded the second command; quoting was resolved and then discarded, so a quoted operator could not be told from a real one, which let `rm "&" -rf build` past A6 and made A7 fire on `echo ">" .env`; `$(...)` and backticks were not modelled, so `echo "$(rm -rf build)"` was inert; an input redirection was dropped with its target, so `cat < README.md` named no file; and a line continuation was a parse error, which means allow. Each is a fact about shell that a lexer has no reason to know, and teaching them one at a time is what produced the crop-per-round pattern. The replacement knows them by construction. **What it deliberately does not model** is recorded here rather than left to be rediscovered: `\r` is treated as whitespace where a shell treats it as an ordinary character (kept, because a pasted CRLF command is the common case on this platform, and no rule verdict was found to depend on it); a `{`/`}` standing alone in argument position is read as a group boundary; and `|&` lexes as `|` then `&`.
- **This module contains four independent character-walkers, and a fact about the shell belongs to the file rather than to one of them.** `_scan`, `_matching_paren`, `_quote_end` and `_heredoc_openers` each read the command for their own purpose, and each modelled the shell separately. Two findings of the closing review were the same omission seen twice: `_heredoc_openers` knew that `#` opens a comment only at a word boundary and that `$((` is arithmetic, while `_matching_paren` knew neither - so a `)` inside a comment closed a command substitution early for the reader while Bash carried on and ran the next line. Both facts are now single shared helpers (`_opens_comment`, `_arithmetic_end`) that every walker calls. When a walker learns something new about the shell, check the other three.
- **Arithmetic expansion is not a command, and it is not inert either.** `$((...))` holds an expression rather than a command list, so `$((rm -rf build))` is a syntax error bash rejects rather than something it runs, and `$((1<<2))` is a left shift rather than a heredoc opener - both were false positives when the reader recursed into it as though it were `$()`. What the correction then missed is that bash EXPANDS the expression before evaluating it, so a command substitution written inside one executes like any other: `echo $(( $(rm -rf build) + 1 ))` really runs the `rm`. The body is therefore scanned for its substitutions and for nothing else. The general form is worth carrying, because this is the third distinct defect at this one construct: a correction that stops the reader looking somewhere has to say what is still true of the place it stopped looking.
- **The arithmetic body is walked directly rather than handed back to the command lexer, and three separate faults are why.** The first version called `_scan` on the body, and `_scan` calls the collector back. That recursion had no depth cap where every other recursion here has one, so roughly 850 nested `$((` raised `RecursionError`; the evaluator catches a crashing rule and allows the command, so a string of punctuation switched five rules off at once. It was also quadratic, each nesting level re-reading a body that is nearly the whole remaining command, which took a 162,000-character payload from 0.03s to 4.69s against a five-second budget that a hook must answer inside or it has allowed the command. And `_scan` is a command lexer, so it honoured `#` as a comment, which arithmetic does not: bash expands the expression before it fails to evaluate it, so a substitution written after a `#` inside `$(( ))` has already run by the time the error is reported. One linear pass over the body fixes all three, and steps INTO a nested `$((` rather than over it so one pass finds a substitution at any depth.
- **A `$((` is not always arithmetic.** When the parens close without a second `)` beside the first, bash re-reads the construct as `$( (`, command substitution of a subshell, and runs it: `$((printf hi) )` prints `hi` where `$((printf hi))` is a syntax error that runs nothing. One space separates the two. `_arithmetic_span` makes that test and the scanner falls through to its ordinary substitution handling when it fails, which is what bash does with the same text.
- **Whether a `$((` is arithmetic is a structural question, not a textual one.** Bash asks whether the `)` matching the SECOND `(` is immediately followed by the `)` matching the first. At the top level `_arithmetic_span` makes that test and checks its own precondition, since asking it of every `$(` inside double quotes once dropped the outer command of `"$(cat $(ls))"`. Inside an arithmetic body the same question is answered by a stack as each paren closes, in one pass, rather than by a forward scan as each `$((` opens.
- **Why a stack, after a budget failed twice.** A forward scan at every nested level is quadratic in depth. Round eleven bounded it with a work budget and a reading past the budget, and both were wrong: that reading first dropped a buried command at the substitution depth cap, then split quoted words so `r''m` read as `r m`, and the budget was charged per walk rather than per command, so many nested siblings together passed the five-second limit. The stack has no budget and no fallback. Its quote handling follows bash's nesting, each rule measured in bash: a `$(` or a backtick inside the body runs even inside quotes; a plain paren inside quotes is literal; and a construct opened inside quotes starts fresh quoting of its own. An earlier draft rejected stack-based pairing on the ground that quote-aware pairing would hide a quoted `$(`; the resolution was to pair plain parens with quote awareness and to recognise substitutions without it.
- **The parse is memoised, and the cache is on the scanners rather than on the segment builder.** `split_segments_detailed` returns `Segment` objects and its own recursion mutates them (`segment.depth += 1`), so caching it would hand two rules the same objects and let the first rule's parse change what the second sees. `depth` is exactly what A3 reads to tell a subshell from its parent, so that cache would have re-created the subshell defect this round fixed, by another route. Caching `_scan` and `_split_heredocs` shares only tokens, which nothing mutates, and every caller still builds its own segments. `tokenize` returns a copy for the same reason. Pinned by `TestSharedParseIsSafe` rather than left as a comment.
- **A crash or a timeout is an allow, so cost is a correctness property here.** The hook has a five-second budget and a hook that does not answer has permitted the command. **The budget applies to a whole fire, and until 2026-09-07 every cost test measured a single rule** - which is how a 240,000-character command came to take 6.5 seconds end to end while all of them passed. Two causes, both closed: the command was fully re-read once per rule (five lexes and twelve heredoc passes for one fire), and the scanner asked all 22 operator candidates at every character rather than only those that could begin there. Measured after: 6.46s to 0.46s on that command, with the budget now reached at roughly 320,000 characters of the worst-costing shape rather than 240,000 of the cheapest (measured end to end: 312,000 characters of operator-dense input takes about 4.7s and 416,000 takes about 7.0s). Earlier, three separate paths crossed the budget and were fixed rather than tuned: A2's path-backslash pattern was quadratic (4.9 seconds on a 20,000-character argument) and is now written as lookarounds; A3 expanded a glob operand fully when it only ever needed to know whether the expansion was empty, so `grep -rn pattern **/*.py` walked the whole project; and A9's write patterns began with a character class and so were retried at every position, reaching four minutes on a 40,000-character inline script. The A9 fix is the general lesson: bounding the repetition was not enough, because 40,000 start positions times a bound is still millions of attempts, so the scan is anchored on the literal method name and reads the receiver backwards instead.
- **What `_precommit_doc_sync` prints and what it reads are two different sets, and both are current.** It still filters what it *prints* to `f[0] == "WARN"`, so drift and only drift is announced at commit time; that filter has not been relaxed. Separately it *reads* the guard's `INFO` and `DEGRADED` counts and writes them to the fire-log, so the guard's switched-off CONTEXT-only LOG clause can be measured against real commits. A reader who meets only the second half will think the filter was loosened; a reader who meets only the first will think `INFO` is discarded. Neither is true.
- `_precommit_doc_sync` filters the guard's findings to `f[0] == "WARN"`, so the guard's DEGRADED severity (a component of the guard that could not run, today its output-inventory probe on an interpreter without PyYAML) prints nothing at commit time. That is the intended boundary while nothing consumes the inventory answers - the advisory exists to name directories needing a documentation update, and a missing package is not one - and it is separate from the `except Exception` above it, which catches a guard that could not run at all. It stops being safe once the guard acts on the inventory, and the guard-coverage scope extension carries a locked decision requiring this advisory to be made degrade-aware at that point, presenting the degrade on its own line rather than folding it into the drift list. The producer half of the boundary is recorded in `workflows/doc-sync-guard/scripts/CONTEXT.md` [[workflows/doc-sync-guard/scripts/CONTEXT]].
- `run.py` inserts its own directory on `sys.path` so `core`, `rules`, and `adapters` import cleanly when invoked as a script path. Kept stdlib-only and light at import time; the personal-data guard is imported lazily only when a write is actually checked.
