# Rule Hooks - Rules

**Last modified:** 2026-09-22

## Purpose
One module per enforcement rule plus a registry mapping an event category (shell / write / read) to its ordered list of checks. Each rule is a pure `check(ctx) -> Decision | None` function, AI-agnostic; the adapters handle the per-AI input and output.

## Contents
- __init__.py - `workflows/rule-hooks/scripts/rules/__init__.py` [[workflows/rule-hooks/scripts/rules/CONTEXT]] - The registry: `rules_for(category)` returns the ordered checks (hard rules before trial rules).
- env_protect.py - Rule A7: block AI writes to `.env` / `.env.*` (except `.env.example`); reads allowed. Compared case-folded, because on this platform `.ENV` is the same file and this was the only rule of the five that compared exactly.
- log_redirect.py - Rule A4: block shell writes into a `LOG.md` file - redirections (`>`/`>>`/`>|`/`&>`/`&>>`) plus `cp`/`mv`/`tee`/`sed -i` targets, via the shared `shell_write_targets` helper (not just `>`/`>>`). The name must BE a log (`LOG.md`, or `-log.md`/`_log.md`/`.log.md`) rather than merely end in those letters: an `endswith` test also matched `backlog.md` and `CHANGELOG.md`, which blocked the documented recovery of `memory/backlog.md` from `memory/backlog-backups/`.
- dangerous_bash.py - Rule A6: block destructive shell (rm -rf, git push --force including a `+refspec`, git reset --hard, git clean -fd/-fdx, destructive SQL, whatever a `find -exec` runs including a shell it invokes, and **every** `find` command carrying `-delete`, blocked on the verb exactly as `rm -rf` is, with none of the expression's shape consulted. **That replaced an adjudication engine on 2026-09-20.** A6 used to ask whether a predicate narrowed the action and allow the command when one did; rounds 14 to 18 each found a defect in the answer, and round 18 settled that the question cannot be answered from the argv at all, `-fstype ntfs` being a genuine test that narrows nothing on a single-filesystem tree, as are `-name '*'`, `-size +0c`, `-type f` on a tree of files and any all-matching regex. `narrows` was a syntactic property of the predicate where safety is a property of the operand supplied, so no table row and no evaluator closed it. The membership test is deliberately a little wider than the action: `find . -name '-delete' -print` names a FILE, deletes nothing, and still blocks, which is the same trade `rm` already makes for `rm -- -rf`); parses the command, never substring-matches, and reads the program through any wrapper or shell keyword in front of it. It asks two questions rather than one: what each segment **runs**, and what a SQL client is **fed** - destructive SQL reaches a client as an argument, as a heredoc body, as a here-string, or through a pipe, and only the first was ever checked. Only the stages **upstream** of the client are read, because a client is often a pipeline's source rather than its sink and `sqlite3 db .dump | grep -c 'DROP TABLE'` is read-only work. An upstream stage's arguments stand in for what it emits, which holds for a command that prints them and for a matcher that selects lines by them, and stops holding when the matcher was asked for something else: `grep -c`, `-l`/`-L` and `-q` emit a count, a filename and nothing respectively, so their pattern is not what reaches the client. **The letters differ per program and are held per program**: in ripgrep `-L` is `--follow` and prints matching lines, so grep's table applied to rg skipped a stage that emits exactly what the sweep exists to read. A matcher absent from that table is never skipped, which is the conservative direction here; `ag` and `ack` are absent deliberately, neither being installed on this machine to measure. Everything after `--` is an operand rather than a flag, the same fact A3's `_flag_args` already knows. A short-flag bundle counts only when every letter in it is one the program takes without a value, because an attached value is not more flags - `rg -tsql` is `-t sql`, whose letters include `q` and `l` - and an attached value is also read as the text it is when the pipeline is searched, so `grep -e'DROP TABLE t'` is not hidden by the flag letter touching the statement. Option letters are read by the shared `option_letters`, which ends a bundle at a value-taking letter and makes one standing last take the next word, so `grep -e -c -e 'DROP TABLE t'` sets no count; an unknown long option is assumed to take a value, which only ever removes a skip. A matcher carrying `--label` is never skipped, because with `-l` or `-c` it prints the label, which is argument text. The force test asks whether a plain `--force` is present rather than whether a lease is absent, so `--force-with-lease --force` is a force push while `--force-with-lease` alone still is not. **A filter that removes the statement is not its source**: an inverted match (`grep -v`, `--invert-match`, `rg -v`) emits the lines that do not match, and a sed script made only of `/re/d` deletions or an awk program that is only `!/re/` or `$0 !~ /re/` emits its input minus the lines naming the pattern, so `sed '/DROP TABLE/d' dump.sql | sqlite3 db` is not read as supplying the DROP it removes. Only those exact shapes qualify: a sed script that prints, substitutes or uses `!d`, a script read from a file with `-f`, and an awk program that does anything else are read as before, because each could as easily add the statement as remove it.
- hidden_command.py - Rule A10: block a command hidden inside a wrapper option's value, which today means `env -S` and `env --split-string` in all four of their spellings (separated, attached, long, and inside a short-option bundle). GNU env splits that option's value into words and executes them, so the value is the command; the shared reader skipped it as wrapper configuration and was left with an EMPTY argv, which every shell rule reads as nothing to judge. It is therefore a bypass of the reader rather than of any one rule, and it was measured as one: before the repair the same wrapper hid a destructive command, a dedicated-tool read, a LOG.md redirect and an inline document write alike. **The shape is refused rather than read**, because recovering the value means reimplementing GNU env's own string splitting (its quoting, backslash escapes, `${VAR}` substitution and leading-`#` comment rule all differ from the shell's) and any difference between the two would be a fresh bypass of the same shape. It runs first in the registry, since a rule reporting that a command cannot be read has to be asked before the rules that read it. Only the wrapper's OWN option region is examined, which is what keeps `env ls -S` (where `-S` sorts a listing by size) allowed.
- personal_data.py - Rule B3 (layer 1): block personal data written into a committable (non-gitignored) file, reusing personal-data-guard.
- powershell_syntax.py - Rule A8: block a PowerShell here-string (`@'...'@` / `@"..."@`) passed to the Bash tool. Detects the opening delimiter at end of line, which is what PowerShell's syntax requires and ordinary Bash never produces, after stripping heredoc bodies so text quoted into a command is not scanned.
- interpreter_write.py - Rule A9: block inline interpreter code (a heredoc body the interpreter opened, or a `-c`/`-e` string including the attached `-c'code'` spelling, in python/node/perl/ruby/php and their version-suffixed names) that writes a markdown file or `.env`. A narrow, deliberate exception to the interpreter coverage boundary: it applies only where the code sits in the command text and can be read, never to a saved script whose writes cannot be known from the command, and not to a heredoc fed to a saved script, whose body is that script's input rather than its code. It inspects the interpreter's code rather than the whole command line, so quoted sample text beside a harmless `-c` does not fire. Each write and its target are found in one pass; where every target is a single quoted literal the question is asked of the target, and where any target is computed the older whole-code test applies, deliberately, because `p = "notes.md"` then `open(p, "w")` is the shape the rule exists to stop. **A document name Python builds but the command's text never spells out is refused before any write shape is consulted.** Python joins adjacent string literals and decodes escapes before the code runs, so `open('notes.' 'md', 'w')`, the same split with a comment or a backslash continuation between the parts, and even a single literal such as `'notes\x2emd'` all write a markdown file while no `.md` text exists for the computed-target fallback to find. The question is asked of Python's own parser (`_hidden_documents`), which is the reader that runs the code and so has no difference from it to exploit: for every string in the program it compares the filename at the string's end with that string's own source text, and refuses when the name is not visible there. It is still a refusal rather than an assembly, nothing about the write being inferred, and it runs before the write shapes because a comma inside a comment between the parts hides the call from them. A read spelled the same way is refused with the rest. Code the parser rejects keeps the older regex refusal of a whitespace join as a backstop, which also covers ruby, the one other interpreter here that joins adjacent literals, and which refuses a split literal naming a non-document too. A target genuinely assembled at runtime (`'notes.' + 'md'`, `"%s.md" % "notes"`, an f-string placeholder) is not a string Python builds before running, and keeps going to the fallback that exists for it. The shapes cover the ordinary spellings of a write rather than one of them: `Path(...).open(...)` with the mode positional or written as `mode=`, with or without the further arguments this project's own encoding rules require; and ruby's `File.open`, whose mode is **read** rather than assumed, since ruby defaults to reading exactly as python does and treating every `File.open` as a write blocked the ordinary way to read a document in a one-liner. Ruby's mode is read in all three of its spellings - the `mode:` keyword, a `"w:UTF-8"` encoding suffix, and an integer built from the `File::` writing constants - because splitting the read from the write lost all three, and the encoding suffix is the form this project's own rules push an author toward. `File.new` and `IO.write` are read like their siblings, the mode string may name both an external and an internal encoding, and a call used as a receiver is read by its argument only when it has exactly one (`Path("notes.md").write_text(...)`); a call with several arguments or none is a computed target, because the path of `io.FileIO(path, mode)` is its first argument while the path of `Path("docs", "notes.md")` is all of them, and `Path("notes.md").resolve()` has none. Ruby's `File.write`, `File.open` and `File.new` are read with or without parentheses, and `binwrite` and Kernel `open(path, "w:UTF-8")` like their siblings. `.env` is covered here because A7 reads the Edit/Write path and the shell write verbs and never reads interpreter code, so that route was guarded by nobody. **Which words are code is read per interpreter**, the way each reads its own command line: node's `--eval`, `--print`, `-p` and `-pe`, php's `-r`, and a code letter ending an option bundle (`python -Sc`, `perl -lne`, `ruby -we`) carry code; node's `-r` loads a module and does not; an option's value (`-W ignore`, `-X utf8`) is not a script name; and reading stops where the interpreter's does, at a script path, a `-m` module, `-`, `--`, and for python after `-c`, so a flag after a script belongs to that script. A heredoc is read as code only when the interpreter has neither a code option nor a script, because beside `-c` or `-e` it is the data the program reads. An option the rows do not know makes the next bare word untrusted as a script, which reads more words rather than fewer. Python's `open()` and `Path.open()` are read with other keywords before `mode=`; a keyword argument of a method call is never taken as the path, while `file=`, `dst=`, `path=` and `filename=` name one; a python string prefix (`r`, `b`, `u`, `rb`) still makes a literal while an f-string stays computed; perl's `open` is read with or without parentheses, with any handle, the `+<`/`+>` modes and a `:layer`; and ruby's Kernel `open` is read without parentheses.
- shell_style.py - Rule A2 (path-shaped backslash), still a warn-only trial, and rule A3 (dedicated tools over shell), blocking since 2026-09-02. A3 blocks a shell command that reads a file with cat/sed/find/grep/head/tail where Read/Grep/Glob apply, and warns on an `echo` redirected into a file. It identifies a file read by whether the command names something that **exists on disk**, counting operands, an input redirection (`cat < README.md` names a file), brace expansion and globs; a command naming no existing file is reading standard input and is allowed. The program is read through any wrapper, environment assignment or shell keyword in front of it. Operands resolve against the directory in force, which `cd`, `pushd` and `popd` move. **All three are applied by one function with one exit status, and a leading `!` inverts that status before it becomes chain state**, so what a success or a failure means for a following `&&` or `||` is decided in a single place: a failure (a `cd` to a directory that is not there, a `popd` or a bare `pushd` with nothing on the stack) does not move the shell and ends an `&&` chain, a success ends an `||` chain, and an unknowable destination (`cd` alone, `cd -`, or a target the shell expands such as `cd $PWD`) ends neither. They were three branches each deciding that for itself, and the result was the same defect three times: `cd` knew that success ends an `||` chain and the two stack verbs did not, so `pushd x ; popd || grep p file` blocked a read bash never performs. In a pipeline stage, which runs in a child, all three lose their directory and stack effects but keep their exit status: one standing at the END of a pipeline still settles the following `&&` or `||`, because a pipeline's status is its last stage's, and one in the middle settles neither. Three further facts the model now holds: a `pushd` saves the directory it is LEAVING, which is known even when the destination is not, so an unresolvable `pushd` no longer leaves the modelled stack empty where bash's is not; a bare `pushd` SWAPS the top of the stack with the current directory rather than blanking it, both halves being known; and `-n` suppresses the directory change for `pushd` and `popd`, leaving only the stack manipulation - including in the two spellings where the change is what would fail, so bare `pushd -n` and `pushd -n nosuchdir` both succeed without moving. A stack position is not a directory name: `pushd +0` rotates by nothing and succeeds, any other position leaves the stack marked unresolvable and the status unknown, and two operands to `pushd` or `cd` are an error that moves nothing. The arguments of all three builtins are read by one parser that follows bash: options only before the first operand, so `pushd workflows -n` is too many arguments; an option the builtin does not accept is an error that moves nothing; a lone `-` is the previous directory, an unknown destination rather than a missing operand; when several stack positions are given the last one is used; `popd +N` shrinks the modelled stack as well as blurring it; and after `--` a `+1` is a directory name. `grep`'s recursive flag is read through the shared `option_letters`, so an attached pattern such as `-e"Refactor"` no longer supplies an `R`. The `pushd`/`popd` directory stack is held per shell depth, because a subshell gets its own copy and what it pushes dies with it. `grep`'s pattern and `sed`'s script are not files however they were supplied, `find` and `grep -r` with no path operand read the current directory, and a `find` given an action or a `tail` in follow mode is not a read at all, since neither has a dedicated-tool equivalent. One allowance: a search **whose pattern** is a byte or control-character escape (`$'\r'`, `\t`, `\x0d`, `\0`) is allowed and warned, because those reads have no dedicated-tool equivalent and the review ledger requires them for line-ending and encoding checks. The allowance is judged per segment and asked of the pattern argument, so a byte-level read excuses neither an ordinary read elsewhere on the line nor one in its own command.

## Known Issues
- A2 is a deliberately log-only trial (higher false-positive risk than the hard rules), reviewed via the fire-log before any promotion to blocking, and intentionally coarse since it scans the raw command. A3 was promoted out of that state on 2026-09-02.
- A3's file-read test rests on the operand existing on disk, so it under-reports by design: a read of a file that is absent is allowed. That direction is deliberate. A rule treating any leftover word as a filename blocks commands that name no file at all, which is the failure that makes a hook something to route around.
- **A relative read after a `cd` the shell expands is allowed, and that gap is a decision rather than an oversight.** `cd $PWD`, `cd "$(pwd)"` and `cd $REPO` name a destination only the shell can resolve, so the working directory becomes unknown and a relative operand after them resolves to nothing: `cd $PWD ; cat README.md` is allowed where `cat README.md` alone blocks. The alternative is to assume such a `cd` did not move the shell and resolve against the previous directory, which catches this case and wrongly blocks a read after a `cd` that really did move. The user chose to keep the gap on 2026-09-07, on the standing grounds above that a false block is the more expensive failure here. Two things do still hold after such a `cd`: the `&&` chain is no longer killed, so later commands are examined, and a read naming an absolute path still blocks. `test_a_relative_read_after_an_expanded_cd_is_a_known_gap` pins the gap so it cannot close unnoticed.
- **A3's byte-level allowance is asked of the pattern, not of the words.** It applies only to `grep` and `sed`, the two programs that have a pattern at all, and only when the pattern itself is the escape - supplied as the leading operand or through `-e`/`-f` in any of its spellings. Two narrowings got it here and both were bypasses rather than tidying: matching the escape anywhere in a word let a Windows path (`workflows\rule-hooks\CONTEXT.md` contains `\r`) buy the allowance, and matching it in any word of the segment let a spare operand buy it, so `cat README.md $'\r'` read the file under a warning.
- A3's `_VALUE_FLAGS` list is not exhaustive. An unlisted flag that consumes the next token makes that token read as a file operand, and if it happens to name something real the command is blocked wrongly. Kept to the forms this project uses; extend it when a false block appears rather than pre-emptively. The same is true of `_WRAPPER_VALUE_FLAGS` in `core.py`, where the failure direction is the opposite and worse: an unlisted wrapper option puts the option in argv[0] and hides the command from every rule. **That table has now failed in a third direction as well, which is worth stating separately because it is not an omission**: a listed option can be the wrong KIND. `-S` was correctly listed as taking a value and wrongly treated as configuration, when GNU env runs that value, so the skip was complete and correct and threw the command away. An entry is therefore two claims rather than one, that the option takes a value and that the value is not a command, and `_WRAPPER_COMMAND_FLAGS` now records the second for the options where it is false. A10 blocks those; nothing checks the rest of the table for the same mistake.
- **Two things A3 sees that no other rule does, and one it does not.** A `find` carrying an action (`-delete`, `-exec`) is not a read and is waived here, because Glob cannot delete; A6 examines what the action runs, so the waiver is not a hole, but it does mean an `-exec cat` rides along and is accepted as the same trade. A `tail -f` is waived for the same reason: the Read tool cannot follow a growing file. What A3 does not see is a file operand arriving on stdin, as with `xargs cat`, because nothing in the command text names it.
- A9 reads interpreter code deliberately, where A3 and A8 strip heredoc bodies first, because the body is exactly where the code it inspects lives. **The cost is that where a write's target is computed it cannot tell code from a quotation of code**: a command whose interpreter code merely *contains* the text of a markdown path fires, even when it is passing that text as data. That is narrowed but not removed. Where every write names its target as a single quoted literal the question is asked of the target, so a `.json` write whose contents mention `README.md` [[README]] no longer fires; where any target is computed the older test applies, because narrowing further would wave through `p = "notes.md"` then `open(p, "w")`. It is accepted for the same reason A8 accepts its equivalent: a wrong fire costs one retry against a block message naming the correct tool, where the alternative is a rule that can be evaded by quoting. It fires in practice on ordinary work - editing a regex that contains `\.md`, or writing a `.txt` whose body mentions a document - so test the rule through the suite rather than through a script that quotes the shapes.
- **Three A9 write routes that are known to be open**, found by a reviewer sweeping for them rather than by anything failing, and recorded here so they are a boundary rather than a surprise: node's `createWriteStream`, python's `os.open` paired with `os.write` (an unquoted integer mode, and a bare `.write(` deliberately not being a write verb), and `perl -pi -e` in-place editing (whose code contains no write call at all, where `sed -i` on the same file is caught by A3). Each is the same "list, not a rule" boundary the entry below describes, and none is a regression. A fourth, `open(path, encoding="utf-8", mode="w")` with the mode after another keyword, was on this list until 2026-09-13, when the user chose to close it because this project's own encoding rules make it a likely spelling rather than an unusual one.
- A9 covers markdown and `.env` targets only. An inline interpreter write to a `.py`, `.json` or other non-document file is allowed by design: throwaway code surgery during mutation testing is legitimate and Edit is not the better tool for it. The line is drawn where the review trail and the personal-data risk live. **The write shapes it recognises are a list, not a rule**, so a write by another name is out of scope: `os.open` plus `os.write`, `fileinput` in-place editing, and shell verbs outside `cp`/`mv`/`tee`/`sed -i` such as `truncate`, `dd of=` and `install`. Those are the same deliberate boundary the workflow's Known Issues records for rare write verbs, and the backstop is unchanged: the fully-covered Edit/Write tool path, `.env` being gitignored, and the git pre-commit gate.
- A8 covers the PowerShell here-string only. Other PowerShell-isms in a Bash command (backtick line continuation, `$env:VAR`, `Test-Path`) are deliberately out of scope: the here-string is the fault that actually recurs, and each of the others needs its own false-positive analysis rather than being bundled in on the assumption that it is the same problem.
- A8's heredoc stripping recognises the common forms (`<<DELIM`, `<<'DELIM'`, `<<"DELIM"`, `<<-DELIM`). A body introduced some other way - a quoted multi-line string built by the command itself, for instance - is still scanned, so a here-string appearing as data inside one would fire. The narrowing to an end-of-line opening delimiter keeps that unlikely, and a wrong fire costs one retry against a block message carrying the correct command.
- A6's destructive-SQL detection considers every client in a pipeline, not the first, and reads only what flows into each one; it fires only when a known SQL client (sqlite3/psql/mysql/mariadb/mysqlsh) is the program, to keep false positives low. **That client list is an enumeration, and enumerations are the shape this rule set keeps getting wrong**, so it is recorded as a deliberate boundary: a client not on it is not checked. It covers argument, heredoc-body, here-string and piped input, reading only what flows into the client. What stays out of scope is `sqlite3 db < drop.sql`, where the statements live in a file and nothing in the command text says what they are - this rule reads commands, not files.
- **A9 asks whether a mode permits writing rather than holding a list of write modes.** The list was `w`/`a`/`x`, which is the set of modes that *begin* by writing, and it silently omitted every read/write mode: `open("README.md", "r+")` was allowed. Python's rule is that a mode carries exactly one of r/w/x/a, optionally one of b/t, optionally a `+`, and no character twice - in **any order**. So the question is whether that single base letter is w, a or x, or a `+` is present anywhere, and it is asked by `_permits_writing` rather than by a pattern. Writing it as a regex was the first attempt and it re-encoded the assumption that the base letter comes first, which is not Python's rule and missed `bw`, `+w`, `+r`, `br+`, `b+r`, `ba+` and `t+r`. The mode must still close its quote, which is what keeps a filename beginning with `w` from being read as a mode - the defect that once blocked one of this project's own commands. The same question is now asked of ruby's `File.open`, whose second argument is the mode, and the receivers whose `open` takes the FILE first (`io`, `codecs`, `gzip`, `os`, ruby's `File`, and their like) are named so their path is never read as a mode; those calls are covered by the `open(target, mode)` shape instead, which reads them correctly.
- **A9's option rows are lists, and two of the six are documented rather than measured.** Which options carry code, take a value or end option reading was measured in Git Bash for python, node and perl on 2026-09-13; ruby and php are not installed on this machine, so their rows follow each interpreter's documentation. An option no row knows is handled in the direction that reads more: the next bare word is not trusted as a script, so option reading continues past it. The cost is a false block when that word really was a script and a later word looks like a code option; the alternative, trusting it, would miss a write whenever the unknown option takes a value.
- **A6's filter skip reads a stage's arguments, not its input.** `grep -v` and a delete-only sed or awk are not read as supplying their pattern, but a heredoc body fed to such a stage is still read, so piping a heredoc that holds a DROP through `sed '/DROP TABLE/d'` into a client is falsely blocked. Kept because the body is text the command itself supplies, and allowing it would need the rule to model what the filter removes from that text.
- **A6's filter skip asks about the filter's OWN pattern, not about what reached it** (R14-4, kept 2026-09-18). `printf 'DROP TABLE t;' | grep -v 'DROP TABLE' | sqlite3 db` is blocked although the filter emits nothing, because the rule reads the earlier producer's arguments as what flows downstream and does not model the later filter removing it; the sed and awk equivalents behave the same. Only ever a false block, on an unlikely pipeline. Kept at the user's decision rather than fixed with the rest of round fourteen, because closing it means modelling what a filter removes from text another stage produced, which widens A6 in exactly the family of defects the recent rounds kept finding. Pinned by `test_recorded_limit_a_later_filter_does_not_unblock_an_earlier_producer`.
- **What A9's hidden-name check covers, and the two things it deliberately does not** (PP1, 2026-09-22). It covers every string Python builds before running, whatever the spelling, because the parser does the reading. It does not cover a name assembled while the code runs, such as `'notes.' + 'md'`, a variable or `chr(46)`: no hook reading the command can see a value that exists only at runtime, and those stay with the computed-target fallback, which finds them only where `.md` or `.env` text appears somewhere in the code. And it runs only on code the Python parser accepts; anything else, other interpreters included, has only the regex backstop for a whitespace join. The accepted cost is that a READ spelled with a hidden name is refused too, since the check cannot rely on the write shapes. It was measured before being accepted: read as though it were inline code, no tracked Python file spells a document name this way, and the transcript measurement for the adjacent-literal shape found no real use.
- **A3 settles chain state only from a directory verb, so a negated pipeline ending in an ordinary command is read wrongly** (R15-2, kept 2026-09-18). The leading `!` is carried across the pipeline correctly, but the inversion is applied only where a directory verb's outcome becomes chain state, so `! cd no_such_dir | echo hi && cat README.md` blocks the payload: Git Bash runs `echo hi`, the pipeline therefore succeeds, the `!` inverts it to a failure, and the `&&` branch never runs. Only ever a false block, and only on a negated pipeline whose last stage is not a directory verb. Kept at the user's decision rather than fixed alongside the round-15 blocker, because closing it means settling chain state from any last stage's known status rather than from a directory verb's, which widens the same directory model that produced this round's blocker. Pinned by `test_recorded_limit_a_negated_pipeline_settling_on_an_ordinary_command`, which carries the un-negated form as its control: that one is a correct block, and a later fix must not take it along.
- **A6 blocks a legitimate `find -delete`, and that is the accepted cost of the 2026-09-20 change rather than a defect.** `find . -name '*.pyc' -delete` is an ordinary cleanup and is now refused, with the block message naming the manual path. The cost was measured before it was accepted: across 82 days of fire-log and the whole session-search index, no session had ever run a `find -delete` as real work, and every occurrence of the command in this project's history postdates the check that adjudicated it. The predicate table, the expression evaluator and their 33 tests went with the change, and with them the whole class of defect that rounds 14 to 18 kept finding. A measured false block on real work is the signal to revisit this, and the decision and its reasoning are in [[guard_coverage_decision_log]].
- **Two limits the user chose to keep on 2026-09-13, both only ever a false block.** A6 assumes a long option it does not know takes the next word, so `grep --color -c 'DROP TABLE' | sqlite3 db` hides its count and is blocked while `--color=always -c` is read.
