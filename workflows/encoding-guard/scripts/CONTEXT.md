# Scripts

**Last modified:** 2026-08-05

## Purpose
Holds the encoding-guard implementation. `run.py` is both a CLI and an importable module: it walks the project tree (pruning system, generated, and scraped-data directories, while scanning authored hidden config dirs such as `.codex/` and `.github/`), classifies each text file for UTF-8 validity, mojibake signatures, unexpected BOMs, and CR line endings, checks Python sources for text I/O calls that omit an explicit `encoding=` or `newline=` or that pass one carrying a value the rule does not allow, and in fix mode rewrites damaged files to clean UTF-8 with LF line endings and ASCII punctuation. The code checks find their calls on the parse tree rather than by matching call-shaped text, so a definition sharing one of the covered names is not read as a call, and a `.py` file that will not parse reports a DEGRADED finding (the check did not run on it) instead of being scanned as raw text. Detection signatures are built from Unicode escapes so this source stays pure ASCII and never flags or repairs itself.

## Contents
- run.py - `workflows/encoding-guard/scripts/run.py` [[workflows/encoding-guard/scripts/CONTEXT]] - Entry point and library. Provides `--check` (read-only scan, with `--json`) and `--fix` (in-place repair, with `--dry-run`). The directory walk prunes system/tooling dot-dirs via a `SKIP_DIRS` denylist but descends into authored hidden config dirs so their tracked prose is covered. The pure helpers `scan_text`, `repair_text`, and `repair_bytes` are unit-tested without touching the filesystem.

## Inputs
No required inputs. Optional flags:
- `--check` - Read-only scan (default when no mode is given).
- `--json` - Emit findings as a JSON object on stdout (for the audit hook).
- `--fix` - Repair flagged files in place.
- `--dry-run` - With `--fix`, print each repair without writing.

## Outputs
- Findings report on stdout (human or JSON).
- In fix mode: repaired files (UTF-8, LF). Read-only check writes nothing.
- LOG.md entries (workflow and root) on a real fix run.

## Steps
Run from anywhere:

```
python workflows/encoding-guard/scripts/run.py --check [--json]
python workflows/encoding-guard/scripts/run.py --fix [--dry-run]
```

## Known Issues
- The code checks find their calls on the parse tree (`_call_sites` over `ast.Call` nodes), and the arguments of a found call are then parsed rather than pattern-matched. They flag a missing `encoding=` on text-mode `subprocess` calls (WARN) and on `open`/`.open`/`read_text`/`write_text` calls (INFO), a missing `newline=` on a text-mode write (WARN), either argument carrying a value the rule does not allow (WARN), and a `.py` file that could not be read as Python at all (DEGRADED). The name set in `_call_name` is now the boundary of what is examined, described below.
- Argument *values* are decided by `_encoding_verdict` and `_newline_verdict`, which return `ok`, `bad`, or None for unreadable. Both read the argument through `_literal_or_none`, which returns the *evaluated* value of a literal (via `ast.literal_eval`) or the fact that it is `None`, and reports anything else as unreadable. Evaluating rather than comparing source text is what makes `"\x0a"` pass as a line feed and `r"\n"` fail as the backslash-and-'n' it actually is, with no special handling of string prefixes. `_literal_or_none` is deliberately separate from `_literal_value`: that one serves the mode reader, which wants the characters as typed and for which `None` is not a mode, so folding them would change how a mode is read in order to answer a different question. The verdicts are separate functions rather than one parameterised check because the allowed sets are not the same shape - `_UTF8_ALIASES` mirrors Python's own codec-name folding (case-insensitive, with `-` and `_` alike), while `_ALLOWED_NEWLINES` is a two-member set holding a line feed and the empty string `csv` needs. A wrong value is WARN where a missing `encoding=` on an `open` stays INFO, and that difference is load-bearing: only WARN hard-fails the close-out gate.
- `_call_name` is the real boundary of both code checks: a call whose callee it does not name is reported clean rather than reported missing, and nothing in the output distinguishes the two. `.open` was absent until 2026-08-04, which made a CRLF-writing append invisible for a day. Adding a shape means adding it to `_call_name`, deciding its mode position in `_OPEN_CALLS`, and writing a positive control per clause. This used to be a regex (`_CALL_RE`) over the source text, which had the opposite failure too: `def open(self, mode="w")` is call-shaped text and was read as a text-mode write with no `newline=`, a WARN that hard-fails close-out on code doing no I/O at all. Discovery moved onto `ast.Call` on 2026-08-05, so a definition is not a call by construction rather than by a special case.
- A `.py` file that will not parse or will not tokenise gets one DEGRADED finding and no code findings. `check_python_code` parses first and returns early; `_blank_tokens` returns None rather than the unmodified source when tokenising fails. The old fallback returned the source unblanked, which meant every string and comment in an unreadable file was then read as code, so prose could become a blocking WARN. Degrading is the honest answer and is non-blocking downstream, but it is a real gap in coverage rather than a pass: the file was not checked.
- The newline check needs an open-style call's mode to decide whether it is a text write. `_open_mode` reads a `mode` keyword or a positional argument at the index `_OPEN_CALLS` gives for that call name: 1 for builtin `open(path, mode)`, 0 for `Path.open(mode)`, where the path is the receiver rather than an argument. A **computed** mode (`open(p, mode, ...)`) is deliberately not guessed at and is left unflagged, so an unreadable call is a false negative rather than a false positive. `.write_text` needs no mode inspection and is always a text write.
- Argument presence is decided by `_parse_call`, not by searching the call text. Every call is parsed once from two aligned views produced by `_blank_tokens`: `_code_only` (strings and comments blanked) supplies argument *names*, and `_no_comments` (comments blanked only) supplies argument *values*, with `_arg_spans` giving the offsets that serve both. Both views preserve the source's length, which is the property that lets one set of spans index either, and which also lets the tree's node offsets index into them. The reason for the split is that the two questions need opposite things: a name must never be readable inside a string or a comment, and a mode literal must still be readable. Collapsing them back into one view silently breaks one question or the other.
- The tree and the blanked views are two descriptions of the same source, and `_call_sites` checks they agree before trusting either. A call found on the tree is kept only if the parenthesis located in the blanked view closes exactly where the tree says the call ends. The case that needs it is a call written inside an f-string: Python only tokenises f-string internals separately from 3.12, so on the project's stated 3.9 floor the whole literal is one blanked token and the search would otherwise run on to some unrelated later call and read *its* arguments. A site that fails the check is dropped, which is a false negative rather than a wrong answer.
- A splatted call (`open(p, "w", **opts)`, `open(*parts)`) is skipped entirely and reported as nothing. `**opts` may carry either keyword, and `*parts` may supply either positionally, so absence is unprovable; `_Call.star` and `_Call.double_star` carry that fact out of the parser. `_open_mode` also treats a positional splat as an unreadable mode, which matters only if it is called directly, since `check_python_code` skips such calls before reaching it.
- `.open` is separated from its namesakes by two tests applied in order, because neither is sufficient alone. First `_receiver_root` walks the receiver expression down to its leftmost plain name and `_call_name` drops the call when that name is in `_NON_PATH_OPEN_ROOTS`, which covers `tarfile.open(...)` and `zipfile.ZipFile(...).open(...)` alike. Whatever survives that is then judged on mode shape: `_as_mode` accepts only a short literal drawn from `rwxab+t`, so an unrecognised receiver calling `.open("some/resource")` is not read as a write on the `x` or `w` inside that string. Each test covers what the other cannot. Mode shape alone cannot tell `tarfile.open("w")`, which opens a file *named* `w`, from `p.open("w")` - that is the gap that existed until 2026-08-05, and with `encoding` now a blocking label the misread would fail close-out. The receiver list alone cannot help with a receiver nobody has heard of, which is most of them. The cost is that a `Path.open` with a computed mode is unflagged, which is the same false-negative trade the paragraph above makes.
- `_NON_PATH_OPEN_ROOTS` excludes `io`, `codecs` and `gzip` along with the rest, and those three are a real false negative rather than a namesake: they take `(file, mode)` like the builtin, so a genuine text write through one of them is not checked. Excluding them is still the right answer for now, because the alternative is reading their filename argument as a mode; giving them the builtin's mode position would be a coverage extension with its own controls.
- The residual false positive is a bare-name receiver: `thing.open("w")` and `p.open("w")` are the same shape, and telling a `Path` from any other object needs type inference the guard does not do. It is accepted deliberately - the alternative is dropping the dotted write check, which is the case the clause exists for - and pinned by a test so it stays a decision rather than becoming a surprise. A receiver with no plain name at its root (`(base / name).open("w")`) is checked for the same reason: it is a real `Path.open` and dropping it would lose coverage.
- Repair maps cover the common Windows-1252 punctuation set. Other invalid bytes are reported but not auto-repaired, to avoid corrupting content by guessing.
- Directory coverage is a denylist (`SKIP_DIRS`), not an allowlist: any future hidden dir not on the denylist is scanned. This is intentional so new AI config dirs are covered automatically, but a new tooling dir that should be skipped must be added to `SKIP_DIRS`. The `TEXT_EXTS` gate still prevents reading binary files in any case.

- 2026-08-04 - `check_python_code` restructured so the encoding and newline clauses are independent checks rather than one early return. It previously did `if "encoding=" in call: continue`, which meant a text write that pinned the encoding and omitted `newline=` never reached any further check and was reported clean - the single line that left the newline half of the AGENTS.md rule unenforced across the project. Three helpers back the new clause: `_split_args` (quote- and bracket-aware top-level argument splitting, so a comma inside a string cannot split an argument), `_literal_value`, and `_open_mode`, which together decide whether an `open()` call is a text write without resorting to a substring test that cannot tell a mode from any other short literal. `_is_text_mode_write` excludes reads, binary modes, and `subprocess`, because the newline rule governs what is written rather than what is read.
- 2026-08-04 - `.open` added to `_CALL_RE`, closing the shape both clauses could not see: `p.open("a", encoding="utf-8")` matched nothing, so it was never examined by either check and read as clean. Two supporting changes were needed rather than the name alone. `_OPEN_CALLS` now maps each open-style call name to the position of its mode argument, because `Path.open` takes the mode first (the path is the receiver) while builtin `open` takes it second; `_open_mode` takes that index as a parameter instead of hardcoding 1, since reading position 1 of a `Path.open` call reads a keyword or nothing and reports silently. `_as_mode` was extracted from the raw `_literal_value` read so a mode must also look like one (at most three characters from `rwxab+t`): `.open` is shared with `webbrowser.open`, `os.open`, and `tarfile.open`, and accepting any literal as a mode makes `webbrowser.open("http://x")` a text write on the `x`. The encoding clause treats an unreadable mode differently per form, and deliberately: builtin `open` is unambiguously a file open so it is still reported, while a bare `.open` with an unreadable mode may not be a file open at all and stays silent.
- 2026-08-04 - Argument presence parsed instead of pattern-matched, replacing `"encoding=" not in call`, `"newline=" not in call`, `a.startswith("mode=")`, and `"text=True" in call`. Each asked whether a token appeared in the raw call text, which a string value, a comment, or a longer keyword (`file_encoding=`) satisfies and which whitespace (`newline = "\n"`) defeats. `_split_args` became `_arg_spans`, returning offsets rather than substrings, because the fix needs to read one argument's name and value from two differently blanked copies of the same source; `_blank_tokens` was factored out of `_code_only` to produce the second copy (`_no_comments`), and length preservation is what keeps a single set of spans valid for both. `_parse_call` returns a `_Call` carrying keyword arguments by name, positional values, and the two splat flags; `_open_mode` and `_is_text_mode_write` now take that parsed call rather than raw text. `_KWARG_RE` gained a capture group so the keyword's name can be read rather than merely detected. Splatted calls are skipped as unprovable, which is a documented false negative and matched nothing in the tree at the time. The subprocess clause was included because it carried the same defect (`note="text=True"` counted as text mode), which the first pass of this fix missed until a control caught it.
- 2026-08-05 - `check_python_code` now judges argument values, not only their presence. The encoding branch gained an `elif` for a keyword that is present but wrong, and the newline branch was restructured from one condition into a nested missing/wrong pair so the two answers stay distinguishable in the output. Three helpers back it: `_literal_or_none`, `_encoding_verdict`, and `_newline_verdict`. String prefixes are not a separate unreadable category: `ast.literal_eval` reads a prefixed literal like any other and returns the characters it really carries. The reason this is a separate round rather than part of the presence work is worth keeping: presence was the question the scanner could answer with the parser it had just been given, and answering it well read as finishing the job. The module docstring gained the new WARN and the note that the two clauses pin different-sized allowed sets, so a later reader does not "simplify" them into one shared check and quietly make `newline=""` a violation or `encoding="cp1252"` legal. `_literal_or_none` was rewritten onto `ast.literal_eval` in the same session: the first version compared source spellings, which would have flagged the legitimate `newline="\x0a"` and excused `r"\n"`, and it needed a regex for string prefixes that the evaluating version does not.
