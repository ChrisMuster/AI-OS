# Tests

**Last modified:** 2026-08-05

## Purpose
Unit tests for the encoding-guard script. They exercise the pure detection and repair helpers without touching the real project tree, verify the directory walk scans authored hidden config dirs while pruning system and verbatim-data dirs, and assert the guard's own source stays pure ASCII so it can never flag or repair itself.

## Contents
- test_encoding_guard.py - `workflows/encoding-guard/tests/test_encoding_guard.py` [[workflows/encoding-guard/tests/CONTEXT]] - Tests for signature generation, `scan_text`, `repair_text`, `repair_bytes`, `_has_encoding_problem`, the code checks (which constructs are calls at all, then their argument presence and values), the hidden-dir walk filtering (`iter_text_files`), and the pure-ASCII-source guarantee.
- run_tests.py - `workflows/encoding-guard/tests/run_tests.py` [[workflows/encoding-guard/tests/CONTEXT]] - One-command unittest runner for this directory.

## Inputs
None. Tests construct their own in-memory fixtures and a throwaway temp tree for the directory-walk test.

## Outputs
None. Prints a unittest summary; exits non-zero on failure.

## Steps
Run from anywhere:

```
python workflows/encoding-guard/tests/run_tests.py
```

## Dependencies
- `workflows/encoding-guard/scripts/run.py` [[workflows/encoding-guard/scripts/CONTEXT]] - The module under test, imported directly.
- Python 3.9+ standard library (unittest, tempfile).

## Revision History
- 2026-06-24 - Initial creation.
- 2026-06-25 - Added TestHiddenDirWalk covering the blind-spot fix: `iter_text_files` now scans authored hidden config dirs (e.g. `.codex`) while still pruning system dot-dirs (`.venv`, `.vscode`) and the verbatim-data exemptions (`raw/`).
- 2026-08-04 - Added 17 tests for the CRLF check and the narrowed repair, taking the suite from 26 to 43. Written against the stated rule rather than the implementation, with a positive control (a CRLF file is reported), a negative control (an LF file is not), and a lone-CR case. Three cover the traps rather than the feature: that the real pipeline reads bytes, so a later change to text-mode reading cannot make the check silently unfireable; that a CRLF-only file keeps its em dash through `--fix`, which is the regression that would follow from routing it through `repair_bytes`; and that `--preserve-mtime` holds a LOG.md timestamp while its absence moves it, since that flag exists to stop a bulk pass falsifying doc-sync-guard's evidence.
- 2026-08-04 - Added `TestNewlineCheck` (8 tests, suite 43 to 51) for the newline clause of the text-I/O rule, after it turned out the code check returned early on `encoding=` and so never enforced it. The positive controls are constructed from the rule as AGENTS.md states it rather than copied out of the tree, which is the half that proves a checker reads the right definition instead of merely firing on something: `write_text` with an encoding and no newline, the five `open()` write modes, and the `mode=` keyword form. The negative controls pin what must stay silent - compliant writes, `csv`-style `newline=""`, reads, binary writes, `subprocess`, prose in a docstring, and a computed mode the checker cannot read and must not guess at. One test asserts the structural guarantee directly: a write missing both arguments reports one finding per clause, so neither check can ever swallow the other again. The six local fixture writes in this file were converted to `write_bytes` in the same pass, since a test suite for this rule breaking it was the first thing a reader would notice.
- 2026-08-04 - Seven tests added for the `.open(...)` write shape (suite 51 to 58), the gap that let a CRLF-writing append pass the entry above. The positive controls are the same rule applied to the call form the earlier ones happened not to cover: an append with an encoding and no newline, the five write modes on a variable receiver, the `mode=` keyword form, and the wrapped-arguments-on-an-expression-receiver layout the project actually uses. Two are controls on the failure mode rather than the feature. `test_the_mode_is_read_from_the_right_argument_position` asserts both sides of the mode offset, because reading the wrong position is silent rather than loud: a builtin read whose path would itself look like a write mode (`open("wax.md", ...)`) must stay clean, and a dotted write must still fire. `test_unrelated_dot_open_calls_are_not_read_as_file_modes` pins the false positives the widened pattern would otherwise create, `webbrowser.open("http://x")` among them, since `.open` is not owned by `pathlib`. The suite's own fixture writes were already compliant and were not touched.
- 2026-08-04 - Added `TestArgumentPresence` (8 tests, suite 58 to 66) for whether an argument is *present*, as distinct from whether its name appears somewhere in the call. The earlier newline and `.open` rounds were both about the checker not seeing a call; this one is about it seeing the call and still answering wrongly, so the controls are split by direction. Positive controls prove the sentinel is not the argument: it inside a string value, inside a comment, and inside the longer keyword `file_encoding=`. Negative controls prove the argument survives spelling: whitespace around `=` in `newline`, `encoding`, and `mode`, where the spaced `mode` case is the one that mattered most, because a mode read as absent is read as a text read and skips the newline clause on a real write. Two more pin the honest-silence boundary for splatted calls rather than a feature. The direction split is the point: a suite built only from missing-argument controls passes on a checker that reports everything, and half of this defect was false positives.
- 2026-08-05 - Added `TestArgumentValues` (13 tests, suite 66 to 79) for whether an argument carries the value the rule names, the question the three presence rounds above left unasked. Positive controls: `encoding=None` and a wrong codec, the same on a text-mode `subprocess` call, `newline=None`, and a newline spelled with a carriage return. Two pin scope rather than a value. One asserts the encoding clause fires on *reads* as well as writes, since a read decoded as cp1252 is how mojibake gets in and the newline clause's write-only scope must not be inherited. The other asserts severity, because only WARN hard-fails the close-out gate: a missing `encoding=` stays INFO, a wrong one blocks. Negative controls hold the two allowed sets apart - every spelling of UTF-8 that Python's codec lookup folds together, and `newline=""` for `csv` - and pin the unreadable cases (a variable, an expression, an f-string) as silent rather than judged. Two more pin the difference between a value and its spelling, added after the source-text comparison they describe was replaced with `ast.literal_eval`: `newline="\x0a"` must pass because it evaluates to a line feed, and `newline=r"\n"` must fire because it evaluates to a backslash and an 'n', which `open()` itself rejects. One more repeats the structural guarantee for the new branch: a wrong value plus a missing argument still reports one finding per clause. The `Path.write_text(..., newline=...)` sample in `TestNewlineCheck` was also annotated rather than removed: it is the negative control for that write shape, but it is a 3.10-only API against the project's stated 3.9 floor, so the comment says plainly that it is not a recommended spelling and points at the Python-floor backlog item that owns the version question.
- 2026-08-05 - Added `TestCallDiscovery` (16 tests, suite 79 to 95) for the step before every other class in this file: whether a construct is a call at all. The four earlier rounds are all about reading a call correctly, and each of them assumed the thing being read was a call; a regex over source text cannot tell `def open(self, mode="w")` from a text write, and that difference had become a close-out hard fail. The controls are written from that boundary rather than from the fix, and they are split three ways because the fix could go wrong in three directions. Positive controls that must stay *silent* pin the definitions (`def`, `async def`, `class`, nested, and the same for `read_text`/`write_text`) and the non-path `.open` receivers (`tarfile`, `zipfile.ZipFile(...)`, `shutil`, and the `io`/`codecs`/`gzip` group whose exclusion is a stated false negative). Positive controls that must still *fire* pin every receiver shape the project actually writes - a bare name, `Path(x)`, an expression with no name at its root, a subscript, an attribute chain - because a receiver rule that dropped calls too eagerly would pass the whole silent block by checking nothing, and the expression receiver is precisely what a "skip anything I cannot name" rule would lose. One test pins the residual false positive (`thing.open("w")` is still checked) so it reads as a decision rather than a bug. Three cover the degrade path: an unparseable file reports DEGRADED and not WARN, the message names the file and the reason, and prose in a non-Python file produces no findings at all, which is the behaviour the old tokenise fallback got backwards. Two cover offsets: a call after non-ASCII text on an earlier line, because `ast` column offsets are UTF-8 byte offsets rather than character ones, and a parenthesis inside a trailing comment, which must not be mistaken for a call's.
