# Biblio Tools Scripts

**Last modified:** 2026-11-24

## Purpose
Contains the canonical project-runtime setup and hand-off helpers, MCP server, setup verification, launcher, and protocol smoke-test scripts.

## Contents
- server.py - `workflows/biblio-tools/scripts/server.py` - The `MCPServer` (`mcp` 2) server defining all ten tools and their typed parameters, including the knowledge-graph build and query dispatcher assembled by the pure, unit-testable `build_kg_query_argv` helper. Its `mcp` import carries a `# runtime-guard: launched via launch.py` marker (below). When run as a script it starts a lifecycle watchdog that exits when the process named in `BOOK_DRAGON_LAUNCHER_PID` (launch.py) dies, falling back to its own parent when the variable is absent, or after 4 hours without a tool call. It watches launch.py rather than its own parent because on Windows its parent is the venv's launcher stub, which outlives a killed launch.py; and not stdin, because `mcp` 2 points a stdio server's stdin at the null device.
- verify.py - `workflows/biblio-tools/scripts/verify.py` - Setup verification script (doctor pattern). Checks environment configuration, shared PDF ingestion, and the configured MCP server for any supported AI. Standard library only. Holds the project Python floor as `PYTHON_FLOOR` and judges both the Python running it and the project `.venv` interpreter against it via `floor_result`: below is a FAIL, above is a WARN tagged `"surface": true` (shown as `[SURFACE]` in plain text and counted in the JSON summary) so that session startup reports it, since the floor is only tested while it is the version the project runs. Its "Codex hook output" check, also for every AI, confirms the Codex SessionStart and Stop hook commands ask for their Codex modes and runs each mode (`rule-hooks run.py --reinject --ai codex`, and `session-search index.py --codex-stop-hook --dry-run`, which writes nothing) to confirm the output is the JSON Codex accepts, since a trusted hook printing anything else is reported as failed in every Codex session; any mismatch is a surfaced FAIL. Accepted means: a JSON object holding only the fields Codex's output schema for that event allows (`CODEX_SESSION_START_FIELDS`, `CODEX_SESSION_START_INNER_FIELDS`, `CODEX_STOP_FIELDS`, from Codex's published schemas, all with additional properties forbidden) with values of the schema's types (`CODEX_HOOK_FIELD_TYPES`), a SessionStart `hookSpecificOutput` naming SessionStart with `additionalContext` text, and a Stop answer that neither blocks nor sets `continue` to false. While `.codex/config.toml` exists, both hooks must be defined. It checks the command strings for the script and flag rather than running the configured launcher line (which for Stop would index for real), so a launcher printing text of its own would pass it; Codex's own report of a hook run is the proof of that. Its "Codex hook trust" check runs for every AI and asks the installed Codex, through its app-server's `hooks/list` request over stdio (no model call, about three seconds), whether it will run each project hook defined in `.codex/config.toml`, under both drive-letter spellings of the project path on Windows. It compares Codex's answer with the hooks the config defines, one per command, so any defined hook Codex would skip, whether unapproved, disabled or simply not listed, is a surfaced FAIL. Plugin hooks are not judged, a missing Codex is a quiet WARN, and a Codex that does not answer within 20 seconds, or gives no answer for one of the spellings, is a surfaced WARN. On a Python without `tomllib` the check returns a surfaced WARN rather than crashing, so the floor FAIL still reaches the report. Its "Review-orchestration SDKs" check, for every AI, asks the project `.venv` interpreter whether `claude_agent_sdk` and `openai_codex` can be found (`importlib.util.find_spec` in a short subprocess run in isolated mode, `-I`, so a `PYTHONPATH` set by another project cannot supply them; it loads neither): both found is a PASS, and a missing one, no `.venv` or a probe that fails is a WARN naming `workflows/review-orchestration/requirements.txt` [[workflows/review-orchestration/CONTEXT]], never a FAIL, since the workflow is optional and a round or run started without an SDK is refused at its own preflight. Its "Codex MCP registry" check, for Codex only, runs `codex mcp get biblio_tools` through the path `shutil.which` resolves, since that honours PATHEXT and so finds a `codex.cmd` shim that `subprocess` given the bare name would not.
- launch.py - `workflows/biblio-tools/scripts/launch.py` - Cross-platform launcher that uses the project `.venv` interpreter when available. It stops the script it starts when its own parent (the AI session) dies, and passes its process ID to that script in `BOOK_DRAGON_LAUNCHER_PID` so the script can exit if launch.py itself is killed.
- mcp_smoke.py - `workflows/biblio-tools/scripts/mcp_smoke.py` - Connects to a configured stdio server, completes the MCP handshake, confirms the ten-tool inventory, calls read-only tools, checks input/path rejection, and verifies knowledge-graph query wiring using saved-index stats when available with a lightweight no-index fallback. Carries a `# runtime-guard: launched via verify.py/lifecycle_check.py under the project .venv` marker (below).
- lifecycle_check.py - `workflows/biblio-tools/scripts/lifecycle_check.py` - Verifies helper-process lifecycle safeguards: MCP handshake, parent-death cleanup (launch.py exits when its parent dies), launcher-death cleanup (server.py exits when the launcher it was given dies, with its stdin still open and the killed stand-in not yet reaped), Codex plugin launcher-death cleanup (a copy of the plugin's `launch_biblio.py` [[.codex/plugins/plugins/biblio-tools/mcp/CONTEXT]], run outside the project as Codex's cache runs it, with the registered `python` command and no project-root hint, must find the project, stay alive after the server answers an MCP initialize, and the server must exit once it is killed, seen as end-of-file on its stdout; every wait is bounded by a named constant, and a surviving server is reported as FAIL rather than hanging the check, stdin closed first and stdout closed only once no reader is blocked on it), and reader stale-PID safety.
- setup.py - `workflows/biblio-tools/scripts/setup.py` - Creates or repairs the canonical `.venv`, installs the root dependency manifest, and verifies package availability and the `.venv` interpreter version (one probe, `runtime_probe`). A `.venv` below its `PYTHON_FLOOR` fails `--check` and is refused for repair, with instructions to delete and recreate it; the script never deletes it.
- runtime.py - `workflows/biblio-tools/scripts/runtime.py` - Shared project-runtime helpers: `.venv` discovery, process liveness checking (cross-platform: Windows reads the exit code; on POSIX a zombie, killed but not yet reaped, counts as dead, read from `/proc/<pid>/stat` or, without `/proc`, from `ps`), the `LAUNCHER_PID_ENV` name shared by launch.py and server.py, and runtime hand-off for dependency-bearing entry points.

## Inputs
None. The server is started by the AI's MCP client.

## Outputs
- Tool responses returned to the MCP client as structured data (JSON).
- Per-AI setup results that distinguish file/config presence from a working MCP handshake and tool inventory.
- A shared `.venv` containing all dependencies declared by the root `requirements.txt`.

## Steps
N/A. The server is started automatically by the MCP client, not run manually.

## Dependencies
- Python `mcp` package (2.x) - Provides `MCPServer` for tool definitions and server runtime, and the client used by mcp_smoke.py.
- `workflows/review-orchestration/requirements.txt` [[workflows/review-orchestration/CONTEXT]] - verify.py's SDK check looks for the two packages it pins (`REVIEW_SDKS` holds their import names, which a test compares with the file).
- Root `requirements.txt` - Includes every workflow-specific Python dependency manifest.
- Project `.venv` - Canonical runtime used by all dependency-bearing workflow entry points.
- All project scripts listed in `workflows/biblio-tools/CONTEXT.md` [[workflows/biblio-tools/CONTEXT]] Dependencies section.

## Known Issues
- The Codex hook trust check finds Codex on PATH, in the Codex desktop app's install folder, or in the VS Code Codex extension, taking the newest build in the first place that has one. A Codex installed anywhere else reads as not installed, which is a quiet WARN rather than a failure. It speaks the app-server's `hooks/list` request directly, so a Codex release that renames that request or its fields would turn the check into a surfaced "could not ask Codex" WARN rather than a false pass.
- The check asks Codex through a background process, so it adds about three seconds to every setup verification on a machine where Codex is installed.
- The comparison assumes `hooks/list` reports one entry per command, which is what Codex 0.152.1 does (its keys end `:<event>:<group>:<command>`), and matches config event names such as `PreToolUse` to Codex's `preToolUse` ignoring case. If a Codex release changed either, the check would report defined hooks as not listed, a surfaced FAIL rather than a false pass; the live test `test_codex_answers_for_this_project` is the one that would show it.
