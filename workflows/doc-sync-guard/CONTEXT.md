# Doc-Sync Guard

**Last modified:** 2026-08-12

## Purpose
Catches CONTEXT.md / LOG.md drift the moment a directory's real content changes but its own documentation is not updated in the same change. It is a deterministic, read-only checker in the guard family (same shape as `encoding-guard`, `personal-data-guard`, and `ai-style-guard` [[workflows/ai-style-guard/CONTEXT]]): a standalone CLI that the full audit and the close-out verifier consume. For every committable directory that changed at all, it verifies that the directory's `CONTEXT.md` moved (a new Revision History entry, with `**Last modified:**` matching the newest entry date) and that its gitignored `LOG.md` gained an entry (verified by mtime, since a gitignored file cannot be content-diffed). "Changed at all" covers two populations: a directory whose real content moved (a file added, removed, or edited that is not the directory's own CONTEXT.md/LOG.md), and a directory whose own `CONTEXT.md` was the only file to change. The second used to open no case at all, which made a directory's own `CONTEXT.md` the one file in the project that could be edited without being checked; the Revision History and Last modified clauses now cover it at WARN like any other drift, while the LOG clause reports it at INFO only (see Known Issues). It also covers the one mechanical parent-propagation case: a child directory added or removed without the parent CONTEXT.md moving. This makes the AGENTS.md "Work maintenance and close-out" rule reliable rather than discipline-dependent. There is deliberately no fix mode: the AI that made the change knows why each directory changed and writes proper entries from that knowledge, where a context-free script could only produce filler.

## Inputs
- `config/output-inventory.yaml` [[workflows/doc-sync-guard/config/CONTEXT]], read through `scripts/inventory.py`: the classified record of every gitignored path. The check loads it and reports a DEGRADED finding if it cannot be read (a component that could not run, not drift); it does not yet act on the documentation answers.
- The current change set, discovered via git: `git diff <base>` (base HEAD by default) plus untracked committable files, or `git diff --cached` in `--staged` mode. Git must be available; without it the guard reports a single WARN finding and scans nothing.
- On-disk `CONTEXT.md` and `LOG.md` files of the changed directories, read to check final-state dates and the newest LOG entry timestamp.

## Outputs
- A findings report on stdout (human text, or `--json` for the audit hook). Drift is WARN under a `doc-sync` label. A second severity, INFO, carries a clause that is built but switched off: today only the LOG check for a CONTEXT-only directory, which is recorded rather than enforced while its rate against real commits is measured. A third severity, DEGRADED, reports a component that could not run (today only the output-inventory probe, which needs PyYAML while the drift scan does not); it is separated from WARN because a `doc-sync` WARN means drift to every consumer, and a missing package is not drift.
- Exit code 0 by default (advisory). With `--strict`, exit 1 when any WARN exists, so a caller can gate on it. A DEGRADED finding never trips `--strict`: the runtime needs repairing, not the documentation.
- No files are written and no LOG.md entry is made on a check run (read-only, like the other content guards).

## Steps
1. Scan the changed directories for CONTEXT.md / LOG.md drift (read-only):
   `python workflows/doc-sync-guard/scripts/run.py --check [--json] [--since REF | --base BRANCH | --staged] [--strict]`
2. Review any WARN findings and update the flagged `CONTEXT.md` / `LOG.md` files (the guard reports directory and reason; it never edits).
3. Re-run until the report is clean.
4. Append LOG.md only when run as a deliberate, logged workflow step (the read-only check and the audit-hook invocation do not log).

## Dependencies
- `AGENTS.md` [[AGENTS]] (root) - Defines the "Work maintenance and close-out" CONTEXT/LOG obligations this guard enforces mechanically, the CONTEXT.md schema (Revision History, Last modified), and the LOG.md rules.
- `templates/` [[templates/CONTEXT]] - The CONTEXT.md and LOG.md schema this guard checks against.
- The `git` CLI for change discovery; otherwise the Python 3.9+ standard library. The guard's own check path stays standard-library only: the inventory loader is the one component needing PyYAML, it is imported lazily, and a run on an interpreter without it reports a DEGRADED finding rather than failing.
- Consumers (all live): `workflows/audit/` [[workflows/audit/CONTEXT]] runs it as an advisory hook, merging drift as WARN under a `doc-sync` label without changing the audit's own exit code, and re-wrapping a DEGRADED finding through its own `degraded()` helper so it arrives with the standard runtime-repair hint; `workflows/close-out/` [[workflows/close-out/CONTEXT]] turns any `doc-sync` WARN into a hard fail (the deterministic gate) while routing a `doc-sync` DEGRADED down its non-blocking degraded path; `workflows/rule-hooks/` [[workflows/rule-hooks/CONTEXT]] runs it as a warn-not-block step in the universal git pre-commit hook; `workflows/handoff/` [[workflows/handoff/CONTEXT]] surfaces a doc-sync section in the gather packet; and `workflows/triggers/` [[workflows/triggers/CONTEXT]] exposes the on-demand "check context is current" phrase.

## Known Issues
- LOG.md freshness is verified by mtime because LOG.md is gitignored and cannot be content-diffed. This is reliable in the build-once-at-the-end flow (the whole body of work stays uncommitted with real mtimes). A deliberate mid-task git operation that rewrites an in-scope file's mtime while leaving LOG.md untouched (a mid-task commit then checkout, `git stash`/`pop`, or `git checkout -- <file>`) can raise a loud false positive - never a silent miss, with the commit-time gate as backstop.
- The check enforces the bookkeeping obligation (the required entries exist), not the correctness of the prose. A Revision History entry with wrong content still passes.
- Subjective parent-directory propagation (whether a change is significant enough for a parent Revision History entry or prose rewrite) stays a human/AI close-out judgement; only the mechanical child add/remove case is enforced.
- Discovery depends on git. Outside a git checkout the guard scans nothing and emits a single WARN finding so audit, close-out, handoff, and pre-commit do not mistake an unrun scan for a clean scan.
- The output inventory is hand-maintained. A test asserts that every non-comment `.gitignore` line is answered by a row, so a line added without one fails the suite; nothing yet catches a script writing to a path nobody registered at all, which is a separate job.
- The inventory loader answers per path, never by prefix, so a documented child directory inside an exempt data store falls through to the default rather than inheriting its container's exemption. Deciding which directory answers for a given file is the caller's job and is not implemented here.
- The Revision History clause does not check an entry's date, so an entry backdated to any date passes as long as the line itself is new. This holds for the plain-add case; the archive-plus-append branch does compare dates, requiring at least one genuinely new entry dated no earlier than the newest retained entry. Adding a date comparison to the plain-add case would be a new assertion needing its own controls, so the clause is used as it stands.
- The Revision History clause still biases to a loud warning on any archive it cannot verify, which is deliberate and is not a silent-miss risk. The same-day re-archive case that made this expensive was closed by stage 14b on 2026-08-12: the clause now asks whether an archive is *recorded* and has not moved backwards rather than whether the reference line *changed*, so a directory archived twice on the same date is no longer read as an in-place edit. Over the branch history back to 2026-06-01 that took clause A from 41 warnings to 32. What remains warning is either genuine (a missing entry, or entries removed with nothing recording an archive) or a shape the guard cannot tell from a forgery - retained entries rewritten alongside the archive, or every old entry archived at once - and those keep warning on purpose.
- **The LOG clause is built but switched off for CONTEXT-only directories**, reporting `INFO` rather than `WARN`, so a CONTEXT-only edit with no corresponding log entry is recorded and not caught. This is a deliberate deferral awaiting a live measurement, not an oversight: unlike the other two clauses it cannot be replayed over history at all (it compares the newest entry parsed out of a gitignored `LOG.md` against a filesystem mtime, and git records neither), so there is no way to know its warning rate in advance, and a `doc-sync` WARN is a close-out hard fail. The whole discharge path: a producer precondition starts the clock, meaning the guard is run once through the pre-commit hook's own interpreter, confirmed to report zero `DEGRADED`, and that result recorded in this directory's `LOG.md` in an entry whose Note contains the exact token `STAGE14-PRODUCER-OK` (until that line exists the period has not started, whatever the fire-log holds); samples then accumulate in `workflows/rule-hooks/fire-log.jsonl`, one record per pre-commit fire that reaches the doc-sync step, carrying that fire's `INFO` and `DEGRADED` counts; the observation period is 30 usable rows rather than a span of calendar time, since evidence only arrives when a commit is made; a sample counts only from a fire reporting zero `DEGRADED`, and if `usable` is zero while `fires` is not, or exclusions are the majority, the answer is to repair the producer runtime and keep sampling, never to close the decision on the surviving rows. The read command is recorded in the guard-coverage plan in both a POSIX and a PowerShell form, and both test for the marker. At the end of the period the count and the enable / drop / redesign decision land in this workflow's own `LOG.md`, and this bullet is rewritten or removed to match with a Revision History entry.
- None of the tracked changes made by the re-plan pass that specified this stage is visible to the guard itself. Each was a CONTEXT-only edit, which opened no case, and the plan documents it moved are gitignored so they never appear in a diff. That pass is a live worked example of the defect this stage closes.
- The guard only checks the current working tree against HEAD, so drift is caught per-commit at the pre-commit hook and again at close-out; a commit made with `--no-verify` (or on a machine with no hook installed) bypasses the gate and is not re-checked afterward - commit through the hook. A whole-branch audit is available on demand with `--base main`, accepting that its mtime-based LOG half is noisy against already-committed files.
