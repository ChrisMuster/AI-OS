# Doc-Verify - Tests

**Last modified:** 2026-08-04

## Purpose
Hermetic tests for doc-verify, and the executable form of its verification protocol. Every check carries three controls, named as such in the test names, because the defect that prompted this workflow was a checker proved by the wrong control: a checker that passes only a negative control has shown it does not over-fire, which is the failure mode nobody was worried about.

All three are stated against **the subject** - the thing the check is about - because that is the only phrasing that survives the counting/validating split below:

- **Positive control** - a legal instance of the subject, constructed from the specification rather than copied out of a document. A table checker gets a two-space-indented separator row, because CommonMark permits up to three.
- **Rejection control** - an illegal instance of the subject, which the check must refuse: a citation range past end of file, a missing file, a reversed range, a four-space-indented separator (an indented code block, not a table).
- **Negative control** - something that is not an instance of the subject at all, drawn from real prose: a clock time is not a citation, "the paragraph above" is not a distance reference, two tables each numbered from 1 are not duplicates of each other.

**A counting checker and a validating checker read "positive control" oppositely, and conflating them is how an illegal instance gets filed as a positive one.** For a counter (`find_tables`, `check_distance`, `find_citations`) a legal instance must be **found**. For a validator (`check_hygiene`, `check_tables`, `check_sequences`, `check_heading_order`, `check_citations`) a legal instance must produce **nothing**, so a CRLF file or a table numbered 1, 3, 2 is an illegal instance and belongs under `rejection_control` however much "the checker found it" reads like a positive result. The class docstrings state which kind each checker is.

**A counting checker that refuses nothing has no rejection control**, and that is a property of the check rather than a gap here: `check_distance` reports INFO candidates and never issues a verdict, so there is no refusal path to prove, and `DistanceTests` carries a positive and a negative control and no third. Inventing one would assert a refusal the checker is specified not to make.

No git, no network, and no dependence on any real document, so the suite is deterministic and safe to run anywhere.

## Contents
- test_run.py - `workflows/doc-verify/tests/test_run.py` [[workflows/doc-verify/tests/CONTEXT]] - 101 tests in thirteen classes: `HygieneTests` (CRLF, tab, trailing whitespace, missing final newline, em dash and non-breaking space by codepoint, invalid UTF-8, clean-file and blank-line negative controls, a whitespace-only line, a CRLF file not double-reported per line, a real trailing space still found inside a CRLF file, an empty file, a loud failure when hygiene is selected without bytes, and `check_file` reading binary so CRLF survives to the check); `FenceTests` (content blanked, line numbers preserved, unterminated fence, marker not closed by a different marker); `TableDetectionTests` (2- and 3-space indents accepted, 4-space rejected, pipe-less rule and fenced separator ignored); `CellCountTests` (leading/trailing pipes, escaped pipe); `TableUniformityTests` (ragged body row, ragged header, separator with no header); `SequenceTests` (gap, duplicate, prefixed `E10` series, lettered sub-item, the pooling negative control, a row out of order, one misplaced row reported once rather than once per later row, successive lettered sub-items ordered, a sub-item written above its own number, a descending table refused, and a duplicate not double-reported as a descent); `HeadingOrderTests` (descending order, gap, duplicate, separate parents not pooled, unnumbered ignored, one misplaced section reported once); `LineCountTests` (a newline-terminated file, an unterminated final line, an empty document, a lone newline, the stats block a caller quotes, and a citation to the last line of a terminated file, which pins the half that was already right); `DistanceTests` (cardinal and digit forms, ordinal, bare direction excluded, direction in a later sentence not swept, INFO tier asserted, plus the logical-line cases: a reference split by a hard wrap is found, reported at the line it starts on, and the join crosses neither a blank line, nor two table rows, nor a full stop); `CitationParseTests` and `CitationResolutionTests` (long form, range, shorthand, clock/version negative controls, past-EOF and missing-file rejection controls); `DocumentTests` (whole-document stats, check selection, clean-document behaviour); and `SmokeTests` (the real CLI as a subprocess: valid JSON at exit 0, `--strict` exit 1 on a FAIL, INFO alone not gating, missing file exit 1, and invalid UTF-8 reported through the hygiene finding rather than the generic read-error path).

## Inputs
- None beyond the checker's `scripts/run.py`, imported directly by file path. Every fixture is built inline or in a `tempfile` directory.

## Outputs
- Test results on stdout (unittest). Exit code 0 when all pass, non-zero on failure. No files written outside the temporary directory.

## Steps
1. Run `python workflows/doc-verify/tests/test_run.py`.
2. Confirm every test passes (exit 0).
3. When adding or changing a check in `scripts/run.py`, add all three controls for it here in the same change.
4. Append LOG.md only when run as a deliberate, logged workflow step.

## Dependencies
- `workflows/doc-verify/scripts/run.py` [[workflows/doc-verify/scripts/CONTEXT]] - the module under test, loaded by `importlib` from a file path.
- Python 3.9+ standard library only (`unittest`, `tempfile`, `importlib`, `subprocess`, `json`, `sys`).
- `workflows/close-out/` [[workflows/close-out/CONTEXT]] discovers and runs this suite (`tests/test_*.py`) as part of the close-out verifier.

## Known Issues
- The controls prove each checker matches its stated definition. They cannot prove the definition is the right one to have chosen; that stays a review judgement, which is why the definitions are written out in prose where a reviewer can attack them.
- Nothing enforces the control naming. A test added without a `positive_control` / `rejection_control` / `negative_control` prefix is simply an unlabelled test, and a defect fixture mislabelled as a positive control passes exactly as well as a correct one - which is how three checkers carried the wrong label for four rounds. The convention is held by review and by the class docstrings alone.
- `SmokeTests` shells out to the real CLI five times, so the suite is subprocess-bound rather than CPU-bound. It still runs quickly.
- Fixture files must be written with `write_bytes`, never `write_text`: on Windows a text-mode write converts every `\n` to CRLF, so a text-mode fixture makes the hygiene check fire on the test's own file instead of on the property under test. This bit three tests the moment the hygiene check was added, and nothing enforces the convention beyond this note and the docstring on `SmokeTests`.
