# Doc-Verify

**Last modified:** 2026-07-30

## Purpose
Read-only structural self-consistency checker for a single long markdown document, given as an argument. A long design document accumulates claims about itself - how many tables it has, that its enumerated rows and numbered sections are contiguous, that a cross-reference points where it says, that a code citation resolves - and verifying those by writing a fresh throwaway script each review round means every runner re-implements the definition. A wrong definition then produces a confident wrong number: the case that prompted this workflow published a table count measured by a checker anchored at column 1, when Markdown permits up to three leading spaces, and the figure propagated to five surfaces before a reviewer caught it.

This is the tracked, tested implementation the AGENTS.md verification-discipline rule already required (a script whose output is quoted belongs in the repo with tests). The target file is a CLI argument and never embedded, so the same checker serves a tracked document, a gitignored design document, or a handover packet without carrying a personal path.

It does not duplicate what the existing guards genuinely cover, and the boundary is drawn from what they check rather than from what they are for. `encoding-guard` [[workflows/encoding-guard/CONTEXT]] reports invalid UTF-8, mojibake and BOMs across the whole tree, including gitignored files, and none of that is repeated here. What it does **not** report is CR bytes, tabs, trailing whitespace, or a missing final newline: its `--fix` normalises line endings, but `--check` never mentions them, so a CRLF file passes silently. `ai-style-guard` [[workflows/ai-style-guard/CONTEXT]] does police typographic tells, but it is scoped to `git diff` content and therefore cannot see a gitignored file at all. Between the two, nothing was checking line endings or typography for a gitignored document; the `hygiene` check here closes that gap, in binary mode, because a text-mode read on Windows translates CRLF to LF and hides the very bytes the check exists to find.

## Contents
- scripts/ - `workflows/doc-verify/scripts/` [[workflows/doc-verify/scripts/CONTEXT]] - The `run.py` entry point and its pure parser/checker functions (binary hygiene, fences, tables, sequences, headings, distance references, citations).
- tests/ - `workflows/doc-verify/tests/` [[workflows/doc-verify/tests/CONTEXT]] - 101 hermetic tests carrying a positive and a negative control for every check, and a rejection control for every check that can refuse.

## Inputs
- One or more markdown file paths, passed as CLI arguments (read as UTF-8). Project-root-relative, per the relative-paths rule.
- For the citation check only: the files a document cites, read from the project root to confirm each path exists and each line range falls inside it.
- No git, no network, no config file.

## Outputs
- A findings report on stdout (human text, or `--json`), plus measured counts per document: lines, tables, table rows, and citations.
- Exit code 0 by default. With `--strict`, 1 when any FAIL or WARN exists; INFO never gates. An unreadable target file always exits 1.
- No files are written and no LOG.md entry is made on a check run (read-only, like the other content guards).

## Steps
1. Run the checker over the target document:
   `python workflows/doc-verify/scripts/run.py --check [--strict] [--json] [--only <check>] <file> ...`
2. Fix every FAIL (a CR byte, tab, trailing space, missing final newline or non-ASCII codepoint; a ragged table row; a sequence gap, duplicate, or table row or heading out of ascending order; a citation whose file is missing or whose range is outside it) and every WARN (a path-less shorthand citation).
3. Adjudicate the INFO candidates by hand. These are distance references and ordinals into growing lists; the discriminator is whether deleting the distance leaves the sentence still saying what it came to say. A claim *about* distance is content and stays.
4. Re-run until FAIL and WARN read zero, so `--strict` is a real gate rather than a tolerated baseline.
5. Append LOG.md only when run as a deliberate, logged workflow step (a read-only check does not log).

## Dependencies
- `AGENTS.md` [[AGENTS]] (root) - the verification-discipline rule this workflow is the executable half of, the encoding rules its I/O follows, and the relative-paths rule its arguments follow.
- The Python 3.9+ standard library only (no third-party packages, so no `.venv` bootstrap is needed).
- `workflows/encoding-guard/` [[workflows/encoding-guard/CONTEXT]] - a boundary rather than a delegation, and the distinction is load-bearing. encoding-guard's `--check` reports invalid UTF-8, mojibake and BOMs across the whole tree including gitignored files, and none of that is repeated here. It does **not** report CR bytes, tabs, trailing whitespace or a missing final newline, so nothing is delegated to it: the `hygiene` check implements those independently, in binary mode. If encoding-guard's scope ever narrows to tracked files only, the three properties it does cover stop reaching a gitignored target and this workflow inherits that gap; the five it never covered were never its to lose.
- `workflows/ai-style-guard/` [[workflows/ai-style-guard/CONTEXT]] - polices typographic tells project-wide but is scoped to `git diff` content, so it cannot see a gitignored file. Nothing is delegated to it either; the codepoint half of the `hygiene` check is what covers those tells for a target it cannot reach.
- `workflows/close-out/` [[workflows/close-out/CONTEXT]] discovers and runs this workflow's test suite as part of the close-out verifier.

## Known Issues
- The distance check reports candidates, never verdicts, and it cannot be otherwise: separating a rotting reference ("the rule two bullets down") from a claim about distance ("round 31 replaced *two bullets up*, which never pointed at that trap") needs judgement. Expect a worklist with legitimate entries in it, and read every one.
- The distance check matches over logical lines, joining consecutive prose lines so a reference broken by a hard wrap is still found. Two consequences worth knowing: a candidate is reported at the line it **starts** on, which is not always the line the direction word sits on; and joining is bounded by blank lines and table rows only, so a sentence that ends without a full stop immediately before a line break can in principle match across the join. Both are accepted, because the alternative is a check whose output depends on where the text happened to wrap.
- A table is recognised only by a separator row carrying a leading pipe, which is the form this project's documents use. A pipe-less Markdown table is legal CommonMark and is not detected. Stated as a definition so a reviewer can disagree with it rather than discover it.
- Fenced code blocks are excluded from every check, so a genuinely broken citation written inside a fence is not reported. This is deliberate - a fence holds quoted or illustrative material - but it is a place a defect can hide.
- Heading-order checking covers plain dotted numbers (`## 4.`, `### 9.2`). A lettered sub-item heading (`### 4.6a`) is not matched and so is neither ordered nor counted.
- Order means **ascending**, for table rows and headings alike, so a deliberately reversed enumerated table (5, 4, 3, 2, 1) is reported as out of order. Accepting either direction would catch the same defects, since 1, 3, 2 is neither ascending nor descending, but it would put two meanings of "in order" inside one check and give a reviewer two definitions to hold. Stated as a limitation so a document that genuinely wants a descending table knows to exclude the check (`--only`) rather than discovering the refusal.
- The checker cannot tell a legal instance quoted for discussion from a real one: a document that writes a banned citation form in order to describe it fails its own check. The resolution is on the document's side (describe the bad form rather than quoting it), which is a constraint on the writer that this file records rather than solves.
